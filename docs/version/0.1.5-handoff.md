### A. 架构收尾：Numen 成为纯插件（必须）

**目标**：`core`（对外叫 **Numen**，模组 id `numen`）是 **Numen API**（`api`，模组 id `numen_api`）的第一个插件，与内置插件、第三方插件平级，只通过 `NumenPlugins.register` 接入，没有特殊待遇。

**现状与差距**：
- `api/common/build.gradle` 有 `api project(':pathing')`，`buildSrc/src/main/groovy/api-loader.gradle` 把 pathing 平铺进引擎 jar。
- `NumenPlayer implements com.dwinovo.numen.pathing.body.Body`（`api/common/.../entity/NumenPlayer.java:46`）。
- `core/common` 编译期依赖完整的 `api:common`，源码里直接导入 pathing（约 145 处）、`network`、`area` 等非公共包。

**由此产生的已证实缺陷**（10-06 在仓库外实测编译）：
- 0.1.4 全部 13 个版本的 `numen-api-<loader>-<mc>` POM 都引用了**未发布**的 `numen-pathing-<mc>`，第三方照文档依赖精简 API 时 Gradle 直接解析失败（0.1.3 的 POM 没有这一项）。
- 排除 pathing 后，精简 API 能编译大部分示例，但调用 `call.her().serverLevel()` 报"无法访问 Body"。
- 绕法（已写进网站依赖关系页）：依赖完整 API 并 `exclude` 掉 `numen-pathing-<mc>`。实测全部示例编译通过。
- 实测工程在会话临时目录，不长期保留；复现方法：仓外建 ModDevGradle 2.0.141 + NeoForge 21.1.233 工程，只从 numen-maven 拉 `numen-api-neoforge-1.21.1:0.1.4:api`。

**要做**：
1. pathing 归 Numen：引擎不再依赖、不再平铺 pathing；`NumenPlayer` 不再实现 pathing 的接口（身体与寻路之间的端口归 Numen 一侧）。
2. Numen 只用公共 API；用到的内部能力要么补进公共 API，要么承认它属于引擎、搬进引擎。
3. bench：`bench:game`（模组 `numen_bench`）代码只导入引擎包，是"考场"；它的 mods.toml 现在依赖 `numen`，改为依赖 `numen_api`。各插件的评测场景（`src/bench`）自己依赖 bench 与被考的插件，由跑 `runBench` 的项目带上（JUnit 式）。
4. CI 加一项检查：**只用已发布的 maven 坐标**编译一个最小插件，防止 POM 引用未发布模块这类问题再次发生。
5. 把网站插件页的法力插件示例（`mymod`）真正装进游戏，用 Lua 调一次 `mymod.mana.get()`，验证运行期。
6. 网站依赖关系页"0.1.4 的已知问题"警告框在 0.1.5 发布后保留为历史说明或删除，由维护者定。

**相关**：`docs/architecture-mind-model.md`、`docs/bench.md`、网站 `zh/develop/dependencies.md`、`zh/develop/plugins.md`。

### B. 征服水（先做前两层）

**问题**（10-05 真机日志）：她闲着时在水里不会上浮，呼吸本能约 11 秒、每秒约两次地报告，刷屏且挤占上下文。

**分层**（讨论结论）：
1. 闲着时在水里默认上浮；呼吸本能只在真有危险时报告。**0.1.5 做**
2. 疾跑游泳；把呼吸当成规划资源（寻路知道水下能待多久）。**0.1.5 做**
3. 水下干活。
4. 改造地形（填水、排水）交给技能，不做专用工具。

**原则**：身体做的事都要如实报告给模型（知情权），但只报真正的危险，不刷屏。
