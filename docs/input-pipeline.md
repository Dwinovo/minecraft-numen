# 输入管线:从有人跟她说话,到她的手按下去

一条线讲完她怎么接收输入、谁替她想、想完怎么落到身体上、她的东西存在哪。合并了原来的 `mcp-server.md`(外部大脑)与 `companion-input.md`(身体的输入层)。
相关的另两份:收件箱的类型表与循环内核见 `agent-loop.md`,群聊的会话与记录见 `group-chat.md`。

**定位(10-16 用户定):Numen 是住在服务器上的 Agent。** 服务端必装,客户端可选;以后还要出 Paper 端(见 `paper.md`),那里的玩家可以不装客户端,也可以装 Numen 的 Fabric 或 NeoForge 客户端。
所以她的身体、收件箱、循环、记忆、配置都只在服务端;客户端退成可选的前端,装了更好用(面板、语音、动效),不装也能用。

## 一、全景

```
渠道(谁在跟她说话)        大脑(谁替她想)                身体(她做事)
游戏私聊 /msg ─┐
面板、快捷对话 ┤                ┌─ 服务端大脑(主人或服主的 key) ─┐
/numen 命令 ──┼─► 收件箱 ──► 驾驶席 ┤                          ├─► Lua 程序 ─► 任务 ─► 输入层(键盘、视角、鼠标、快捷栏)
QQ、Discord ──┤  (每只一个)        └─ 外部大脑(MCP,自带 key) ┘    (ServerPrograms)
弹幕、定时 ───┤
世界的事 ─────┘
```

三层两管:渠道把话送进收件箱;驾驶席上的大脑从收件箱取件、交出 Lua 程序;身体在服务端跑程序,最后落到她的键盘和鼠标上。
加一个渠道不碰大脑,换一个大脑不碰渠道,谁驱动她都用同一副身体。

**现在。** 第 2 步已落地(§十四):收件箱、循环、她的记忆、模型配置、外部大脑的端点(单人游戏与专用服都在服务端,专用服默认关)都在服务端,
主人一下线她照样想、照样干,话和事都攒在收件箱里,他回来再处理。声线与皮肤库也是服务端的库(第 3 步);语音的出声与听写留在客户端(§八)。下文各节先写当时的现状,再写目标;已落地的在 §十二 与 §十四 标明。

## 二、渠道

| 渠道 | 现状 | 目标 | 她的回话送到哪 |
|---|---|---|---|
| 面板、快捷对话(装了客户端) | 客户端,`NumenGateway.emit` | 经网络包送进服务端收件箱 | 面板、打字机、语音 |
| 语音输入(装了客户端) | 客户端录音、客户端识别 | 不变:客户端录音、用本机的 key 识别,转写文字作为一句话送上来(§八) | 同上 |
| 群聊(多人对她说话) | 已落地,见 `group-chat.md` | 不变 | 同上 |
| 插件桥接(弹幕、群消息) | 客户端,`NumenGateway.emit` | 走远程端点的渠道令牌(§五) | 原渠道 |
| 游戏私聊 `/msg <她>` | 没有 | 服务端接住发给她的私聊 | 她私信回 |
| `/numen` 命令 | 只有管理类命令 | 加"对她说一句" | 命令回显 |
| 世界的事、定时 | 服务端 `NumenEvents.emit`,主人离线进出箱 | 直接进服务端收件箱 | 不需要回话 |

- 每条输入记着**从哪个渠道来、谁说的**。她说的话总在游戏里说出来(气泡、聊天行),另外送回问她的那个渠道:从 QQ 问的,QQ 上收到回答。
- **装了客户端,玩家的交互与现在一样**:面板、快捷对话、按键说话、她的朗读都照旧,变的只是背后在服务端。
- **没装客户端也能用(10-18 用户定)**。她是真玩家,能用原版的就用原版的;不读公屏,公屏上提到或 @ 她都不算跟她说话:
  - **私聊**:原版 `/msg <她> <话>`(自带补全),进她的单聊会话,她私信回。别的玩家 `/msg` 她,按群聊的旁听档(talk,AMBIENT)进收件箱、标着是谁说的,不叫醒她、不花主人的钱。
  - **会话(群)**:就是面板左栏那套(`group-chat.md`),一个会话 = 主人 + 他名下几只同伴的成员表,单聊是只有一只的会话;命令只是面板操作的另一种按法,
    同走 `OwnerInput` 的会话操作,成员表还是那一张(`Conversations`),不另存:
    `/numen group invite <会话> <她>`(拉人,拉进第二只就成了群)、`remove`、`rename`、`dissolve`;
    `/numen chat <会话>` 相当于在左栏点中它——之后聊天栏打的字进这个会话,只有自己看得到、带 `[会话名]`;在里面 `@小柚` 和面板里一样由服务端解析:
    `@` 谁谁醒、不 `@` 全体醒、同伴之间互相旁听,规则一条不改;`/numen chat` 切回公屏;`/numen chat <会话> <话>` 只发一句。
    **`@` 要有补全**:原版 1.19.1 起服务端能给聊天框加自定义补全词(`ClientboundCustomChatCompletionsPacket`,Paper 是 `Player#addCustomChatCompletions`)——
    切进会话时把 `@<成员名>` 设成他的补全词,切回公屏或成员变了就跟着换;`/numen chat <会话> <话>` 的话这一段由命令的补全给出同样的 `@<成员名>`。补全词只有一个来源:会话的成员表。
  - 征询变成带可点按钮的聊天消息([允许] [总是允许] [拒绝],底层是现有的 `/numen consent`);她在干什么显示在动作栏;1.21.6 起可以用原版的服务端对话框;
  - 自己的 key:`/numen key <服务商> <key>`,回执只露前后几位、不广播给其他管理员;1.21.6 起用原版对话框的输入框填,连命令都不经过。
    原版与两个加载器不记录玩家执行的命令,Paper 默认记(说明里提醒服主);
  - 皮肤:`/numen skin add <名字> player <正版名>` 或 `… url <图片网址>`。
  - **召唤只要名字,不设任何前提**(10-18 用户定):人人能召唤,每人上限是服务器设置(默认不限)。档案、人设、皮肤、声线都是召唤后再改的绑定——
    面板编辑卡,或 `/numen companion <她> profile|persona|skin|voice <条目>`(补全列"内置 + 我的")。召唤卡与命令走服务端同一个召唤入口。
    没绑档案时她停在 `BLOCKED`,主人跟她说话时照实回"还没配模型档案"。
  - 面板、语音、本地选图、头顶气泡、思考过程要客户端(原版客户端录不了音、也放不了自定义音频)。
  - **给原版客户端说话的字由服务端翻**:按那位玩家客户端报上来的语言设置翻好再发。
  - **"装没装客户端"只在一处判**:这位玩家有没有注册我们的通道(`Hello`)。我们的网络通道全部改成可选,原版客户端才进得来;
    Numen 没有注册物品、方块、实体,两个加载器上要实测原版客户端能进服。用了本身要客户端的插件(如车万女仆),客户端必装是插件的要求。
- 我们的客户端与服务器之间只走 MC 自己的连接(自定义网络包,`Wire`/`Fragments` 分片:下行单包 1 MiB、上行 32767 字节、一条消息至多 8 MiB),不另开端口。
  群组服(Velocity、BungeeCord)要实测网络包的转发。
- **网络包不许拖慢服务端的刻。** MC 的收发在 Netty 的网络线程上,主线程只是把包排进去;拖慢游戏的是"收到以后在主线程上做了重活"。
  规则:拼装与解码在网络线程,识别、合成、模型请求、磁盘读写、渲染在后台线程,
  主线程只做碰世界与她的状态的那一小步(进收件箱、改一个字段);每位玩家的上行设带宽预算,超了就丢弃,不排进主线程的队。
  下行的大东西(历史分页、朗读音频)按页、按段推,不一次推几 MB。
  现状(第 2 步提交 2、3):上行处理器登记时声明 `Execution.NETWORK` 或 `MAIN`(缺省)。NeoForge 照声明在网络线程上调;
  **Fabric 的网络 API 总是在服务端主线程上调接收器**(核对过 `ServerPlayNetworkAddon.receive`),拿不到连接自己的线程,所以 `NETWORK` 的处理器在那里
  也在主线程上调——处理器必须在两种线程上都对。要在 Fabric 上也把大消息的拼装挪出主线程,得在 `ServerCommonPacketListenerImpl.handleCustomPayload`
  上加一个 mixin,各分支写法不同,等真有大消息要在 Fabric 上传时再做。分片已登记为 `NETWORK`;每位玩家分片字节的预算(`UplinkBudget`,256 KiB/s、桶容量一条最大消息)
  已落地。磁盘写走每个归属一条的串行车道(`Lanes`,`Homes` 给出),停机时排空;崩溃最多丢车道里还没写下去的那几毫秒,没有对任何一种写另开同步路径。

**落地时的出入(第 6 步;`/numen key`、`/numen skin`、召唤与绑定命令随第 3 步后半落地,见 §六末尾;1.21.6 的对话框不在这一步)**:

- **"装没装客户端"有两个问法,各管一件事。** 发包之前问"这位玩家的连接上有没有这种包的频道"(`INetworkChannel.canSend`,NeoForge 查协商出来的频道表,
  Fabric 查对端登记的接收器),没有就不发——频道可选以后这不是错,而 NeoForge 对发往没有该频道的连接的包会在发送处抛异常。
  **界面怎么走**(推 `Feed` 还是发聊天文字、征询画答复框还是发按钮、`/numen settings` 这类作用在客户端上的指令能不能用)只问 `Presence.hasClient` 一处:报到过 `Hello`、协议版本对得上。
  不把两者并成一个,是因为客户端在名册包到达后才报到(`RemoteCompanions.hello`),报到之前服务端仍得把名册推给它,"能不能收包"不能等 `Hello`。
- **原版客户端进得来**:NeoForge 上我们登记的频道全是 `optional()`(Numen API 的,与 Numen 自己的寻路调试包);Fabric 本来不拒。证据:`NeoForgeHandshakeTests` 对着本进程登记的全部频道原样跑
  NeoForge 对非 NeoForge 客户端的配置阶段协商(`NetworkRegistry.initializeOtherConnection`)——它第一次跑是红的,就是被寻路调试包一条非可选的登记拦下。
  没有证到的:真的原版客户端进服(不启动客户端)、Velocity 与 BungeeCord 的转发。Numen 没有注册物品、方块、实体,也没有 `SERVER` 类配置,这条协商是仅有的关口。
- **翻译在发包的出口一处做**(`MixinServerCommonPacketListener`):没装客户端的玩家的系统聊天与动作栏包,按他客户端报上来的语言(`clientInformation().language()`)把原版客户端认不得的键换成字再放行;装了客户端的照旧发带键的消息。
  所以指令回话、她的话、征询、动作栏都不必各管语言。语言表读每个已加载模组 jar 里的 `assets/<模组 id>/lang/<语言>.json`(英文打底,缺的键退回英文),不论模组叫什么;
  只有原版自己的键(`minecraft` 命名空间)原样留着让原版客户端自己翻。别的模组的物品、方块名出现在她的话里,原版客户端同样不认得,一并翻好。
- **`/msg`**:私聊的包到她的"客户端"(`FakeClient`)——聊天类型是 `msg_command_incoming` 的玩家聊天包,带发话人的 uuid,交给 `Whispers`。主人的话经 `OwnerInputs`(和面板输入框同一个入口)进她的单聊会话;别的玩家的话按旁听档进收件箱。
  控制台与命令方块发的私聊是不带发话人的 disguised 包,不接。GameTest 里没法发一条真客户端那样签了名的指令,所以照原版 `MsgCommand` 最后一步的写法直接把包送到她手里。
- **她的回话在哪问就在哪答**用 `Venue`(面板 / 命令切进的会话 / 私聊)记在她的循环上,和"最后被哪个会话叫醒"一样是会话态、不落盘;`Voice` 按它交给 `Link.said`。装了客户端的主人用 `/msg` 或 `/numen chat` 说话时,面板照旧也收到(`Feed` 不变),另有一行聊天。
- **会话命令**:会话参数写名字(单聊就是她的名字)或 id;名字不是纯 ASCII 字母数字时要加引号(Brigadier 的 `string()` 限制,`drive` 同)。办不成的原因是 `OwnerInputs.Applied.problem` 那句英文开发文字,原样说给主人,没有翻译。
  聊天栏的拦截靠各加载器的聊天事件(NeoForge `ServerChatEvent`、Fabric `ALLOW_CHAT_MESSAGE`),都只调 `ChatRoutes.take`;Fabric 一侧编过、没跑。
- **征询的按钮**只有三个([允许]、[以后都允许]、[拒绝]);"说一句再拒绝"没做成按钮,`/numen consent deny <号> <话>` 仍可用。**动作栏**每秒刷一次,只显示正在干着具体活的同伴(`LoopStatus.activity`),闲着或只在想的不显示。
- Fabric 的 GameTest 模拟连接(`FabricMockConnection`)配不出"频道协商好"的样子,Fabric 上取下行载荷的用例会收不到包;本仓只跑 NeoForge 的 GameTest。

## 三、收件箱

现状(第 2 步已落地):每只同伴一个,在服务端她的家里(`companions/<uuid>/inbox.jsonl`),入队即落盘、取走即清;投递方式(叫不叫醒她、随哪一次调模型交出去)写在类型表里,见 `agent-loop.md` §七。
`EventQueue`、`EventTypes`、`JsonlJournal` 本来就在纯 Java 的 `agent` 模块里,原样搬的。

- 入口合成服务端一个:世界上的事经 `NumenEvents.emit` 直接进她的收件箱,客户端的输入(`NumenGateway.emit`)作为 `OwnerInput.Emit` 经网络包送进来,收件箱的去处只有这一个。
- 没有出箱:它存在是因为收件箱在客户端、主人离线时事件没处放;收件箱在服务端,离线只是"攒着"。旧版存档里留下的 `numen_event_outbox.dat` 在服务器第一次起来时一次性读进各同伴的收件箱(`LegacyMigration.outbox`),读完改名 `.migrated`。

## 四、大脑

现状:循环内核 `AgentLoop`(纯 Java,`agent` 模块)跑在主人客户端,用主人的 key 调模型;外部大脑接管时循环停牌(`Hold.EXTERNAL`),
驾驶席只在 `McpMode.driving()` 一处判。

目标(10-16 用户定):**只有两种大脑,同一时刻只有一个坐在驾驶席上。**

| 大脑 | 怎么跑 | key 在哪 | 什么时候用 |
|---|---|---|---|
| 服务端大脑 | 服务端跑 `AgentLoop`,自己调模型 | 主人自己的钥匙串,没有再用服主提供的(受每人每天的限额,§六) | 默认;主人在游戏里时 |
| 外部大脑 | 循环停牌,外部 agent 经远程端点驾驶(§五) | 外部 agent 自己的 | 主人用自己的 Claude Code、Codex 一类 agent 指挥她;想在别人的服务器上用自己的 key,也走这条 |

- **不做客户端大脑,也不做"主人客户端代调"。** 代调要把每一轮的请求反向发给客户端、流式传回,复杂、费网络,同类模组也没人这样做;
  "key 不离开玩家的机器"这件事,外部大脑已经做到了:key 留在玩家自己的 agent 里,服务端只收发事件与程序。客户端大脑在 Paper 端同样不存在。
- **记忆的真源只有一份**:不管谁驾驶,进来的话、她说的话、程序与回执都记进服务端那本日志(§六);大脑自己的上下文是从日志派生的缓存。换大脑时新大脑从日志接着来。
- 打字机、语音、气泡、token 台账照旧订阅循环事件 `LoopEvent`,事件经网络包推给在线、装了客户端的主人。
- **主人在不在,认两样(10-18 用户定)**:他人在游戏里,或者他的外部大脑连着(远程端点上持他令牌的会话)。两样都没有就是不在。
  - **不在了就收拾**(现状不变):`ServerPrograms.ownerLeft` 收掉她的程序,循环 `halt(DISCONNECT)` 后停在 `Hold.AWAY`,收件箱照收。身体留在世界里(`CompanionChunkLoader` 保持 3×3 区块)。
  - **外部大脑连回来就算主人回来了**:`AWAY` 解开,外部大脑坐上驾驶席(驾驶席的规矩不变),服务端不调模型,只把她重新加载回游戏、跑外部大脑交来的程序。
    要问主人的事**问的是人,不是驾驶席上的模型**(它就是要动手的一方,自己点允许等于没有权限层):照 MCP 规范用 elicitation,经外部大脑的客户端弹给坐在电脑前的主人;
    主人在游戏里时照旧在游戏里问。客户端不支持 elicitation 的,只能等主人进游戏答,到期按拒绝(主流客户端的支持情况见 §五 末尾)。
    外部大脑断开、人也不在游戏里,就和主人登出一样再收拾一次。
  - "在不在"只在一处算(`HostPort.ownerPresent` 那一处),身体、征询台、远程端点都问它,不各自判。
- 主人不在时:她的活已经收了,只剩收件箱里攒着的东西,不发征询。
- **渠道(QQ、Discord……,插件桥接)**:主人从渠道说一句话,由服务端大脑去想(用主人的 key),回话回那个渠道;这一轮做完他还不在,就回到收拾好的样子,不因来过一句话一直醒着。
  征询也交给那个渠道:Numen 只给出通用的征询(编号、要做的事、可选的答复)和一个答复入口(与游戏里、`/numen consent` 同走 `ConsentDesk.reply`);
  在 QQ、Discord 上怎么显示、主人怎么点,是渠道插件自己的事(10-18 用户定),Numen 不管。
- 单人游戏是同一进程里的内置服务端,路径一样,不多一跳网络。
- **模型配置在服务端。** 档案、models.dev 目录、三种协议都在纯 Java 的 `ai` 模块里。模型档案是一种库(内置 + 我的,§六),key 不在档案里,在钥匙串里。

## 五、外部大脑

### 现状(第 4、7 步已落地):服务端一个远程端点,所有人共用

外部 AI 客户端(Claude Desktop、Claude Code、Cursor 或任何支持 MCP 的东西)直接驱动她。驱动期间内置大脑停手——同一具身体同一时刻只有一个脑;
主人在游戏里照常和她说话,话进同一条事件线,由外部大脑接走并回话。单人游戏与专用服走同一条路:宿主在服务端(`McpMode`/`McpServer`),
配置、令牌、审计住在服务器的家里(`Homes.server()`:`mcp_server.json`、`mcp_tokens.json`、`mcp_audit.jsonl`)。

- **按令牌认人。** 主人用 `/numen token create <brain|channel> [all|<同伴>] [<天数>]` 发令牌(明文只显示这一次,点一下复制),`list` 看自己的,
  `revoke <编号>` 作废(用它的会话下一刻就断开)。存档只存 SHA-256 哈希,令牌是 256 位随机数;编号取哈希前 8 位。每个请求带 `Authorization: Bearer`,令牌不进查询串。
- **令牌带作用域与身份**:作用域是 `all`(他名下全部,含以后召唤的)或点名的几只;身份是**大脑**(`list_companions`、`create_companion`〔要 `all`〕、
  `delete_companion`、`get_events`、`say`,加上和内置大脑同一批工具)或**渠道**(`list_companions`、`send`、`get_replies`、`answer_consent`)。
  Claude Code 拿大脑令牌,QQ 机器人拿渠道令牌。
- **权限不会因令牌变大**:外部大脑的程序走她自己的工具口,同样过权限层,主体是那只同伴;渠道根本没有跑程序的口。
- **限流**:每张令牌限同时在飞的调用数(长等待的 `get_events` 占一个名额)与每分钟调用数,整个端点再限总并发与总频率;四个数都在 `mcp_server.json` 的 `limits` 里,服主可配。
  超限的工具调用得到一句"限流了,等几秒"(工具错误,模型读得到),接入超限是 HTTP 429。每张令牌至多 8 个会话。
- **协议**:Streamable HTTP(2025-06-18),多会话:`initialize` 开会话、答复带 `Mcp-Session-Id`;`GET` 开服务端→客户端的 SSE 流(征询走它,每 15 秒保活);`DELETE` 结束会话;
  回复都是 `application/json`;校验 `Origin`(带了就必须是同源)与 `MCP-Protocol-Version`;请求体至多 1 MiB;不收 JSON-RPC 批。工具回执后面照旧附这段时间到达的事件。
- **审计**:每次接入、拒绝与工具调用在 `mcp_audit.jsonl`(`store` 的只追加日志)记一条:会话号、令牌编号、工具名、同伴编号、成败、请求与回执的字节数;不记程序源码、事件正文、她的话,也不记令牌。
  没认出令牌的请求按来源地址管:一个地址一分钟里认证失败满 10 次,这一分钟它没通过认证的请求回 429(令牌照常验,验过的照常放行,代理后面共用地址的合法用户不受连累);同一地址一个窗里的失败只记一条(次数、首末时刻),窗收场时写。
  日志写到 4 MiB 就轮转成 `.1`(原有的顺延),只留最近 4 份旧的。令牌库(`mcp_tokens.json`)读不了时那份文件原样不动,这一局端点拒绝所有令牌,`/numen token` 如实回文件与原因,服主修好或挪走后下次起服再读。
- **端口**(只有外部大脑需要,我们的客户端不需要):默认关,服主在 `mcp_server.json`(或单人游戏的设置页)里开。开着且绑在回环之外时,日志和设置页警告端点是明文 HTTP,建议前面放反向代理加 HTTPS;
  文档里同时给隧道的办法(如 Cloudflare Tunnel,不开入站端口)。以后调研"和 MC 共用一个端口,按开头几个字节分流",照顾只给一个端口的托管服,先确认和代理、别的网络类模组共存;中继服务等用的人多了再说。
- **主人在不在**(第 7 步):只在 `OwnerPresence.present` 一处算——人在游戏里,或他的大脑令牌会话连着,或渠道上他的话正由服务端大脑想着。身体(循环的 `HostPort.ownerPresent`)、
  征询台、远程端点都问它。玩家下线时外部大脑还连着不收拾,外部大脑断开、渠道来访做完时再看一次:人不在、别的也没撑着,就收拾一次(`ServerPrograms.ownerLeft`、循环 `halt(DISCONNECT)`,停在 `Hold.AWAY`)。
  "连着"只在 `McpSessions` 一处算:有调用在飞、流开着,或最近 2 分钟出过声。驾驶席按同伴算:她主人名下有连着的大脑会话、其令牌的作用域管着她,外部大脑就坐上驾驶席(`McpMode.driving`)。
- **征询问人,不问模型**:主人不在游戏里、外部大脑驾驶着她时,征询经 `ConsentVenues` 交给游戏之外的场所;外部大脑这一个场所用 elicitation(`elicitation/create`)经客户端开的流弹给人,
  只问声明了 `elicitation` 能力、开着流、令牌管得着她的会话;客户端不支持就不问,征询挂到主人进游戏答(进游戏时补推),到期按拒绝。服务端没有任何让模型自己答征询的工具。
  人选了"允许 / 允许并记住 / 拒绝(可带一句话)"走 `ConsentDesk.reply`;关掉弹窗没选不算答复。
- **渠道**:主人从渠道令牌 `send` 一句话,同走 `OwnerInputs` 的 `Emit` 进收件箱,由服务端大脑用主人的 key 想;这期间("来访",`Visits`)主人算在场,她的回话和通用形式的征询
  (编号、同伴、要做的事、记住会写的规则、可选答复 allow/remember/deny)投进这张令牌的信箱,渠道用 `get_replies` 长等待取走,用 `answer_consent` 交回主人的选择。
  来访在她的内核没有在飞的回合、也没有马上要开的回合时结束(`AgentLoop.settled`),主人若还不在,回到收拾好的样子。在 QQ、Discord 上怎么显示是渠道插件自己的事,Numen 只给这两个口。

### 使用策略(10-16 审出来的)

外部 agent 每调一次工具就是一次完整的模型请求,要重发整份上下文。所以策略的头一条是**少调用**:

- **长等待(已落地)。** `get_events` 没事就一直等,最长 50 秒(给桥接层与客户端的请求超时留余量,Codex 的工具超时默认 60 秒),到点返回"没有新事件",再调一次接着等。
  什么算"有事"读的是内脑开 run 的同一条判据:投递档声明会叫醒她的条目(`EventTypes.Delivery.wakes`)落地就返回,不必是急件;
  捎带的(AMBIENT,以及非急件的 NOTICE)不单独叫醒,等别的事叫醒、到点清扫或程序回执时一起交。外脑没有内脑那套"攒够条数、等够时长"的档位:
  它停在那里本来就是空闲的,第一条会叫醒她的事就该返回。逻辑在纯 Java 的 `ExternalWait`,取件只走 `EventQueue.takeRenderedText` 这一个口。
  `wait_seconds` 保留为可选的上限(0 = 立刻取走队里现有的)。
- **事件跟着回执走(已落地)。** 外脑调 Numen 的工具(`lua` 等)时,回执后面另附一段这段时间到达的事件;取走走同一个口,之后 `get_events` 不再重复给。
- **看得见。** 以后 `look` 返回图片内容(§九,暂缓),支持看图的 agent 直接看。
- **技能与 API 文档不暴露成 MCP 资源或提示词(评估后不做)。** MCP 规范把资源定为"应用驱动"(host 决定怎么用,`2025-06-18/server/resources`):
  Claude Code 里资源是用户用 `@server:uri` 手动引用,另外自动提供列出与读取资源的工具,也就是模型读它仍要一次工具调用,
  和现在调 `skill`、`numen.api.help` 同价;提示词是用户触发的斜杠命令。Codex 的文档只写了工具与服务器说明,没写资源。
  技能还是按同伴的,API 帮助是运行时从注册表出的,做成资源要再维护一份清单与变更通知。收益不大,`skill` 与 `numen.api.help` 仍是唯一来源。
  (Claude Code 会把服务器说明截在 4096 字符,我们的接入说明远小于此,保持简短。)
- 接入说明(`INSTRUCTIONS` 与「复制接入提示词」)已照此改写:想等主人说话或等事情发生时调 `get_events`,干活时事件跟着回执回来。

### 落地时的出入(第 4、7 步)

- **授权是静态 Bearer 令牌,没做 OAuth 授权服务器那一套**(受保护资源元数据、动态注册、授权码)。令牌由主人在游戏里发、客户端手填头(Claude Code 的 `--header`、Codex 的 bearer 环境变量、`mcp-remote` 的 `--header`);
  未带或带错是 `401` 加 `WWW-Authenticate: Bearer`,令牌不进查询串(旧版的 `?token=` 删了)。令牌是不透明的个人令牌,没有受众绑定。
- **旧的单令牌与"失联回退"删了**:配置里的 `token`、设置页的重新生成与"无响应自动断开"、`quiet_fallback` 都没有了(旧文件里的这几项读时忽略)。
  原因:驾驶席现在跟着"有没有连着的大脑会话"走,断开(安静 2 分钟、会话被删、令牌作废)就现算地交还内脑,不需要另一个开关;"开着端点就让她一直安静待命"在多人服上会让所有人的同伴哑掉,不留。
  设置页的令牌那一行改成告诉人去哪发;接入提示词不再内嵌令牌(可以放心发给任何 AI)。
- **elicitation 只走客户端开的 GET 流**,没有把征询塞进正在等的那个 `tools/call` 的 SSE 回复里。TypeScript 与 Python 的官方 SDK 客户端接入后都会开 GET 流;不开流的客户端当作问不了。
  主流客户端:Claude Code 文档写明支持(`code.claude.com/docs/en/mcp` 的「Respond to MCP elicitation requests」,表单模式;有 `Elicitation` 钩子可以让用户自己配置自动答复,那是用户的选择);
  VS Code 的 MCP 文档(`code.visualstudio.com/docs/copilot/customization/mcp-servers`)没有提到 elicitation,Cursor、Codex、Claude Desktop 没有查到明确的说法,按"没声明能力就不问"处理,不替它们猜。
- **建/遣散同伴要主人在游戏里**(召唤与遣散的权威校验认一个 `ServerPlayer`);`create_companion` 还要求令牌作用域是 `all`。
- **渠道的信箱不落盘**,每张令牌最多攒 256 条,满了丢最老的;渠道桥重启后没取走的回话就没了(话本身在她的对话日志里)。
- 长等待的 `get_events` 每次也记一条审计。
- `ConsentDesk.Line.clear` 多了征询号(场所要凭号撤);`ConsentDesk.resendTo` 在客户端报到时把主人不在时挂着的征询补推给他。
- 关服线程的核对见下一条提交的说明:宿主的 HTTP 线程池没随停服收掉、调度线程非守护、stdio 子进程只杀了最外层、等授权的线程要等满期限。

## 六、她的东西存在哪

现状:对话、札记、长期目标、人设、技能、模块真源、模型档案与 key 都在主人客户端 `config/numen/`;服务端只按哈希在内存里缓存她的模块。
落盘的方式已经统一(第 1 步,见下"存储的三层"):各存储只保留自己的记录格式,读写、原子替换、版本迁移都在 `store`。

目标(10-11 定、10-16 用户确认):**她的一切都在服务端,客户端不存任何一份必须的数据。** 大脑可以换,换了以后她还得记得自己干过什么——
夜里服务端大脑做了什么,早上主人上线她要知道;而外部大脑与服务端大脑都只能读服务端。

**每样东西只有一个归属,归属决定它在哪个根目录(10-18 用户定)。** 单人游戏里服务端与客户端共用一个 `config/numen/`,所以服务器、玩家、本机各占一个子目录,根下不放散文件。

| 归属 | 根目录 | 谁能写 | 放什么 |
|---|---|---|---|
| 同伴 | 世界 `<存档>/numen/companions/<她的 uuid>/` | 跟着她;主人经界面改 | 对话日志(外部大脑驾驶的那段也记)、收件箱、札记、长期目标、token 台账、**绑定**(`binding.json`:用哪个人设、模型档案、声线、皮肤,四项都在这里);待办不落盘 |
| 玩家 × 世界 | 世界 `<存档>/numen/players/<玩家 uuid>/` | 本人 | 会话成员表;权限规则在存档的 `SavedData`,不动 |
| 服务器 | `config/numen/server/` | 管理员 | `server.json`(总开关、各种上限、每人同伴数 `maxCompanions`、服主 key 的每人每天 token 限额 `dailyTokenLimit`、权限的两项 `hardRules` 与 `unknownAsOther`;代理是加载器配置里的那一处,与调模型共用;外部大脑端口在 `mcp_server.json`)、**内置**(各库,`<库>/<命名空间>/<名字>`)、服主的钥匙串 `keys/`、外部大脑令牌哈希、`cache/`(models.dev 目录) |
| 玩家 | `config/numen/players/<玩家 uuid>/` | 本人 | **我的**(各库,同一布局)、他的钥匙串 `keys/`、`prefs.json`(主动性档位、各库条目的开关);跟着服务器走,换世界还能用 |
| 本机 | `config/numen/client/` | 这台电脑 | 界面主题、窗口、按键;置顶、文件夹、草稿、已读;语音服务的 key、麦克风、音量(删了不丢她的东西) |
| 外部大脑 | 外部 agent 那边 | — | 它自己的 key 与上下文;上下文从服务端日志派生 |

- **跟着世界走**:备份世界就连她一起备份,删世界她也跟着走;每个世界的她各有各的经历。
  旧的客户端记录(`config/numen/conversations/<uuid>.jsonl` 等)按她的 uuid 在主人首次上线时迁上去。
- **手艺跨服务器只能导出导入**:同一台服务器内跨世界共享;没有客户端的真源以后,带去别的服务器靠导出、导入。
- **存法:文件,不用数据库。** 要存的全是"按同伴一份、按时间顺序读"的东西,没有关联查询,写的只有服务端。不用 SQLite:
  要带各平台的原生库,服主边开服边拷贝世界时库文件可能拷坏,13 条版本分支与 Paper 都要各验一遍;以后真要全文搜索或多服共享,
  优先纯 Java 的嵌入式库,换的只是最底层。存储分三层,用组合拼起来,每层只管一件事(见下)。
- **客户端不留副本**:面板打开时向服务端分页取,之后跟着实时事件长;只在内存里。历史按页拉,别一次推几 MB 挤占那位玩家的连接。
- **群聊照旧"存储按人、视图按会话"**(`group-chat.md` §七),只是那本日志换到服务端。
- 变长靠现有的整理(摘要替换更早的历史),规则不变。
- **日志不写对话内容。** 服主与托管商看得到 `latest.log`,玩家求助时又常把日志整份传到 mclo.gs 一类公开网站;
  INFO 级只记编号与摘要(哪个工具、成没成、多大),对话原文、程序源码、事件正文不进日志。已落地(第 1 步):
  判据是"能还原出她说过、做过、被告知过什么的内容不进 INFO/WARN",留下的是类型、编号、字数、成败。

代价照实说:服主看得到她的对话与札记。这不是"存在哪"带来的:循环在服务端跑,每句话都经过服务端,服主在内存里就看得到;存盘只多了保留。
原版服务端本来就把公共聊天明文写进 `latest.log`,进第三方服务器本来就信任服主。所以做到的是说清楚、可撤回:进服授权卡写明"服主看得到她的对话",
保留时长可设,面板上一键导出、一键清空;给服主一段可以写进服务器隐私说明的文字。单机没有这个问题。
10-11 用户定:只存服务端,不做"只放主人电脑"的选项,也不做下线交接。

### 存储的三层(10-16 用户定:要做就做好)

1. **基础件,新模块 `store`(已落地)**:纯 Java,只依赖 Gson,不认识任何业务;`ai`、`agent`、`numen-api` 都在它上面。只有两种
   (外加两种共用的小件:`Atomic` 先写临时文件再原子替换,一条一个文件的内容文件——札记、人设、模块、播种的配置——只用它;`Io` 由使用方给执行器):
   - **只追加的日志**:首行带版本的头;每条记录有稳定的 `id` 与 `parentId`(照 pi 的会话格式;先不做分支的界面);记录分类型,
     未知类型跳过但留在文件里;坏行跳过;换版本时整份迁移,先写临时文件再原子替换并留备份。对话日志、审计日志用它。
   - **小文档**:JSON,带版本号,读时迁移;写时先写临时文件再原子替换。札记、待办、目标、绑定、玩家的库、令牌哈希、额度台账用它。
   - 磁盘读写交给使用方注入的执行器(`Io`)。现在各处都给"调用线程直接做",后台线程是第 2 步搬家时的事;它只管"怎么可靠地存",不管存的是什么。
2. **记录格式,各管各的**:对话日志有哪些记录类型、怎么推出给模型的上下文与给面板的视图;收件箱条目的样子;札记、待办、库各自的结构。
   每一类只依赖 `store`,彼此不认识。对照 pi 改三处:
   - **压缩是指针,不复制**:压缩记录只写摘要与"从哪条 id 起保留",不再把保留的几条原样抄一份进去(同一条消息不在文件里出现两次);
   - **换模型、换思考档位记成记录**:面板能显示"从这里起换成了某某",模型自己也知道;每条消息仍带出处(llm 0010);
   - **插件的自定义记录**:不进模型上下文,重新加载时插件拿来恢复自己的状态。
3. **按归属组装**:"她的存档"把她的日志、收件箱、札记、待办、目标组合在 `<存档>/numen/companions/<uuid>/` 下;"服务器配置"与"玩家的库"各自组合。
   用的一方拿组合好的那一份,不碰文件路径。

pi 有、这里不要的:文件锁(pi 防的是同一台机器上开好几个 pi;服务端单进程,一份数据只有一个写入方)。

### 库:内置与我的(10-18 用户定)

模型档案、人设、技能、模块、MCP 工具、声线、皮肤都是同一种东西:**一个库,一条条有名字的条目**。只有一套机制,每种库只声明条目长什么样。

- **同一布局**:`<根>/<库>/<命名空间>/<名字>`,像数据包的 `命名空间:路径`。根有三个:各 jar 里的 `numen/`、服务器的 `config/numen/server/`、玩家的 `config/numen/players/<uuid>/`。
  Numen 自带的内容与插件自带的一样放在自己 jar 的 `numen/` 下(Numen 是插件之一,不特殊);现在三种布局(引擎里的 `assets/numen_api/persona/`、Numen 的 `skills/`、`modules/`、
  插件的 `plugins/<id>/…`)统一成这一种,默认人设从引擎挪到 Numen。工具、装备位这类代码照旧走扩展点,这里只管内容。
- **玩家看到两组**:**内置**(服务器目录里的,管理员可读可写)与**我的**(玩家目录里的,本人可读可写)。读取只认这两个目录,按顺序叠,同名时我的优先;
  玩家对内置只读,能在自己的 `prefs.json` 里开关,想改就"复制到我的"再改。管理员改内置用界面、命令或直接改文件,改的是同一个目录。单人游戏里房主就是管理员。
- **jar 只负责把内置放进去**:服务器起来时把各 jar 的 `numen/` 同步进 `config/numen/server/`,同步清单 `config/numen/server/.shipped.json` 记每个文件的来源与指纹(dpkg 对配置文件的办法):
  - 文件没被动过(指纹对得上)→ 换成新版;被改过 → 留他的,新版写在旁边(`<名字>.new`),界面提示"默认内容有更新";
  - 管理员删掉的 → 清单记下,不再放回来;
  - 插件卸载了 → 它没被改过的条目一起删,改过的留下、标"来源已卸载"。
- **MCP 工具**:玩家只能加 HTTP 类的;stdio 类起的是服务器机器上的进程,只有管理员能加(§十)。
- **钥匙串(key 不在条目里)**:档案、声线、MCP 条目只写"用哪个服务商",key 按服务商存在钥匙串里——服务器 `server/keys/`(服主出钱、玩家看不到)、
  玩家 `players/<uuid>/keys/`(只有本人看得到、改得了)、本机 `client/keys/`(语音,§八)。用的时候先找主人的,再找服主的;服主的受 `server.json` 里每人每天的 token 限额
  (默认不限,服主查得到每人的用量),主人自己的不受限。所以内置条目能带"推荐的模型档案、MCP 服务器、声线",填上对应服务商的 key 就能用;jar 里永远没有 key。
- **皮肤**:条目存原图与 Mojang 签名的皮肤数据(value 与 signature),签名在**服务端**做、一次存永久:正版玩家名向 Mojang 查,图片交给 MineSkin 签。
  服务端排队一个一个发,被限流就等,告诉玩家排到第几;服主可在钥匙串里填 MineSkin 的 API key 提高额度;代理用服务器上调模型的同一处(国内服直连会超时)。
  装了客户端的玩家在本机选图、预览,图片经我们的通道传上来;界面写明"图片会交给 MineSkin"。客户端里现在的签名代码(`MineSkinClient`、`MojangSkinLookup`)挪到两边共用的地方,只剩服务端一处调用。

**谁看得见她的话**:只给主人——面板里的会话回在面板,命令切进的会话回在带 `[会话名]` 的聊天行,`/msg` 回私信(§二);装了客户端的主人另有头顶气泡、聊天栏打字机与朗读,只给他(`SpeechBubbles`)。

**旧数据(10-18 用户定,beta 期)**:单人游戏把本机的皮肤库、声线、`looks.json`、各库迁进新布局(复制不移动,同 `LegacyMigration`);多人服不迁,也不上传本机的任何东西。

**落地时的出入(第 3 步前半:存储归属、库机制、钥匙串)**
- **库的类**:一套机制在 `library` 包——`LibraryKind` 声明条目长什么样(一个文件,或一个带标记文件的目录)、`Shelf` 是一个根下一种库的内存表(写先改表再交车道落盘)、
  `Library` 是玩家看到的内置加我的(同名我的优先、开关、复制到我的)、`Shipped` 是 jar 内置的同步(登记、清单、`.new`)、`LibraryHub` 是一台服务器上所有库的出处
  (评测与单测用 `LibraryHub.headless` 在一个目录上开同样的一份)。条目的名字是 `命名空间:名字`,玩家自己建的放 `my`,管理员往内置里加的放 `server`;
  同伴的绑定记的就是这个名字(人设 `numen:小焰`、档案 `my:我的 DeepSeek`),所以旧绑定迁移时改写。
- **手改磁盘上的文件要 `/reload` 才读到**:库在内存里(读不碰盘,可以在脚本线程上读),`/reload` 重扫各库、钥匙串和 `server.json`;模块不再每次读盘。
- **同步按文件算**:清单 `.shipped.json` 是文件级的,目录型条目(技能)里每个文件各按各的;"默认内容有更新"就是有 `.new` 文件。管理员处理新版用库协议的
  `accept`(换成新版)与 `dismiss`(保留自己的、这一版不再提示)。管理员删掉的内置不再放回。管理员改过的内置条目,右键菜单有"恢复默认"(库协议 `restore`):丢掉改动、取回 jar 里这一版,清单记成这一版是它的底。
- **管理员往内置里新建**:协议(`put` 带 `group: "builtin"`)与界面都有——管理员在列表页的"新建"旁边多一个"新建内置"。
- **MCP 工具按玩家有两处连接**:服务器的一处(内置组,管理员配,工具人人可见)和每位玩家自己的一处(我的组,工具只有他的同伴看得到),同伴看得到哪些工具
  只问 `ToolBook`。条目里的 `enabled` 是条目主人的"连不连"(协议 `connect`/`disconnect`),玩家对别人的内置条目的开关只管他的同伴看不看得到那台的工具。
  stdio 条目只有管理员能加,也不能把内置的 stdio 复制到自己名下。`McpClientManager` 不再是静态单例,配置的真源是库里的文件。
- **key**:按厂家存,档案与 MCP 条目只写厂家/服务名(MCP 条目的 `service`,作为 Bearer 带上);同一个厂家(含自定义厂家)只有一把;迁移旧档案时同一厂家几把不同的
  key 留第一把。服主 key 的限额在 `server.json` 的 `dailyTokenLimit`(缺省 0 = 不限),用量按天记在 `server/usage.json`,`/numen usage` 给管理员查;
  超了停在 BLOCKED,原因 `endpoint.quota`。多人服玩家第一次存自己的 key,答复里带一行 `notice`,客户端弹一条提醒。型号目录与连通性检测对所有玩家开放
  (人人有自己的档案要填)。
- **本机文件**按 `Homes.clientDir()` 住进 `config/numen/client/`(`ClientFiles` 复制旧位置的):界面偏好、语音总开关、语音合成与识别的 key;
  `ConfigRootMigration`(早年的 `config/numen_api/`)照旧。
- **旧数据迁移(单人)**:`LegacyLibraries`——旧档案进内置组、key 进服主的钥匙串,人设/技能/改过的模块进房主的"我的"(和内置一模一样的不搬,旧绑定改指内置),
  旧的"删掉的出厂模块"与技能全局开关换成房主的开关,`mcp_clients.json` 进内置组,同伴绑定里的旧名字改写;和 `LegacyMigration` 一样复制不移动、先暂存再改名。

**落地时的出入(第 3 步后半:声线与皮肤成为库、绑定、签名、召唤、命令、导出与清空)**
- **声线与皮肤各是一种库**(`VoiceProfile.KIND`、`SkinProfile.KIND`,一条一个 `.json`),走"内置 + 我的"的同一套库协议与设置页。声线条目是后端、音色、参数,
  外加 `service`(用钥匙串里哪个服务的 key,缺省是后端的标识);**不含 key**。key 在本机钥匙串 `config/numen/client/keys/`(`ClientKeys`),按声线的服务名存;
  语音识别的 key 同在这里,按识别服务商存(`stt-<服务商>`),原先放在加载器配置文件里的 `sttApiKey` 删了(旧值不迁,填一次)。客户端朗读时读她绑定的那条声线
  (状态 `CompanionState.voiceId`,表来自库协议)加本机的 key 合成(`SpokenVoice`)。语音总开关是这台电脑的偏好(`ClientPrefs`),不跟着她走。
- **皮肤签名只在服务端一处**:`SkinSigning` 一条队、一个工作线程一个一个发。图片三种来源——玩家上传的图(界面选图、分片上来)、服务端按网址取的图
  (只收公网 http(s)、不跟重定向、至多 256 KiB、必须是 64×64 或 64×32 的 png)、借正版玩家的(向 Mojang 查,本来就是签好的,不经 MineSkin)。被 MineSkin 限流就按
  `Retry-After`(没说就 30 秒)等了再发同一张,一张总共等不过 10 分钟;每人最多同时 5 张在排。条目签好才写进货架(原图 + 手臂模型 + value/signature),之后召唤和换肤不再联网。
  队里的状态(排第几、在签、在等限流、失败的原因)作为皮肤表里 `pending` 的几行交给当事人;`cancel` 撤掉排着的或不再显示失败的。MineSkin 的 API key 是服务器钥匙串里的 `mineskin`,
  管理员在皮肤表单里填;代理用的是调模型的同一处(`INumenConfig.getProxy()`,现状就是服务器一个代理),**没有另放一份在 `server.json`**,免得一件事两个真源。
  `MineSkinClient`、`MojangSkinLookup` 挪到主源码集(`skin` 包),客户端不再有任何签名代码。
- **绑定四项在她的存档**(`binding.json`:`provider`、`persona`、`voice`、`skin`,值是 `命名空间:名字`)。改绑只有一个入口 `CompanionBinding`:条目要在主人看得到、没关掉的库里;
  皮肤另外穿到身上(`Companions.applySkin`,原地重建身体)。面板编辑卡发 `OwnerInput.Bind`,命令 `/numen companion <她> profile|persona|voice|skin [<条目>]` 同走它(不写条目是不绑,档案不能不绑);
  库里的条目改了名,绑着它的同伴跟着改指(`CompanionLoops.rebind`);皮肤重签换了数据,穿着它的同伴穿上新的。
- **召唤只有一个入口** `Companions.summonFor`:召唤卡、`/numen player summon`、外部大脑的 `create_companion` 都走它。名字合 MC 规则、不撞在线的别人、每人上限(`server.json` 的 `maxCompanions`,0 = 不限)。
  召唤卡只剩名字和模式。没绑档案的她停在 `BLOCKED`,原因 `endpoint.unbound`(现有的),主人跟她说话时界面照实说"还没配模型档案"。
- **`/numen key <服务商> <key>`** 存进他自己的钥匙串(面板钥匙串页同走 `Libraries.saveOwnKey`),回执只露前三位和末两位(短的一位不露),不广播,多人服第一次保存提醒一次。
  **`/numen skin add <名字> player <正版名>` / `url <网址>`** 进他的皮肤库,排上队说排第几,被限流说一声,签好或没成回一句。
- **面板导出与清空**:资料页"记忆"一节写明"她的记忆存在这个服务器上,服主看得到",有"导出"和"清空"。导出先在主人客户端弹系统保存对话框(取消就什么也不要),选定了才向服务端要:服务端在她的写车道上把 `chat.jsonl` 与 `memory/` 打成 zip,按 64 KiB 一段依次下行,每位玩家每个服务器刻至多一段(`Exports`,这就是下行预算),客户端按序收齐再写盘,总大小不设上限;玩家下线、段序不对就作废;
  清空要主人确认,删掉日志、札记、长期目标,名册与身体不动,往她的收件箱放一条如实说明的 `server_message`,面板收到 `Feed.Wiped` 作废她的记录。她正在想事情、死着、外接大脑驾驶着时不清。只有主人能做。
- **旧数据**(单人游戏,`LegacyLooks`):`client/voice.json` → 房主的"我的"声线(key 进本机钥匙串,同一个服务几把留第一把);`client/skin.json` 加 `skins/*.png` → "我的"皮肤(没签成的留着,编辑保存即用存着的原图重签);
  `client/looks.json`(更早是旧家的 `binding.json`)里每只同伴的选择改写成新名字写进她的绑定,只在她的家刚搬过来的那一次做。复制不移动、只做一次。多人服不迁、不上传。
- **库协议**多了 `voice`、`skin` 两种,`restore` 与 `cancel` 两个操作;`LibraryRequest`/`Library` 两个包可分片(皮肤带原图);皮肤条目内容一变(签好、采用新版、恢复默认),所有绑着它的在场同伴(内置的不论谁名下)都按 `applySkin` 换上。库列表页在服务端推来"没办成"的原因时亮一条错误。
- `PROTOCOL` 加到 2:`OwnerInput` 的 `Bind`/`Export`/`Wipe` 替掉了 `SetProvider`/`SetPersona`,`CompanionState` 多了声线与皮肤,召唤请求只剩名字和模式,`ChangeSkinPayload` 删了。

## 七、身体的输入层(已落地)

她是没有客户端的服务端玩家。真人手里的键盘、视角、鼠标、快捷栏,她都有,而且**只此一份、谁驱动她都用同一份**——寻路、Numen 的工具、
第三方插件、外接大脑的程序,最后都按这几样让她动。参照:Mineflayer 本体的 `setControlState`/`lookAt`/`dig`/`activateItem`、Carpet 的
`EntityPlayerActionPack`、Baritone 的 `InputOverrideHandler`——都是一层统一的"玩家输入",粒度就是真人能按的东西,寻路建在它上面。

全在 Numen API 的公开包 `com.dwinovo.numen.api.entity`,进瘦 jar:

```java
NumenPlayer her;
her.controls()  // 键盘:前后左右、跳、潜行、疾跑
her.look()      // 视角:at(点)、turn(朝向)、faceToward(x, z);看向一格方块上她看得见的那一点或那一面
her.mouse()     // 鼠标:pick/on/itemRay 准星;dig/attack/release 左键;use/useItem/stopUse 右键;intents() 此刻要问许可的意图
her.hotbar()    // 快捷栏:hold(格)、grip(东西),每次换了都交回 BodyAction
```

- **粒度就是真人的输入。** "挖掉那一格""放一块到那里"这类组合不进这一层,是使用者用这四件拼出来的。四件都是"一具服务端玩家 + 状态"的小类,
  普通假玩家也能 `new` 来用(寻路的 `TestBody`)。
- **鼠标只对准星起作用。** 先 `look()` 转过去再按;`mouse()` 自己做准星拾取,"手点到了哪一格"只有一个出处。要的是某一格时先问 `on(pos)`。
- **每一下如实交回结果。** 左键交回 `Strike`(还在挖 / 挖掉了什么 / 被拒及理由 / 准星没落在方块上);右键交回 `Use`(缓手没按 / 按了:落着什么、
  世界变了哪几格、打开了什么界面 / 被拒)。点格子、点空气、点实体是同一个右键、同一种结果,`numen.use.*` 都从它写回执。右键按住(拉弓、吃喝、举盾)
  与左键按住挖一样归鼠标管,两次按下的间隔是鼠标的事。
- **权限长在鼠标上。** 左键换到新的一格时问能不能拆;右键会往世界里放东西时问能不能放,否则问能不能用。要问主人时鼠标停下、交回 `Refusal.Asks`,
  由驱动者决定怎么问(寻路是走到那一格停下问);不许是 `Refusal.Denied`;服务端把挖掘退回来是 `Refusal.Server`(身体汇报,不是裁决)。
  判据只认身体是谁:是同伴就过权限层,普通假玩家照原版;别人自己 `new` 一个同伴的鼠标也绕不过去。
- **原版公式只有一个出处。** `DigTime`(挖掘进度与冷却,从 `DigTime.Mining` 算,不碰真身体也能算)、`Reach`、`Sight`、`Faces`、`Replaceable`
  身体与寻路规划共用;挑工具归 `ToolChoice.take`。纯规划的几何(`Footing`、`Stepping`、`Clearance`)与规划用的身体快照留在 pathing。
- **换驱动者时统一松手。** `CompanionBrain` 每刻只选一个驱动者(反射 > 同步 > 当前任务 > 空闲姿态),换人那一刻调完旧驱动者的 `stop` 就把键全松、
  挖掘进度清零、右键松开,新驱动者从干净的身体开始;任务与反射不各自松键。
- **寻路怎么接。** 身体端口 `Body` 留在 pathing,交出那具玩家与这四件,寻路直接用;`Ports` 里只剩寻路自己的策略。

## 八、语音

原版客户端录不了音、也放不了自定义音频,麦克风与喇叭都在玩家的电脑上,所以语音要客户端。10-18 用户定(方案 B):**她的声线跟着她在服务端,出声与听写在客户端。**

- **声线定义在服务端**:声线是一种库(§六,服务商、音色、参数,不含 key),她用哪条记在她的绑定里。换电脑、换客户端都还在。
- **语音输入(不变)**:客户端录音,用本机钥匙串里识别服务的 key 边说边转成文字,填进输入框,发出去就是一条普通的话。服务端看不到音频。
- **朗读(不变,只是声线改从服务端读)**:服务端把她回复的文字片段(`Feed.Delta`)推给主人的客户端;客户端分句(首句到第一个逗号就切)、
  用本机钥匙串里那家语音服务的 key 合成(预取两句)、从她身体的位置放出来;主人开口打断就硬停,她自己接着说就句界衔接。客户端报"在放音",身体据此看着主人。
- **语音服务的 key 在本机**(`config/numen/client/keys/`),各家语音服务的实现(豆包、阿里云、MiniMax、Fish Audio、GPT-SoVITS、OpenAI 兼容……)留在客户端。
- **只有主人听得到**(10-18 用户定:附近的人暂时听不到)。以后要让附近的人也听到,办法是主人的客户端合成后把音频传上服务端、转发给附近装了客户端的人
  (Simple Voice Chat 的做法,压缩后约每秒 3 KB),主人出钱、大家听到同一个声音。
- **以后可选的联动**:Simple Voice Chat 的服务端 API 能收玩家麦克风的包、能建以实体为声源的音频频道。给装了它、没装我们客户端的玩家一条语音路,
  她的声音也能从她身上发出来;它的 Paper 插件同样要玩家装它的客户端。做成 `plugins/` 下的联动,拿真模组验过再接。

## 九、多模态:谁来画她看到的东西

服务端大脑与 Paper 服上没有渲染器,专用服务器连方块贴图都没有。主流做法:

- Mindcraft:bot 进程里跑无头 3D 渲染(prismarine-viewer,three.js + WebGL 画布),从 bot 眼睛的位置画 800×512 的 JPEG,
  先交给视觉模型读成文字,再把文字交给主模型。
- BlueMap(服务端 3D 地图):服务端用 Java 从世界数据渲染;贴图在服主打开 `accept-download`(确认接受 Mojang 的 EULA、拥有正版)后
  从 Mojang 下载客户端 jar 取,不再分发;模组方块的贴图从模组 jar 里取。

试过服务端照 BlueMap 的取资源办法从她眼睛处画一帧(两轮原型):方块是数据,通用;实体与方块实体是客户端代码,只能逐个照抄,模组实体无穷多,维护不起。

定了(10-16,body 0004,暂缓):**画面交给装了我们客户端的主人那边画**,服务端请求、主人客户端把相机临时放到她眼睛处画到屏幕外的画布上、经上行分片传回;
**服务端只出"看见了什么"的清单**(视线锥内没被挡住的实体:类型、名字、距离、位置),主人不在场也能用。
主人不在线、没装客户端、或她不在主人已加载的范围里,就只有清单。排在输入管线之后。

## 十、安全:第三方服务器上谁防谁

服务端必装以后,她多半活在别人的服务器上。三方各有要防的,分开说:

**1. 玩家防服务器。** 服务器上的一切(背包、房子、公共聊天)本来就在服主手里,她的记忆跟着身体住在那里,这一层只能靠信任,做到的是说清楚、可撤回:

- **按服务器授权,像浏览器按网站给权限。** 第一次带她进一个多人服时,客户端弹一张卡说清这个服务器要什么:存她的记忆(服主看得到)。单机不弹。
- **玩家可以把自己的 key 交给服务器(10-18 用户定:进服就是信任服务器)。** 存在他的钥匙串(`players/<uuid>/keys/`),只有他自己在界面里看得到、改得了;
  服主在磁盘上看得到。多人服第一次保存时提醒一次:"服主看得到这把 key,请用设了花费上限的那一个。"不信任服主的,走外部大脑,key 留在自己的 agent 里。
- **key 碰不到的地方。** 不进日志、不进命令回执、不进模型上下文(提示注入问不出来);Lua 沙箱没有文件与系统访问,谁的 key 玩家的程序都读不到。
- **日志不写对话内容**(§六)。
- **看得见、删得掉。** 面板上写明"她的记忆存在这个服务器上",一键导出、一键清空。

**2. 服务器防玩家。** 玩家提交的 Lua 在服务端跑,没装客户端的玩家也能提交:

- 沙箱上限(指令数、字符串、时长)、每个主人同时几段、主线程每刻预算,都由服主可配(10-05 已有,改成可配)。
- 服主提供的 key 按玩家限额(每人每天的 token,`server.json`,默认不限);远程端点按令牌限并发与频率,服主可配总量。
- 远程端点默认关;令牌高强度随机、只存哈希、可设过期、随时作废、带作用域;开了明文 HTTP 时界面与日志警告,建议反向代理加 HTTPS;每次接入与调用记审计日志。
- 服主的总开关:能不能用 Numen、能不能用服务端大脑、能不能开远程端点、能不能夺舍,各自一个。
- 接进来的 MCP 服务器只有管理员能配(见 §十四 提交 9b):stdio 类型起的是服务器机器上的进程,地址、令牌、命令行对别人不可见。

**3. 玩家防玩家。** 不让她成为搞破坏的工具:

- **她的命令权限就是主人的(10-18 用户定)**:主人是几级她就是几级,主人离线也照他的等级算(`getProfilePermissions` 认档案,不要求在线)。
  现在 `McApi` 用的是她自己的等级,服主给她开了 op,普通玩家就能借她跑 op 命令;改成只看主人,她自己在不在 op 名单里不再起作用。
- 权限层的硬规则:别人的东西拆不得、拿不得、打不得,主人点"允许"也解不开(`permission-layer.md` §六)。
- **专用服务器上"说不清是谁的"按别人的算**(硬拒),服主可改;单机与局域网照旧问主人。否则别人装模组前盖的房子,
  一个想搞破坏的主人点一下"允许"就拆了。
- 提示注入:只有主人与群聊成员的话算命令,别人 `/msg` 她的话、QQ 与弹幕渠道进来的话都标着来源;模型就算被说动,
  动手也过权限层,越不过主人本身的权限,更越不过硬规则。

## 十一、以后:夺舍

主人下线时,用和主人同一个身份的假玩家顶替主人的身体干活(像 Carpet 的 `/player shadow`)。在这条管线里只是"换一个身体来源",渠道、收件箱、大脑都不变。
要单独定:上线时的交接(防复制物品)、主人明确授权与范围、死亡与危险保护、服主开关、回来时完整交代做了什么。不在本方案里做。

#### 14.1.2 玩家的库:不产生两个真源的办法

- **人设库**:循环每轮要读,所以必须在服务器。按主人存成玩家库,界面通过 14.3 的库协议编辑,客户端只在打开页面时拉列表、编辑时发改动,**不存文件**。单人游戏里"服务器 `config/numen`"就是原来那个目录,文件几乎不用搬(旧的全局人设库在单人游戏归给房主,见 14.6)。
- **声线库**:循环不读,里面是语音服务的 key,按 §八 随第 5 步搬到服务器的玩家库。第 2 步里它和 `binding` 里的声线 id 一起留在客户端(一个客户端偏好文件,按同伴 uuid 记"她用哪条声线"),因为朗读此刻还在客户端。这不是第二个真源:服务端没有对应的东西。
- **皮肤库**:循环不读;条目是 MineSkin 代签好的公开签名数据,客户端用本机代理去换,服务端只在召唤、换肤时收到 (value, signature)。**建议不搬**,当作玩家本机的皮肤收藏(像资源包),`binding.skinId` 删掉:编辑卡标"当前皮肤"改为拿身体当前的皮肤签名去和库里条目比(身体是唯一真源)。可行性待核:客户端能不能读到她的皮肤属性。这条是**待定**(见 14.9)。
- 否决的另外两个办法:① 同伴存档里存一份人设正文副本——改人设时对不上,正是现有代码注释明确拒绝的"第二真源";② 绑定时把人设拷给同伴(拷贝语义)——"编辑人设立即对所有同伴生效"的现有行为会丢。

### 14.2 客户端剩下什么、怎么变成纯前端

原则:**客户端不存真源、不留副本**;内存里的只是"订阅来的视图",关面板即弃。所有视图读自 `RemoteCompanion`(显示行、在飞的打字机与思考、状态、用量、目标、会话),数据来自服务端。

| 客户端功能 | 订阅服务端的什么 | 往服务端发什么 |
|---|---|---|
| 聊天面板(显示行) | 实时 `LineAppended(id, 行)`;打开时 `HistoryPage` 分页取(14.3) | `HistoryRequest(前于某 id, 条数)` |
| 打字机、思考块 | `Turn` 事件里的 `delta`(服务端按刻合并);重进时 `Snapshot` 带上已到的半截 | 无 |
| 头顶气泡、聊天栏的话、系统提示条 | `Said(text, 会话)`(她说出口的唯一出处在服务端,见下)、`Failed`、`Blocked` | 无 |
| 快捷对话、面板输入、斜杠命令 | `Status`(含"此刻能不能整理/清空"及理由的键,判据只在服务端) | `OwnerInput`(说话、命令回显、停止、整理、清空、设目标、收工),命令里技能正文由服务端展开,路由沿用 `Conversations.say` |
| 语音朗读(第 5 步前仍在客户端) | `Turn` 的 `start(ownerSpoke)`、`delta`、`end`,以及 `Halted` | `Speaking(是否在放音)`:`SpeakingStatePayload` 缩成只报放音这一位,"在想"服务端自己知道 |
| 语音输入 | 无 | 识别仍在客户端,转写文字走 `OwnerInput`(第 5 步再改成送音频) |
| token 台账显示、`/usage` | `Usage` 随状态推送 | 无 |
| 模型配置页 | 档案列表(普通玩家看不到 key 与地址,见 14.4) | 库协议 `LibraryPut/Delete`(仅管理员) |
| 人设页 | 库协议列表 | 库协议 |
| 群聊视图(左栏、成员、@ 补全) | `ConversationList`(成员表真源) | `ConversationOp`(拉人、移出、改名、解散、说话、停止) |
| 目标栏、计划清单 | `Status` 里的目标;清单从日志行推 | 目标走 `OwnerInput` |
| 征询卡 | 现有 `ConsentRequest` | 现有 `ConsentReply` |
| 同伴名册、背包页、位置 | 现有 `CompanionList`、`NumenState`、`NumenLocations` | 现有请求 |
| 技能命令补全 | `SkillList`(服务端技能目录) | 命令回显交服务端展开 |
| 主题、窗口、按键、置顶/文件夹/草稿/已读、声线偏好、皮肤收藏 | 无 | 无(纯本地展示偏好,删了不丢她的东西) |

- **"她说出口"在服务端只有一处**:循环收到最终回复(含外部大脑的 `say`)那一刻,服务端 `Voice.said(...)` 做四件事——同会话的其他成员旁听(现 `Conversations.heard`)、发 `Said` 给装了客户端的主人、没装客户端的主人收到只发给主人的系统消息、按渠道回给来源渠道。现在 `TurnPresenter.spoke` 在客户端做,会拆到这里;客户端只留"画"(气泡、打字机、语音接线)。
- **删掉的客户端类**:`EntityAgentLoop`、`AgentLoopRegistry`、`ToolDispatcher`(兜底超时的判据搬到服务端工具口)、`TokenLedger`、`CompanionHome`、`Conversations` 的成员半边、`McpTranscript`(外部大脑的话也进服务端日志,面板读日志,不再有"现场缓冲")、`ClientNumenState` 里循环用的那部分、`ClientPrefs.initiative`、客户端 `ProviderLibrary`/`PersonaLibrary`/`JsonLibrary`(服务端版进主源码集,客户端是 `RemoteLibrary` 视图)、`McpMode`/`McpServer`/`McpClient*`/`McpOAuth`(见 14.5)。
- **服务端语言**:循环里只有一处面向主人的本地化文字——整理、清空两种控制条目的回显(现在 `I18n.get` 在入队时写死当前语言)。改成条目存语言无关的键,客户端渲染时翻译。其余(`CauseWords`、`ToolWords`、`ChatDisplayModes`)本来就是画的一侧。

### 14.3 网络协议

**新增(下行 S→C)**:
1. `HelloAck(协议版本, 是否管理员)`;客户端据此决定订阅与显示哪些页。
2. `Feed(companion, seq, 事件…)`:一刻一包,把循环事件译成展示用的少数几种(`Turn{start,delta,end}`、`Said`、`Failed`、`Blocked`、`Halted`、`LineAppended`、`PendingChanged(id…)`),译的地方只有一处(`FeedEncoder`),**不直接编码 `LoopEvent`**——`LoopEvent` 带整份 `AssistantTurn` 与工具参数,面板要的行从日志来;行的正文用日志自己的 JSON,不另写一套 `StreamCodec`。
3. `Status(companion, LoopStatus、能否整理/清空的理由键、目标、用量)`:变了才发,按刻合并。
4. `Snapshot(companion)`:客户端进服或重连时一次,含状态与在飞的半截;服务端那份"在飞缓冲"是真源。
5. `HistoryPage(请求号, 行[含 id], 下一页游标)`:按字节预算(约 256 KB)切页,单页过大走 `Fragmentable`。
6. `ConversationList`、`LibraryEntries(kind, …)`、`LibraryChanged(kind, id)`、`SkillList`。
7. `Rejected(请求号, 原因键)`:预算超了或权限不够时让客户端退避。

**新增(上行 C→S)**:`Hello(协议版本)`、`OwnerInput(companion, sealed 输入)`、`HistoryRequest`、`ConversationOp`、`LibraryList/Put/Delete(kind, …)`、`SkillListRequest`、迁移用的 `MigrationOffer/Chunk`(14.6)。

**删除**:`RunProgramPayload`、`ProgramResultPayload`、`StopProgramPayload`、`CancelTasksPayload`(循环与程序同在服务端,不过网络)、`NumenEventPayload`、`NumenDeathPayload`、`NumenRespawnPayload`(服务端直接调循环)、`CurrentTaskPayload`、`ClientUiActionPayload.RESET_LOOPS`(变成服务端调试命令)。`NumenStatePayload`/`RequestStatePayload` 留着(背包页用)。**留着**:`ClientCallPayload`/`ClientCallResultPayload`(反向请求,供只有客户端知道的函数:FTB 任务书、TLM 皮肤列表),但**模块那条线整个撤**:`ModuleSync`、`ModuleCache`、`RunModules`、`RunResult.Missing`、`ProgramUplink`、`ClientEndpoint`、`LoopbackClient/Transport`(评测改直接调 `ServerPrograms`)。`ModuleApi` 现在是客户端函数(模块在客户端),模块搬服务端后变成普通服务端函数,少一条反向请求。

**历史按 id 分页**:
- `ConvoLog.Line` 加 `id`(就是 `AppendLog` 的记录 id);**`EventQueue.Entry` 加稳定 `id`**(入箱时由日志记录 id 给),主人的话变成日志里的 `user` 行时记下 `from=<条目 id>`,客户端据此把"待发"气泡和落盘行对上、不画两份。
- 群会话的归并(现在客户端取 N 本日志合并去重)**搬到服务端写成一个函数**(`group-chat.md` §七本来就要求面板与 MCP 同一个出口),游标由服务端给、是不透明串,客户端不解析。
- store 要补一件:`AppendLog` 按 id 向前读 N 条(惰性建 id 到偏移的索引,后台一次顺扫),不能每次整份读。

**线程**(落实 §二末尾的规则):
- 现状已核:Fabric 的上行处理器一律 `server.execute` 回主线程(`FabricNetworkChannel`),NeoForge 默认在主线程;`NumenNetwork.fragmentFromClient` 的拼装与 `Fragments.decode` 因此在主线程。
- 改法:`INetworkChannel.registerClientToServer` 增加执行位 `NETWORK | MAIN`。`FragmentPayload` 登记为 `NETWORK`(拼装和解码在网络线程,每连接一个 `Inbox`,同一连接的包本来就串行);拼回的包按自己登记的执行位分发:`OwnerInput`、`HistoryRequest` 这类**只做校验后投进每位玩家一个有界信箱**(`NETWORK`),主线程每刻最多取 N 条处理(进收件箱、改字段);读历史、读库、迁移落盘走后台执行器,结果直接 `sendToPlayer`(原版 `Connection.send` 线程安全,**两个加载器上待实测**);碰世界的(召唤、换肤等现有包)仍是 `MAIN`。
- 上行带宽预算:每位玩家一个令牌桶,按字节记,超了丢弃并回 `Rejected`,不排进主线程的队。
- 下行:历史、库列表按页推;`Feed` 的 `delta` 按刻合并,一刻一包。
- 磁盘:`ConvoLog`、收件箱、各 `JsonDoc` 的写交给 store 已有的 `Io` 执行器,**每只同伴一条串行车道**(保序),服务器停机时等车道排空(挂 `ServerLifecycle`)。现在各处都是调用线程直接写。

### 14.4 谁能改服务端的配置

- 判据**只在一处**:`Authority.isAdmin(ServerPlayer)` = 单人游戏的房主(`server.isSingleplayerOwner`)或 op。库协议里每种 `kind` 声明自己的访问级别(`OWN`:只能改自己名下;`ADMIN`:仅管理员),分发层统一查,工具和界面里不再另写。
- `kind`:`persona`(OWN)、`provider`(ADMIN 改;其他人只读**脱敏视图**:id、名字、型号,没有 key、地址、代理)、`mcp-client`、`mcp-server`、`server-config`(代理、默认人设;ADMIN)、`prefs`(OWN)、`permission`(OWN:主人的规则与同伴的模式,管理员也只摸得到自己那份)。脱敏发生在服务端编码那一处,客户端拿不到就不存在泄露。
- 普通玩家给同伴绑档案,只能从脱敏视图里选;选择也过 `OwnerInput`,服务端校验这个档案存在。
- 待定:op 取几级(建议 4,key 会花服主的钱;但不少服只给 2-3 级)。

### 14.5 外部大脑(MCP)

同意倾向:**这一步把宿主原样搬服务端,令牌、作用域、限流、多会话留第 4 步**。核实:`McpServer` 对循环的全部接触已经收在 `NumenActuator` 一个门里(`companions/create/delete/awaitUrgent/takeEvents/say/invoke`),所以搬迁的实质是:`McpServer`/`McpMode`/`McpConfig`/`McpAccessPrompt` 进主源码集,`NumenActuator` 换成直接操作进程内循环的服务端实现,`McpMode.driving()` 仍是驾驶席唯一的判据(循环 `Hold.EXTERNAL`)。单人游戏同一进程,本机端口和现在一样。设置页"外部大脑"变成管理员页(走库协议 `mcp-server`)。
- 外部大脑驾驶的那段进服务端日志,`McpTranscript` 现场缓冲删。
- **接进来的 MCP 工具**(`McpClientManager`,循环读工具表要用)也在这一步搬,否则工具表读不到。**风险**:`McpOAuth` 要弹浏览器;单人游戏同机可用,专用服没有界面。这一步只保证单人游戏与带令牌的服务器,专用服的 OAuth 另给 `/numen mcp auth <名>` 打印链接(待定,见 14.9)。
- **排序**:搬宿主排在构建期最后一个提交,等你把另一个执行者对 MCP 使用策略的提交并进我的基底再做,避免撞同一批文件。为了不在切换之前就让外部大脑断掉,宿主以 `Actuator` 端口的两个实现并存到清理提交(旧:客户端实现;新:服务端实现),翻转提交里一起翻。

### 14.6 迁移

要迁的(都在客户端 `config/numen/`):`companions/<uuid>/{chat.jsonl(含 .v*.bak)、stats.json、inbox.jsonl、blocks.json、memory/、goal.json、binding.json、world}`、`conversations.json`、全局的人设库、`lua/<主人>/`(模块加账本)、`skills/`、`providers.json`、MCP 两份配置、`numen.json`;服务端旁的 `EventOutbox` SavedData。

**单人游戏(含局域网房主,服务端在同一台机器上)**——不过网络,服务端直接读磁盘:
1. 触发:主人进世界,服务端对名册上的每只同伴检查"世界里有没有她的目录";没有且旧目录 `config/numen/companions/<uuid>/` 存在(旧的 `world` 标记与这个世界对得上,或没有标记),就迁。
2. **复制不移动**:复制到 `companions/<uuid>.migrating/`,逐文件校验(日志经 `ConvoLog.migrateIfNeeded` 升到最新,坏行照旧跳过),完成后原子改名为 `companions/<uuid>/`,最后给旧目录改名 `<uuid>.migrated`(不删,留到以后的版本)。中途崩溃:下次看见 `.migrating` 就清掉重来,看见新目录已就位而旧目录还没标记就只补标记——**可重来、只做一次、不丢**。
3. 全局库归给房主:人设库、模块、账本进 `players/<房主>/`;`providers.json`、`skills/`、MCP 配置本来就在服务器目录,不动。
4. `EventOutbox`:启动时把存档里的内容倒进各同伴的收件箱,然后删掉那个数据文件;读它的最小 codec 只留在迁移里,类本身删。
5. `conversations.json`:按成员 uuid 过滤出属于这个世界的会话,写进 `players/<房主>/conversations.json`;展示偏好留客户端文件。

**多人(专用服、局域网访客)**——数据在玩家客户端,只能上传:
1. 客户端连上带 `Hello`;若有旧目录,发 `MigrationOffer(同伴 uuid 列表、各自大小)`。服务端只接受:是他名下的、世界里还没有数据的、总量不超过上限的。
2. 客户端用分片流把文件送上去(沿用 `Fragments`,走上行预算,慢但不挤游戏),服务端落到 `.migrating` 再原子改名,回 ack;客户端收到 ack 才把旧目录改名 `.migrated`。人设与模块一并上传到 `players/<主人>/`。
3. **key 永不上传**:`providers.json` 不在上传清单里;旧同伴迁上去后档案悬空,她停在"未绑定",主人从服主提供的档案里选一个。
4. 这条上传路径体量不小,建议单独一个提交,且可以晚于单人游戏的切换(待定,见 14.9)。

旧的"对账清理孤儿目录"(`CompanionHome.reconcile`)随世界归属一并消失:同伴数据住在世界里,遣散就是删世界里那个目录。

### 14.8 主流参照

本会话读了源码原文的:
- **Mindcraft**(`src/agent/history.js`):每个 agent 的状态是 `bots/<名>/memory.json`(摘要 `memory`、当前 `turns`、自提示状态),被挤出的旧回合追加进 `histories/<时间戳>.json` 存档;超过 `max_messages` 时摘要并归档。可借鉴:**"当前视图"与"完整存档"分开**,和我们"日志不改、压缩只是指针"同向;不借鉴它的整份覆盖写(崩溃易丢,我们有追加日志)。
- **Voyager**(`voyager/agents/skill.py`):技能库按目录落盘(`skill/code/*.js`、`skill/description/*.txt`、`skill/skills.json` 加向量库),重写技能时旧版本留成 `V2/V3`,恢复时校验向量库条数与技能表一致、对不上就报错。可借鉴:**手艺与一局的经历分开存**(对应我们的玩家库与模块、对世界里的日志),以及"恢复时自检一致性"。
- **Citizens**(NPC 插件,`Citizens.java`):NPC 数据存服务端文件(默认 YAML,经 `NPCDataStore` 抽象可换后端),启动后晚一刻装入,按配置的周期定时存、停服时立即存;不需要任何客户端。可借鉴:**存储后端用一个窄接口隔开、周期落盘加停服强制落盘**,对应我们的 `Io` 车道与停机排空。它的存盘是否异步、装入在哪个线程,读到的文件里看不出,不引为依据。
- 没有找到可借鉴的:**LLM 循环自己在服务端 tick 里怎么避免拖慢主线程**——同类要么是独立进程(Mindcraft、Voyager),要么没有 LLM(Citizens)。这块没有现成做法,按 14.3 自己定规则。

### 14.9 风险与需要定的事

风险:
1. **主线程负担**:所有人的循环、模型回调、事件都在服务器主线程。靠 14.3 的合并与后台车道缓解;多人时每刻的合并与编码成本需要实测。
2. **磁盘异步化的崩溃语义**:写入进车道后,崩溃会丢车道里还没落的几条。追加日志坏行跳过、压缩是指针,可恢复,但"主人的话刚说出口就崩"可能丢一句;不另开同步路径(已定,见下)。
3. **单人游戏暂停**:集成服务端暂停时不 tick,打字机与"攒够时长"熟度停住;模型回调仍会处理。行为与现在略有不同,需要真机看一眼。
4. **向后兼容**:新服务端遇到旧客户端(无 `Hello`)按"没装客户端"处理,不推 `Feed`;协议版本不一致时客户端拒绝订阅并提示。
5. **`NumenGateway.emit`**:外部模组在客户端调的公开入口。服务端版直接入箱;客户端版变成发包,只能回 `HANDED_OFF`,`Delivery` 的 `QUEUED/SEEN/TO_EXTERNAL_BRAIN` 报不出来(要报就得加回包)。
6. **评测的 `Brain` 与产品零件重复**:它和旧的客户端循环各接一遍端口。服务端循环落地后让 `CompanionLoop` 接受注入的模型、人设、主动性,评测复用同一个类;在提交 12 收口。
7. **专用服 MCP OAuth**:见 14.5。

  - **事件只有收件箱一个去处**:删 `EventOutbox` 与 `NumenEventPayload`,`NumenEvents.deliver` 直接送进她的大脑;`NumenDeathPayload`/`NumenRespawnPayload`/`CurrentTaskPayload` 也删(当前任务是任务槽交给大脑的 `TaskReport`)。
    GameTest 里直接造的同伴也配一个不思考的脑(`GameTestKit.withBrain`),用例从 `GameTestKit.events` 读她的收件箱,不为测试另留一条路。

  - **设置页不留第二个出处**:模型目录、草稿解析成的端点、连通性检测在服务端算(库协议 `catalog`、`provider-check`),档案表单只画答案;技能目录是服务器全局的,管理员在技能页用 ↻ 让服务器重扫。
