# 输入管线:从有人跟她说话,到她的手按下去

一条线讲完她怎么接收输入、谁替她想、想完怎么落到身体上、她的东西存在哪。合并了原来的 `mcp-server.md`(外部大脑)与 `companion-input.md`(身体的输入层)。
相关的另两份:收件箱的类型表与循环内核见 `agent-loop.md`,群聊的会话与记录见 `group-chat.md`。

**定位(10-16 用户定):Numen 是住在服务器上的 Agent。** 服务端必装,客户端可选;以后还要出 Paper 端,那里只有原版客户端。
所以她的身体、收件箱、循环、记忆、配置都只在服务端;客户端退成可选的前端,装了更好用(面板、语音、动效),不装也能用。

## 一、全景

```
渠道(谁在跟她说话)        大脑(谁替她想)                身体(她做事)
游戏聊天 @她 ─┐
面板、快捷对话 ┤                ┌─ 服务端大脑(服主的 key) ─┐
/numen 命令 ──┼─► 收件箱 ──► 驾驶席 ┤                          ├─► Lua 程序 ─► 任务 ─► 输入层(键盘、视角、鼠标、快捷栏)
QQ、Discord ──┤  (每只一个)        └─ 外部大脑(MCP,自带 key) ┘    (ServerPrograms)
弹幕、定时 ───┤
世界的事 ─────┘
```

三层两管:渠道把话送进收件箱;驾驶席上的大脑从收件箱取件、交出 Lua 程序;身体在服务端跑程序,最后落到她的键盘和鼠标上。
加一个渠道不碰大脑,换一个大脑不碰渠道,谁驱动她都用同一副身体。

**现在与目标。** 10-05 "客户端想、服务端做"已经把 Lua 程序搬到服务端,身体那一段已经在服务端;收件箱、循环、她的记忆、模型配置、外部大脑的端点还在主人客户端,
所以主人一下线,她能把手上的活干完,但听不见、想不了。下文每节先写现状,再写目标。

## 二、渠道

| 渠道 | 现状 | 目标 | 她的回话送到哪 |
|---|---|---|---|
| 面板、快捷对话(装了客户端) | 客户端,`NumenGateway.emit` | 经网络包送进服务端收件箱 | 面板、打字机、语音 |
| 语音输入(装了客户端) | 客户端录音、客户端识别 | 客户端只录音,音频经网络包送上来,服务端识别(§八) | 同上 |
| 群聊(多人对她说话) | 已落地,见 `group-chat.md` | 不变 | 同上 |
| 插件桥接(弹幕、群消息) | 客户端,`NumenGateway.emit` | 走远程端点的渠道令牌(§五) | 原渠道 |
| 游戏聊天 @她 | 没有 | 服务端读聊天 | 聊天行、头顶气泡 |
| `/numen` 命令 | 只有管理类命令 | 加"对她说一句" | 命令回显 |
| 世界的事、定时 | 服务端 `NumenEvents.emit`,主人离线进出箱 | 直接进服务端收件箱 | 不需要回话 |

- 每条输入记着**从哪个渠道来、谁说的**。她说的话总在游戏里说出来(气泡、聊天行),另外送回问她的那个渠道:从 QQ 问的,QQ 上收到回答。
- **装了客户端,玩家的交互与现在一样**:面板、快捷对话、按键说话、她的朗读都照旧,变的只是背后在服务端。
- **没装客户端也能用**:说话靠聊天 @她;征询卡变成一条带可点按钮的聊天消息(底层是现有的 `/numen consent`);她在干什么显示在动作栏或 Boss 栏;
  1.21.6 起可以用原版的服务端对话框做卡片。面板、语音要客户端(原版客户端录不了音、也放不了自定义音频)。
- 我们的客户端与服务器之间只走 MC 自己的连接(自定义网络包,`Wire`/`Fragments` 分片:下行单包 1 MiB、上行 32767 字节、一条消息至多 8 MiB),不另开端口。
  群组服(Velocity、BungeeCord)要实测网络包的转发。
- **网络包不许拖慢服务端的刻。** MC 的收发在 Netty 的网络线程上,主线程只是把包排进去;拖慢游戏的是"收到以后在主线程上做了重活"。
  现状:Fabric 侧收到的包一律 `server.execute` 到主线程,NeoForge 的处理器默认也在主线程;分片的拼装与整条消息的解码因此都在主线程上。
  音频这种连续的流、几 MB 的消息搬上来以后,规则是:拼装与解码在网络线程,识别、合成、模型请求、磁盘读写、渲染在后台线程,
  主线程只做碰世界与她的状态的那一小步(进收件箱、改一个字段);每位玩家的上行设带宽预算,超了就丢弃或让客户端退避,不排进主线程的队。
  下行的大东西(历史分页、朗读音频)按页、按段推,不一次推几 MB。

## 三、收件箱

现状:每只同伴一个,在主人客户端,入队即落盘、取走即清;投递方式(叫不叫醒她、随哪一次调模型交出去)写在类型表里,见 `agent-loop.md` §七。

目标:**搬到服务端,跟着她。** `EventQueue`、`EventTypes`、`JsonlJournal` 本来就在纯 Java 的 `agent` 模块里,原样搬。

- 入口合成服务端一个:`NumenEvents.emit` 与 `NumenGateway.emit` 并成一处,客户端的输入经网络包送进来。
- 出箱 `EventOutbox` 删掉:它存在是因为收件箱在客户端、主人离线时事件没处放;收件箱在服务端,离线只是"攒着"。

## 四、大脑

现状:循环内核 `AgentLoop`(纯 Java,`agent` 模块)跑在主人客户端,用主人的 key 调模型;外部大脑接管时循环停牌(`Hold.EXTERNAL`),
驾驶席只在 `McpMode.driving()` 一处判。

目标(10-16 用户定):**只有两种大脑,同一时刻只有一个坐在驾驶席上。**

| 大脑 | 怎么跑 | key 在哪 | 什么时候用 |
|---|---|---|---|
| 服务端大脑 | 服务端跑 `AgentLoop`,自己调模型 | 服主的配置(单人游戏与自己开的服,服主就是主人) | 默认;主人下线后接班 |
| 外部大脑 | 循环停牌,外部 agent 经远程端点驾驶(§五) | 外部 agent 自己的 | 主人用自己的 Claude Code、Codex 一类 agent 指挥她;想在别人的服务器上用自己的 key,也走这条 |

- **不做客户端大脑,也不做"主人客户端代调"。** 代调要把每一轮的请求反向发给客户端、流式传回,复杂、费网络,同类模组也没人这样做;
  "key 不离开玩家的机器"这件事,外部大脑已经做到了:key 留在玩家自己的 agent 里,服务端只收发事件与程序。Paper 端只有原版客户端,客户端大脑在那里也不存在。
- **记忆的真源只有一份**:不管谁驾驶,进来的话、她说的话、程序与回执都记进服务端那本日志(§六);大脑自己的上下文是从日志派生的缓存。换大脑时新大脑从日志接着来。
- 打字机、语音、气泡、token 台账照旧订阅循环事件 `LoopEvent`,事件经网络包推给在线、装了客户端的主人。
- 主人下线后怎么接班,主人给每只同伴选一项:停下待命(默认)、外部大脑接班、服务端大脑接班(服主允许时)。
  身体本来就不随主人下线休眠(`CompanionChunkLoader` 在她周围保持 3×3 区块),接上一个能想的大脑就是全天候。
- 主人不在时要问的事:征询发到主人接得到的渠道(QQ、Discord……,渠道令牌认的是主人本人);哪里都找不到他,到时按拒绝,她只做本来就放行的事。
- 单人游戏是同一进程里的内置服务端,路径一样,不多一跳网络。
- **模型配置搬到服务端。** 档案、models.dev 目录、三种协议都在纯 Java 的 `ai` 模块里,原样搬;设置里的模型配置页变成服主的配置页(单人游戏里就是你自己)。

## 五、外部大脑

### 现状:主人本机起一个 MCP 服务器

外部 AI 客户端(Claude Desktop、Claude Code、Cursor 或任何支持 MCP 的东西)直接驱动她。驱动期间内置大脑停手——同一具身体同一时刻只有一个脑;
主人在游戏里照常和她说话,话进同一条事件线,由外部大脑接走并回话。工具:`list_companions`、`create_companion`、`delete_companion`、
`get_events`、`say`,其余与内置大脑相同(`lua`、`skill`、`todo`、`memory`)。端点开在主人客户端(默认只绑 `127.0.0.1:8765`,令牌认人),
界面在 `G` → 设置 → 外部大脑。

### 目标:服务端一个远程端点,所有人共用

- **按令牌认人。** 主人用 `/numen token` 发令牌,随时作废;存档只存哈希;照 MCP 的授权规范做。
- **令牌带作用域**:能指挥自己名下的哪几只;角色是**大脑**(取件、发程序、说话,等于驾驶)或**渠道**(只能把话送进收件箱、收她的回话)。
  Claude Code 拿大脑令牌,QQ 机器人拿渠道令牌——插件桥接从此也走这里,不再挂在客户端上。
- **权限不会因令牌变大**:外部大脑的程序同样过权限层,主体是那只同伴。
- **限流**:每个令牌限并发与频率,服主可配总量。
- **协议**:Streamable HTTP,多会话。
- **端口**(只有外部大脑需要,我们的客户端不需要):默认关。先做"服主自己开一个端口,建议套反向代理加 HTTPS"——服务端模组里常见
  (BlueMap 的网页地图、Dynmap、Simple Voice Chat 都另开端口);文档里同时给隧道的办法(如 Cloudflare Tunnel,不开入站端口)。
  以后调研"和 MC 共用一个端口,按开头几个字节分流",照顾只给一个端口的托管服,先确认和代理、别的网络类模组共存;中继服务等用的人多了再说。

### 使用策略(10-16 审出来的,要改)

外部 agent 每调一次工具就是一次完整的模型请求,要重发整份上下文。所以策略的头一条是**少调用**:

- **不再要求每 2 秒轮询 `get_events`。** 现在的接入说明这样要求,等于每分钟 30 次模型请求,哪怕什么都没发生。
  改成长等待:没事就一直等,有事立刻返回,最长 50 秒(给桥接层的请求超时留余量)。
- **事件跟着回执走。** 程序的回执顺带附上这段时间到达的事件;她干活时外部大脑不用另外轮询。
- **看得见。** `look` 返回图片内容(§九),支持看图的 agent 直接看。
- **技能与 API 文档可浏览。** 考虑暴露成 MCP 的资源或提示词,少一轮"先调工具拉说明"。
- 接入说明照这几条改写。

## 六、她的东西存在哪

现状:对话、札记、待办、长期目标、人设、技能、模块真源、模型档案与 key 都在主人客户端 `config/numen/`;服务端只按哈希在内存里缓存她的模块。

目标(10-11 定、10-16 用户确认):**她的一切都在服务端,客户端不存任何一份必须的数据。** 大脑可以换,换了以后她还得记得自己干过什么——
夜里服务端大脑做了什么,早上主人上线她要知道;而外部大脑与服务端大脑都只能读服务端。

| 数据 | 存哪 |
|---|---|
| 收件箱、对话日志(外部大脑驾驶的那段也记)、札记、待办、长期目标、她绑定的人设内容、模块与技能的副本 | 世界存档 `<存档>/numen/companions/<她的 uuid>/` |
| 模型档案与 key、语音服务的 key、models.dev 目录缓存、外部大脑令牌(只存哈希)、权限规则、额度台账 | 服务器 `config/numen/`(服主管) |
| 每位玩家自己的库:人设库、皮肤库、声线库 | 服务器上按玩家:`config/numen/players/<玩家 uuid>/`,跟着服务器走,换世界还能用 |
| 界面主题、窗口布局、按键 | 客户端(只是展示偏好,删了不丢她的东西) |
| 外部大脑自己的 key 与上下文 | 外部 agent 那边;上下文从服务端日志派生 |

- **跟着世界走**:备份世界就连她一起备份,删世界她也跟着走;每个世界的她各有各的经历。
  旧的客户端记录(`config/numen/conversations/<uuid>.jsonl` 等)按她的 uuid 在主人首次上线时迁上去。
- **手艺跨服务器只能导出导入**:同一台服务器内跨世界共享;没有客户端的真源以后,带去别的服务器靠导出、导入。
- **存法:文件,不用数据库。** 要存的全是"按同伴一份、按时间顺序读"的东西,没有关联查询,写的只有服务端:
  长流水(对话、审计)用只追加的 JSONL,沿用现在客户端的格式;小文档用 JSON,先写临时文件再改名;很小的结构化状态继续用原版 `SavedData`;
  读写都在后台线程,不占主线程。不用 SQLite:要带各平台的原生库,服主边开服边拷贝世界时库文件可能拷坏,13 条版本分支与 Paper 都要各验一遍;
  以后真要全文搜索或多服共享,优先纯 Java 的嵌入式库,存储先收在一个接口后面。
- **客户端不留副本**:面板打开时向服务端分页取,之后跟着实时事件长;只在内存里。历史按页拉,别一次推几 MB 挤占那位玩家的连接。
- **群聊照旧"存储按人、视图按会话"**(`group-chat.md` §七),只是那本日志换到服务端。
- 变长靠现有的整理(摘要替换更早的历史),规则不变。
- **日志不写对话内容。** 服主与托管商看得到 `latest.log`,玩家求助时又常把日志整份传到 mclo.gs 一类公开网站;
  INFO 级只记编号与摘要(哪个工具、成没成、多大),对话原文、程序源码、事件正文不进日志。客户端现在就照这条改。

代价照实说:服主看得到她的对话与札记。这不是"存在哪"带来的:循环在服务端跑,每句话都经过服务端,服主在内存里就看得到;存盘只多了保留。
原版服务端本来就把公共聊天明文写进 `latest.log`,进第三方服务器本来就信任服主。所以做到的是说清楚、可撤回:进服授权卡写明"服主看得到她的对话",
保留时长可设,面板上一键导出、一键清空;给服主一段可以写进服务器隐私说明的文字。单机没有这个问题。
10-11 用户定:只存服务端,不做"只放主人电脑"的选项,也不做下线交接。

**显示照旧只给主人。** 存在哪与谁看得见是两回事:头顶气泡、聊天栏里她的话、语音只给主人(`SpeechBubbles`:她的思考与发言是主人的私事),
这一点不变。没装客户端时,她的回话用只发给主人的系统消息,不进公共聊天。

## 七、身体的输入层(已落地)

她是没有客户端的服务端玩家。真人手里的键盘、视角、鼠标、快捷栏,她都有,而且**只此一份、谁驱动她都用同一份**——寻路、Numen 的工具、
第三方插件、外接大脑的程序,最后都按这几样让她动。参照:Mineflayer 本体的 `setControlState`/`lookAt`/`dig`/`activateItem`、Carpet 的
`EntityPlayerActionPack`、Baritone 的 `InputOverrideHandler`——都是一层统一的"玩家输入",粒度就是真人能按的东西,寻路建在它上面。

全在 Numen API 的公开包 `com.dwinovo.numen.api.entity`,进瘦 jar:

```java
NumenPlayer her;
her.controls()  // 键盘:前后左右、跳、潜行、疾跑
her.look()      // 视角:at(点)、turn(朝向)、faceToward(x, z);看向一格方块上她看得见的那一点或那一面
her.mouse()     // 鼠标:pick/on/itemRay 准星;dig/attack/release 左键;use/useItem/stopUse 右键;intents() 此刻要问许可的意图
her.hotbar()    // 快捷栏:hold(格)、grip(东西),每次换了都交回 BodyAction
```

- **粒度就是真人的输入。** "挖掉那一格""放一块到那里"这类组合不进这一层,是使用者用这四件拼出来的。四件都是"一具服务端玩家 + 状态"的小类,
  普通假玩家也能 `new` 来用(寻路的 `TestBody`)。
- **鼠标只对准星起作用。** 先 `look()` 转过去再按;`mouse()` 自己做准星拾取,"手点到了哪一格"只有一个出处。要的是某一格时先问 `on(pos)`。
- **每一下如实交回结果。** 左键交回 `Strike`(还在挖 / 挖掉了什么 / 被拒及理由 / 准星没落在方块上);右键交回 `Use`(缓手没按 / 按了:落着什么、
  世界变了哪几格、打开了什么界面 / 被拒)。点格子、点空气、点实体是同一个右键、同一种结果,`numen.use.*` 都从它写回执。右键按住(拉弓、吃喝、举盾)
  与左键按住挖一样归鼠标管,两次按下的间隔是鼠标的事。
- **权限长在鼠标上。** 左键换到新的一格时问能不能拆;右键会往世界里放东西时问能不能放,否则问能不能用。要问主人时鼠标停下、交回 `Refusal.Asks`,
  由驱动者决定怎么问(寻路是走到那一格停下问);不许是 `Refusal.Denied`;服务端把挖掘退回来是 `Refusal.Server`(身体汇报,不是裁决)。
  判据只认身体是谁:是同伴就过权限层,普通假玩家照原版;别人自己 `new` 一个同伴的鼠标也绕不过去。
- **原版公式只有一个出处。** `DigTime`(挖掘进度与冷却,从 `DigTime.Mining` 算,不碰真身体也能算)、`Reach`、`Sight`、`Faces`、`Replaceable`
  身体与寻路规划共用;挑工具归 `ToolChoice.take`。纯规划的几何(`Footing`、`Stepping`、`Clearance`)与规划用的身体快照留在 pathing。
- **换驱动者时统一松手。** `CompanionBrain` 每刻只选一个驱动者(反射 > 同步 > 当前任务 > 空闲姿态),换人那一刻调完旧驱动者的 `stop` 就把键全松、
  挖掘进度清零、右键松开,新驱动者从干净的身体开始;任务与反射不各自松键。
- **寻路怎么接。** 身体端口 `Body` 留在 pathing,交出那具玩家与这四件,寻路直接用;`Ports` 里只剩寻路自己的策略。

## 八、语音

原版客户端录不了音、也放不了自定义音频,麦克风与喇叭都在玩家的电脑上,所以语音要客户端。玩家的用法不变,变的是背后:

- **语音输入**:客户端照旧录音,不再自己调识别;音频经 MC 的连接送上服务端,服务端用服主配置的 key 识别成文字,进她的收件箱。
- **朗读**:服务端用服主配置的 key 合成,音频推给主人的客户端播放。
- **客户端不存任何 key。** 现在客户端里的各家语音服务实现(豆包、阿里云、MiniMax、Fish Audio、GPT-SoVITS、OpenAI 兼容……)搬到服务端,
  大多是 HTTP 调用;流式识别要重新接到上行的音频流上。
- **音频的流量**:16kHz 单声道 PCM 约每秒 32 KB,一句话一两百 KB,上行要分片,和游戏流量挤一条连接;先压缩再传,避开原生库(Opus 的常见实现是原生库)。
- **以后可选的联动**:Simple Voice Chat 的服务端 API 能收玩家麦克风的包、能建以实体为声源的音频频道。给装了它、没装我们客户端的玩家一条语音路,
  她的声音也能从她身上发出来;它的 Paper 插件同样要玩家装它的客户端。做成 `plugins/` 下的联动,拿真模组验过再接。

## 九、多模态:谁来画她看到的东西

服务端大脑与 Paper 服上没有渲染器,专用服务器连方块贴图都没有。主流做法:

- Mindcraft:bot 进程里跑无头 3D 渲染(prismarine-viewer,three.js + WebGL 画布),从 bot 眼睛的位置画 800×512 的 JPEG,
  先交给视觉模型读成文字,再把文字交给主模型。
- BlueMap(服务端 3D 地图):服务端用 Java 从世界数据渲染;贴图在服主打开 `accept-download`(确认接受 Mojang 的 EULA、拥有正版)后
  从 Mojang 下载客户端 jar 取,不再分发;模组方块的贴图从模组 jar 里取。

打算:**服务端照 BlueMap 的取资源办法,从她眼睛的位置画一帧低分辨率的图。** 不依赖客户端,单人游戏、模组服、Paper 都能用。
初版只画方块,实体画成简单的方块形状;透明方块与光照后补。图怎么交出去:服务端大脑放进模型请求;外部大脑经 MCP 的图片内容返回;
模型不支持看图时,按 Mindcraft 的办法先读成文字。先出原型与样图,看模型读不读得懂再定做不做全。

## 十、安全:第三方服务器上谁防谁

服务端必装以后,她多半活在别人的服务器上。三方各有要防的,分开说:

**1. 玩家防服务器。** 服务器上的一切(背包、房子、公共聊天)本来就在服主手里,她的记忆跟着身体住在那里,这一层只能靠信任,做到的是说清楚、可撤回:

- **按服务器授权,像浏览器按网站给权限。** 第一次带她进一个多人服时,客户端弹一张卡说清这个服务器要什么:存她的记忆(服主看得到)。单机不弹。
- **在别人的服务器上用自己的 key,走外部大脑。** 服务端从头到尾拿不到它;服务端大脑用的是服主的 key、服主出钱。
  没有任何一条代码路径会让玩家把 key 交给服务端;要把 key 交给服务器的玩法只能明确提醒:交出去的 key 服主拿得到,只交设了花费上限的那一个。
- **key 碰不到的地方。** 不进日志、不进模型上下文(提示注入问不出来);Lua 沙箱没有文件与系统访问,服务端大脑的 key 玩家的程序也读不到。
- **日志不写对话内容**(§六)。
- **看得见、删得掉。** 面板上写明"她的记忆存在这个服务器上",一键导出、一键清空。

**2. 服务器防玩家。** 玩家提交的 Lua 在服务端跑,没装客户端的玩家也能提交:

- 沙箱上限(指令数、字符串、时长)、每个主人同时几段、主线程每刻预算,都由服主可配(10-05 已有,改成可配)。
- 服务端大脑按玩家配额;远程端点按令牌限并发与频率,服主可配总量。
- 远程端点默认关;令牌高强度随机、只存哈希、可设过期、随时作废、带作用域;开了明文 HTTP 时界面与日志警告,建议反向代理加 HTTPS;每次接入与调用记审计日志。
- 服主的总开关:能不能用 Numen、能不能用服务端大脑、能不能开远程端点、能不能夺舍,各自一个。

**3. 玩家防玩家。** 不让她成为搞破坏的工具:

- 权限层的硬规则:别人的东西拆不得、拿不得、打不得,主人点"允许"也解不开(`permission-layer.md` §六)。
- **专用服务器上"说不清是谁的"按别人的算**(硬拒),服主可改;单机与局域网照旧问主人。否则别人装模组前盖的房子,
  一个想搞破坏的主人点一下"允许"就拆了。
- 提示注入:只有主人与群聊成员的话算命令,别人在聊天里 @她、QQ 与弹幕渠道进来的话都标着来源;模型就算被说动,
  动手也过权限层,越不过主人本身的权限,更越不过硬规则。

## 十一、以后:夺舍

主人下线时,用和主人同一个身份的假玩家顶替主人的身体干活(像 Carpet 的 `/player shadow`)。在这条管线里只是"换一个身体来源",渠道、收件箱、大脑都不变。
要单独定:上线时的交接(防复制物品)、主人明确授权与范围、死亡与危险保护、服主开关、回来时完整交代做了什么。不在本方案里做。

## 十二、分步落地

每一步单人游戏行为不变,日常 GameTest 两个加载器全过。

1. **收件箱与日志搬服务端**:入口合一、出箱删掉、条目带渠道与说话人;日志落世界存档、不写对话内容;客户端面板经同步包分页读;旧数据首次上线迁上去。
2. **循环与模型配置搬服务端**:服务端大脑跑 `AgentLoop`;档案、目录、协议随 `ai` 模块搬;呈现订阅经网络包;驾驶席二选一。
3. **记忆与玩家的库搬服务端**:札记、待办、目标、人设落在同伴存档;人设、皮肤、声线库按玩家落在服务器;模块与技能副本落盘;面板导出与清空。
4. **远程端点**:`McpServer` 搬服务端;令牌、作用域、限流、多会话、审计;插件桥接改用渠道令牌;使用策略照 §五 改(长等待、事件随回执、接入说明)。
5. **语音搬服务端**:识别与合成在服务端,客户端只录音与播放(§八)。
6. **无客户端交互**:聊天 @她、可点的征询消息、动作栏状态、1.21.6+ 对话框。
7. **服务端大脑全天候**:按玩家配额;征询发到渠道;主人下线后的接班选项。

多模态(§九)不在这条线上排,先出原型。安全(§十)不单独成一步:每一步把它涉及的那几条一起做——第 1 步带日志不写对话,第 4 步带令牌与审计,第 7 步带配额与服主开关。
