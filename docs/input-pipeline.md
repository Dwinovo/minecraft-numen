# 输入管线:从有人跟她说话,到她的手按下去

一条线讲完她怎么接收输入、谁替她想、想完怎么落到身体上、她的东西存在哪。合并了原来的 `mcp-server.md`(外部大脑)与 `companion-input.md`(身体的输入层)。
相关的另几份:收件箱的类型表与循环内核见 `agent-loop.md`,群聊的会话与记录见 `group-chat.md`,总的分工见 `architecture-mind-model.md`。
这一条线的定案是 [ADR runtime 0008](adr/runtime/0008-brain-on-owners-client.md):**脑子和记忆在她的创建者(主人)的客户端上,身体在服务器上,两端之间一个座位。**

**定位(11-25 定):Numen 是主人电脑上的 Agent 驾驶服务器上的一具玩家身体。** 服务端必装;她的创建者必须装客户端——脑子在那里。
别的主人(分享给了的人)和任何玩家不装客户端也能用原版的方式跟她说话(§二)。

## 一、全景

```
渠道(谁在跟她说话)        大脑(谁替她想,在创建者的客户端上)   座位          身体(服务端)
面板、快捷对话(客户端本机)─┐
游戏私聊 /msg、聊天栏会话 ─┤                ┌─ 内置循环(主人自己的 key) ─┐
/numen 命令 ──────────────┼─► 收件箱 ──► 驾驶席 ┤                          ├─► program/run ─► Lua 程序 ─► 任务 ─► 输入层
QQ、Discord、弹幕(渠道桥)─┤  (每只一个)        └─ 外部大脑(MCP,自带 key) ┘    (JSON-RPC)   (ServerPrograms)
定时 ────────────────────┤
世界的事、别人的话 ───────┘(服务端 events/new 送来)
```

三层两管:渠道把话送进收件箱;驾驶席上的大脑从收件箱取件、写出 Lua 程序;程序经座位送到服务端,在身体旁边跑,最后落到她的键盘和鼠标上,
回执同样经座位回到大脑。加一个渠道不碰大脑,换一个大脑不碰渠道,谁驱动她都用同一副身体;服务端不知道、也不关心驾驶席上坐的是内置循环还是外部大脑。

**服务端要用的放服务端,只有脑子用的放客户端。** 服务端:身体与背包、主人表、权限设置与征询、她穿的皮肤、内置模块与插件登记的函数、技能与提示片段、世界上的事。
客户端:循环、收件箱的那一份、对话日志、摘要、札记、目标、定时、key、模型档案、人设、声线、自己的技能、接进来的 MCP 工具、外部大脑的入口。

## 二、渠道

| 渠道 | 在哪接 | 怎么到她的座位 | 她的回话送到哪 |
|---|---|---|---|
| 面板、快捷对话 | 创建者的客户端本机,`NumenGateway.emit` | 直接进本机收件箱;群里与共享主人的话经服务端(下) | 面板、打字机、语音 |
| 语音输入 | 客户端录音、客户端识别,转写文字作为一句话 | 同上 | 同上 |
| 群聊(多人对她说话) | 见 `group-chat.md`;成员表在服务端 `Conversations`,话只经 `Hearing` | 服务端 `events/new` | 带会话名回到聊天行与面板 |
| 游戏私聊 `/msg <她>` | 服务端接住发给她的私聊(她是真玩家,包到她的 `FakeClient`) | `Hearing.whisper` → `events/new` | 她私信回(`say` 带说话的地方) |
| `/numen chat <会话>` 聊天栏切进会话 | 服务端 `ChatBar` 拦聊天栏 | `Hearing.say` → `events/new` | 带 `[会话名]` 的聊天行 |
| 插件桥接(弹幕、群消息) | 连创建者客户端上的外部大脑端点,用渠道令牌(§五) | 本机收件箱 | 原渠道 |
| 世界的事 | 服务端 `NumenEvents.emit` | `events/new` | 不需要回话 |
| 定时 | 创建者客户端上的 `OwnerSchedules` | 本机收件箱 | 同面板 |

- 每条输入记着**从哪个渠道来、谁说的、在哪儿说的**:别人对她说的话(群里、私聊、共享主人在面板里说)只有 `Hearing` 一处把它们变成事件送进创建者的座位,
  事件带说话人(`player@短码 (名字)`,身份只有这一种写法)和说话的地方(`Spoken`:`who`、`venue`=面板/会话/私聊、会话号);点了名的或私聊她的 keeper 的话会叫醒她(`<query>`,
  带 `venue="whisper"`/`"group"`,群里再带 `<audience turn="…">` 一行说还有谁听得见、这是第几句),别人的话与群里没点到她的是旁听(`talk`,捎带投递不叫醒)。
- **她说话也带着说话的地方**:`say` 带上 `Spoken`,由服务端在聊天里说出来(`Voice.line`:面板 `<她> …`、会话 `[会话名] <她> …`、私聊用原版 `commands.message.display.incoming`),
  客户端从不自己碰聊天。这一句的听众是 `Spoken.who` 那一位,会话里的其他成员由 `Hearing.heard` 旁听。
- 程序替谁做事看 `program/run` 带的 keeper:主人在面板上说的就是创建者,共享主人说的就是他;服务端按主人表核对,权限与"这是谁的"都按这一位 keeper(`NumenPlayer.keeperUuid`),
  不按最近谁说话猜。
- **创建者必须装客户端**(脑子在那里);共享主人与别的玩家不装也能用原版的:
  - **私聊**:原版 `/msg <她> <话>`(自带补全),她的 keeper 的话是主人的话,她私信回;不在主人表上的玩家 `/msg` 她按旁听档进收件箱、标着是谁说的,不叫醒她。
  - **会话(群)**:就是面板左栏那套,一个会话 = 主人 + 他用得了的几只同伴的成员表,单聊是只有一只的会话;命令只是面板操作的另一种按法,同走 `OwnerInput` 的会话操作:
    `/numen group invite|remove|rename|dissolve`;`/numen chat <会话>` 之后聊天栏打的字进这个会话,只有自己看得到、带 `[会话名]`;`@` 谁谁醒、不 `@` 全体醒、同伴之间互相旁听;
    `/numen chat` 切回公屏;`/numen chat <会话> <话>` 只发一句。`@` 的补全词(`ClientboundCustomChatCompletionsPacket`)切进会话时由服务端设成成员名,词只有一个来源:成员表。
  - 征询变成带可点按钮的聊天消息([允许] [以后都允许] [拒绝],底层是 `/numen consent`);她在干什么显示在动作栏。
  - **召唤只要名字,不设任何前提**:人人能召唤,每人上限是服务器设置(默认不限);档案、人设、声线在创建者的客户端上绑,召唤卡上可以一并选。
  - 面板、语音、本地选图、头顶气泡、思考过程要客户端。
  - **给原版客户端说话的字由服务端翻**:按那位玩家客户端报上来的语言设置翻好再发(`MixinServerCommonPacketListener` 一处),装了客户端的照旧发带键的消息。
  - **"装没装客户端"只在一处判**:`Presence.hasClient`——`Hello` 的协议版本对得上、`ClientCaps` 报了它提供哪些只在客户端的联动,两样都到齐才算。
    握手由服务端先开口:`ServerHello(协议号)` → 客户端 `Hello` + `ClientCaps` → 服务端 `HelloAck(是否管理员, 是否房主)` 并推名册与会话表。
    我们的网络通道全是可选的,原版客户端进得来;Numen 没有注册物品、方块、实体。
- 我们的客户端与服务器之间只走 MC 自己的连接(自定义网络包,`Wire`/`Fragments` 分片:下行单包 1 MiB、上行 32767 字节、一条消息至多 8 MiB),不另开端口。
- **网络包不许拖慢服务端的刻。** 拼装与解码在网络线程,识别、合成、模型请求、磁盘读写在后台线程,主线程只做碰世界与她的状态的那一小步;每位玩家的上行设带宽预算(`UplinkBudget`),
  超了就丢弃。上行处理器登记时声明 `Execution.NETWORK` 或 `MAIN`;Fabric 的网络 API 总在服务端主线程上调接收器,所以处理器必须在两种线程上都对。磁盘写走每个归属一条的串行车道(`Lanes`),停机时排空。

## 三、收件箱

脑子在创建者的客户端上,**收件箱也在那里**(她的家 `config/numen/client/companions/<uuid>/inbox.jsonl`,入队即落盘、取走即清)。
服务端不存她的收件箱:世界上的事经 `NumenEvents.emit` 进座位上的发件留存(`Outbox`,内存里、有界,满了丢最老的并记账),每条一个递增序号,经座位的 `events/new` 送到客户端,客户端 `events/ack` 确认后服务端才丢;
断线重连 `seat/open` 带上最后收到的序号,从下一号补。别人对她说的话同样走这一条。事件还带代数(她的身体每进一次世界加一),`program/run` 带着脑子以为的代数,对不上就退回"她已经不是那个身体了"。
投递方式(叫不叫醒她、随哪一次调模型交出去)写在类型表里,见 `agent-loop.md`;`EventQueue`、`EventTypes`、`JsonlJournal` 在纯 Java 的 `agent` 模块里,两端用同一份急件规则。

- 入口只有两个:服务端 `NumenEvents.emit`(世界的事)与 `Hearing`(别人的话);客户端本机的输入(面板、语音、定时、渠道)直接进本机收件箱。
- 主人下线(创建者的座位没人坐)她登出(body 0008);他回来 `seat/open` 续传。服务端的留存不落盘,服务器重启丢掉没确认的那几条。

## 四、大脑

循环内核 `AgentLoop`(纯 Java,`agent` 模块)由 `LoopHost`(`mind` 包)宿在创建者的客户端上,用主人的 key 调模型;外部大脑接管时循环停牌(`Hold.EXTERNAL`),
驾驶席只在 `McpMode.driving()` 一处判。**只有两种大脑,同一时刻只有一个坐在驾驶席上**:

| 大脑 | 怎么跑 | key 在哪 | 什么时候用 |
|---|---|---|---|
| 内置循环 | 客户端上跑 `AgentLoop`,自己调模型 | 主人电脑上的钥匙串 | 默认 |
| 外部大脑 | 循环停牌,外部 agent 连主人本机的端点驾驶(§五) | 外部 agent 自己的 | 主人用自己的 Claude Code、Codex 一类 agent 指挥她 |

- **记忆的真源只有一份**:不管谁驾驶,进来的话、她说的话、程序与回执都记进主人客户端上她的家里那本日志(§六);大脑自己的上下文是从日志派生的缓存。换大脑时新大脑从日志接着来。
- **座位**:服务端对每只同伴开一个座位,只认创建者的客户端来坐(`seat/open`)。方法:`catalog/get`(她能做什么:函数与说明、技能、提示片段、本能名册)、`program/run`(带 keeper、代数;答复是结构化的结局)、
  `program/interrupt`/`program/cut`/`body/stop`、`state/get`(她此刻的样子 `<runtime_state>`,一轮开头取一次,每份程序结局也带着)、`say`(带说话的地方)、`events/ack`;
  服务端发的通知与请求:`events/new`、`catalog/changed`、`client/call`(只有主人客户端答得了的函数);
  客户端报回的通知:`run/started`、`run/ended`(服务端在 `SeatConnection` 一处派成 `CompanionEvent.RUN_STARTED`/`RUN_ENDED` 给插件)。JSON-RPC 的编号配对、超时、撤回由 `mcp` 模块的 `RpcPeer` 管,装进一种 MC 自定义包。单人游戏两端同进程,包只在内存里转一手。
- **主人在不在**只在 `OwnerPresence.present` 一处算:**创建者的座位上有人坐**(内置循环与外部大脑都经这个座位)。共享主人在线、创建者不在,没有谁能驾驶她,她照 body 0008 登出。
  身体的去留不在这里定:座位有人坐、没人坐的每个时机都只是让 `Companions.reconcile` 对一次账(判据见 `Attendance`);登出时在跑的程序当场切断,结局留着,重连时随续传补上。
- 打字机、语音、气泡、token 台账订阅循环事件 `LoopEvent`,都在客户端本机;服务端不知道。
- **渠道(QQ、Discord……,插件桥接)**:主人从渠道说一句话,由客户端上的大脑去想,回话回那个渠道。征询也交给那个渠道:Numen 只给出通用的征询(编号、要做的事、可选的答复)和一个答复入口,
  怎么显示是渠道插件自己的事。
- **模型配置在客户端。** 档案、models.dev 目录、三种协议都在纯 Java 的 `ai` 模块里;模型档案是主人库里的一种条目,key 不在档案里,在钥匙串里(§六)。

## 五、外部大脑

外部 AI 客户端(Claude Desktop、Claude Code、Cursor 或任何支持 MCP 的东西)直接驱动她。驱动期间内置循环停手——同一具身体同一时刻只有一个脑;主人在游戏里照常和她说话,话进同一条事件线,由外部大脑接走并回话。
**端点开在主人的电脑上**(`McpMode` 是 `ClientServices` 持有的实例,绑 `127.0.0.1`;端点是纯 JVM 模块 `mcp` 里的 `McpEndpoint`,协议是我们自己实现、自己维护的,见 control 0019),
配置、令牌、审计住在 `config/numen/client/mcp/`。服务器不用开端口;外部大脑经同一个客户端、同一个座位开她,谁在驾驶由客户端一处定。

- **按令牌认人。** 主人在聊天栏里的会话命令(`/token create <brain|channel> [all|<同伴>] [<天数>]`、`list`、`revoke <编号>`)发令牌:明文只显示一次,创建时整把复制到剪贴板、界面只显示前缀。存档只存 SHA-256 哈希,令牌是 256 位随机数。每个请求带 `Authorization: Bearer`,令牌不进查询串。
- **令牌带作用域与身份**:作用域是 `all` 或点名的几只;身份是**大脑**(`list_companions`、`create_companion`、`delete_companion`、`get_events`、`say`,加上和内置循环同一批工具)或**渠道**(`list_companions`、`send`、`get_replies`、`answer_consent`)。
- **权限不会因令牌变大**:外部大脑的程序经座位送到服务端,同样过权限层,主体是那只同伴与程序替谁做事的 keeper;渠道根本没有跑程序的口。
- **限流与审计**:每张令牌限同时在飞的调用数与每分钟调用数,整个端点再限总并发与总频率(`mcp_server.json` 的 `limits`);每次接入、拒绝与工具调用在 `mcp_audit.jsonl` 记一条(不记程序源码、事件正文、她的话、令牌);同一来源认证失败过多就限流。
- **协议**:MCP 2025-11-25(向下照客户端谈 2025-06-18、2025-03-26),Streamable HTTP,跑在 JDK 自带的 HTTP 服务器上;请求过一条处理链:查 `Origin`/`Host` → 认 Bearer 令牌 → 管陌生地址 → 传输;
  只实现用到的协议面:握手、ping、工具、进度、取消、表单式征询。
- **征询问人,不问模型**:外部大脑驾驶着她时,征询经 `ConsentVenues` 交给场所:游戏里的卡、外部大脑的 elicitation(`elicitation/create`,只问声明了能力、开着流、令牌管得着她的会话)、渠道。
  人选了"允许 / 允许并记住 / 拒绝(可带一句话)"走 `ConsentVenues.answer`,经 `ConsentReplyPayload` 回服务端的 `ConsentDesk.reply`;不支持 elicitation 的客户端不问,征询挂到主人在游戏里答,到期按拒绝。没有任何让模型自己答征询的工具。
- **渠道**:渠道令牌 `send` 一句话进本机收件箱;她的回话和通用形式的征询投进这张令牌的信箱,渠道用 `get_replies` 长等待取走,用 `answer_consent` 交回主人的选择。
- 接进来的 MCP 工具(她用的,`McpClientConfig`)也在主人客户端上:配置在她的库里,stdio 类起的是主人自己电脑上的进程,令牌在主人的钥匙串 `mcp-oauth.<名>`。

### 使用策略

外部 agent 每调一次工具就是一次完整的模型请求,所以策略的头一条是**少调用**:

- **长等待。** `get_events` 没事就一直等,最长 50 秒,到点返回"没有新事件",再调一次。什么算"有事"读的是内置循环开 run 的同一条判据(投递档声明会叫醒她的条目落地就返回);逻辑在纯 Java 的 `ExternalWait`。
- **事件跟着回执走。** 外脑调工具(`Lua` 等)时,回执后面另附一段这段时间到达的事件;取走走同一个口,之后 `get_events` 不再重复给。
- **外脑看到的与内置循环同一份。** 交给外脑的正文只在 `ExternalBrain` 一处生成:程序回执 = 结果的话 + 这段时间的事件 + 她此刻的 `<runtime_state>`(经座位 `state/get` 现取);工具表是内置循环每轮发的那份。
  连上时的说明(`McpInstructions`)只放外接特有的几段,并让它先调一次 `guide(companion)`,`guide` 交出内置循环读的同一份系统提示。
- **技能与 API 文档不暴露成 MCP 资源或提示词**:`Skill` 与 `ApiSearch` 是唯一来源。
- **所有等待都不在主线程上**:端点的等待经 `ExternalBrain.await(hands, future)`,在主线程上调会直接抛。

### 与旧做法的出入

- 旧版端点在服务端、令牌发在服务器上、外脑要服主开端口;现在在主人电脑上,`/numen token` 与服务端的 `TokenCommands` 已删,令牌命令是客户端会话命令。
- `mcp-server` 这种库已不在服务端,`LibraryDesk.MCP_SERVER` 由客户端自己的 `McpMode` 回答。
- 授权是静态 Bearer 令牌,没做 OAuth 授权服务器那一套(我们作为客户端接别人的 MCP 服务器时的 OAuth 在 `mcp` 的 `client/auth`)。

## 六、她的东西存在哪

**每样东西只有一个归属,归属决定它在哪个根目录。** 单人游戏里服务端与客户端共用一个 `config/numen/`,所以服务器、本机各占一个子目录,根下不放散文件。

| 归属 | 根目录 | 放什么 |
|---|---|---|
| 对话记录 | 世界 `<存档>/numen/conversations/<会话 uuid>.jsonl` | 一段对话一个文件,Claude Code 会话记录的格式,只追加;她的登记项里记着她当前的会话 id,清空上下文换一个新的,旧的留着;只有坐着她座位的客户端能写,她的主人表上的人能翻页、订阅(ADR runtime 0010) |
| 同伴(身体) | 世界 `<存档>/numen/companions/<她的 uuid>/` | 身体的旁路轨迹(`trace/`,开了才写,寻路为什么放弃);她的身体与名册、主人表在存档的 `SavedData` 里 |
| 玩家 × 世界 | 世界 `<存档>/numen/players/<玩家 uuid>/` | 会话成员表 `conversations.json`;权限规则在存档的 `SavedData`,不动 |
| 服务器 | `config/numen/server/` | `server.json`(总开关、各种上限、每人同伴数 `maxCompanions`)、插件开关(服务器上没有任何 key) |
| 本机(主人的电脑) | `config/numen/client/` | **她的家** `companions/<uuid>/`:收件箱、札记 `memory/`、token 台账 `stats.json`、绑定 `binding.json`(人设、模型档案、声线各是谁绑的与条目名;皮肤是对签名缓存的引用)、定时 `schedules.json`、旁路轨迹(开了才写);**库** `library/`(人设、模型档案、声线、技能、接进来的 MCP 工具,同一布局 `<库>/<命名空间>/<名字>`);钥匙串 `keys/`;`mcp/`(外部大脑的配置、令牌哈希、审计);`cache/models-dev.json`;签名皮肤缓存 `skin-cache/`;界面偏好、置顶、文件夹、草稿、已读、语音服务的 key |
| 外部大脑 | 外部 agent 那边 | 它自己的 key 与上下文;上下文从客户端日志派生 |

- **脑子的东西不在服务器上,也不会因为换服务器而不见;换一台电脑才会不见**:配置与记忆不跟着人换电脑;存档拷给别人,身体过去了,她不记得以前的事(ADR 0008)。服主看得到她的对话(记录在服务器上),看不到她的札记,也不替谁出模型的钱。
- **服务器不再有"服务器提供"的库**:技能、内置模块与插件登记的函数是服务端的东西,大脑经座位按需取(`catalog/get`、`skill/read`),不抄进主人的库;
  jar 自带的人设、模型档案、声线、MCP 条目放进主人的库(`Shipped` 同步清单,dpkg 对配置文件的办法:没被改过换成新版,改过的留他的、新版写在旁边 `<名字>.new`)。
  每种库在主人电脑上只有一个货架(`Library`、`Shelf`):自带的与主人自己写的在同一份里,没有"服务器提供/我的"两组;清单标出哪些是自带、改过、有新版,主人能采用新版、保留自己的或恢复默认。
- **存法:文件,不用数据库。** 存储分三层,每层只管一件事:
  1. **基础件 `store` 模块**:只依赖 Gson。只追加的日志 `AppendLog`(首行带版本的头;每条记录有稳定的 `id` 与 `parentId`;记录分类型,未知类型跳过但留在文件里;坏行跳过;换版本时整份迁移,先写临时文件再原子替换并留备份)、
     小文档 `JsonDoc`(JSON、带版本号、读时迁移、原子写)、原子写 `Atomic`、读写放哪个线程的 `Io`。
  2. **记录格式,各管各的**:对话日志的记录类型与怎么推出模型的上下文与面板的视图;收件箱条目;札记、库各自的结构。压缩是指针不复制,换模型换思考档位记成记录,插件的自定义记录不进模型上下文。
  3. **按归属组装**(`Homes`):每处一条写车道(`Lanes`),她的所有文件共用她那一条,按提交顺序落盘。
- **日志不写对话内容。** 服主与托管商看得到 `latest.log`,玩家求助时又常把日志传到公开网站;INFO 级只记编号与摘要,对话原文、程序源码、事件正文不进日志。
- **key 在钥匙串,不在条目里**:档案、声线、MCP 条目只写"用哪个服务商",key 按服务商存在主人电脑的 `keys/`;她的主人不止一位时,每项绑定在绑它的那个人看到的库里解析、用他的钥匙串
  ([ADR runtime 0006](adr/runtime/0006-keepers-ownership-use-provenance.md));别人绑的档案,其余主人只看得到名字。jar 里永远没有 key。
- **皮肤不是库**([ADR runtime 0005](adr/runtime/0005-skins-are-pngs-in-a-folder-signed-on-use.md)、[0009](adr/runtime/0009-skins-signed-by-the-chooser.md)):
  皮肤就是文件夹里的 png,文件名就是皮肤名,每台机器一个 `config/numen/skins/`。**签名是挑皮肤的人的客户端做的**:拿到原图(本机或服务器皮肤文件夹、网址、正版玩家名)
  → 按"图片内容哈希 + 粗细"(`SkinRef`)查这台电脑的签名缓存(`SkinCache`,`config/numen/client/skin-cache/`)→ 没签过就进这台电脑的签名队
  (`SkinSigning`:MineSkin,key 是这台电脑钥匙串里的 `mineskin`,没填走匿名额度;被限流按 `Retry-After` 等,最多同时 5 张在排;借正版玩家的皮肤本来就是 Mojang 签好的,不经 MineSkin)
  → 交给服务端穿上。整条流程是客户端的 `Wardrobe`(`ClientMachine` 持有)。**服务端只验签和穿上**:库协议 `skin` 的 `put`(她、引用、value、signature)是唯一入口,
  `SkinDresser` 用原版服务器已有的 Mojang 服务公钥(会话服务验 profile property 签名)验过才换身体,验不过或没有公钥就拒绝;`delete` 是脱掉。
  `skin-files` 是服务器皮肤文件夹的列表与原图。同伴身上记的是引用(`<哈希>-<粗细>`)。
- **库协议只剩服务端管的几样**(`Libraries`,包 `LibraryRequestPayload`/`LibraryPayload`):皮肤(`skin`、`skin-files`)、权限(主人的"不用问"名单与档位,`permission`)、插件花名册(`plugin`,开关只有管理员与房主能改)。
  她的大脑的配置(模型档案、key、人设、声线、技能、札记、定时、接进来的 MCP)都是主人客户端上的,不经这里。
- **绑定**:库条目的绑定(人设、模型档案、声线)是主人客户端的事,存在她家里的 `binding.json`,形状只在 `Bindings` 一处(`{"by": 绑的人, "id": "命名空间:名字"}`);服务端只在主人表变了时让被移出的人绑的几项退回未绑定(`CompanionBinding.releaseBoundBy`)。
- **召唤只有一个入口** `Companions.summonFor`:召唤卡、`/numen player summon`、外部大脑的 `create_companion` 都走它。名字合 MC 规则、不撞在线的别人、每人上限(`server.json` 的 `maxCompanions`,0 = 不限)。
- **面板导出与清空**:导出把当前对话记录(向服务端要来的原文,`conversation.jsonl`)与 `memory/` 打成 zip 存到主人选的地方(`MemoryExport`);清空删掉札记、长期目标,对话从一个新的会话重新开始,旧的记录留在服务器上。
- **本机文件**按 `Homes.clientDir()` 住进 `config/numen/client/`;旧位置的界面偏好(`ClientFiles`)照旧在启动时接过来。

**谁看得见她的话**:只给她的主人——回话回给说话的那一位:面板里的会话回在面板,命令切进的会话回在带 `[会话名]` 的聊天行,`/msg` 回私信(§二);面板上的动态她的每一位装了客户端的主人都收得到。
装了客户端的主人另有头顶气泡、聊天栏打字机与朗读(`SpeechBubbles`)。她不止一位主人时,`<query>` 的开标签上写明是哪一位说的(`from="player@短码 (名字)"`),
面板据此把别的主人的话画在左边、按人标名字和脸(说话人在她的主人表里认,`NumenRoster.speaker`)。

## 七、身体的输入层(已落地)

她是没有客户端的服务端玩家。真人手里的键盘、视角、鼠标、快捷栏,她都有,而且**只此一份、谁驱动她都用同一份**——寻路、Numen 的工具、
第三方插件、外接大脑的程序,最后都按这几样让她动。参照:Mineflayer 本体的 `setControlState`/`lookAt`/`dig`/`activateItem`、Carpet 的
`EntityPlayerActionPack`、Baritone 的 `InputOverrideHandler`——都是一层统一的"玩家输入",粒度就是真人能按的东西,寻路建在它上面。

全在 Numen API 的公开包 `com.dwinovo.numen.api.entity`,进瘦 jar:

```java
NumenPlayer her;
her.controls()  // 键盘:前后左右、跳、潜行、疾跑;impulse(x, z) 她自己这一刻给水平速度加的一份
her.look()      // 视角:at(点)、atNearest(碰撞箱)、turn(朝向)、faceToward(x, z),直接转到位
her.mouse()     // 鼠标:reaches(格 / 实体) 够不够得着;dig(格)/attack(实体)/release 左键;use(格, 面)/use(实体)/useItem/stopUse 右键;aim(格, 面) 与 intents() 这一下要问许可的意图;itemRayOn 桶自己沿视线打的那一条
her.harvest()   // 她的手挖出来的东西当场进背包;open() 开一本账,读这一趟挖到了什么、哪些放不下留在了哪
her.hotbar()    // 快捷栏:hold(格)、grip(东西),每次换了都交回 BodyAction
```

- **粒度就是真人的输入,只多一样。** 按键只能加减加速度,惯性让她停不准、拐弯侧滑;这几刻驱动她的一方用 `controls().impulse` 直接改水平速度
  (收脚的最后一刻、空中对准落点、拐弯,body 0010)。它和键一样每刻在物理步进里落一次;别的东西动了她的速度(击退、爆炸、被推)时让开,
  到身体重新有依托为止。竖直速度与位置不经这一层改。
- **组合不进这一层。** "挖掉那一格""放一块到那里"是使用者用这四件拼出来的。四件都是"一具服务端玩家 + 状态"的小类,
  普通假玩家也能 `new` 来用(寻路的 `TestBody`)。
- **她守服务端的规矩(body 0009、0011)。** 点哪一格、哪只实体由驱动者指名,够得着就点得中:够不够得着只有一个出处 `mouse().reaches`,
  就是原版服务端收包时查的那一条(眼睛到那一格、那只碰撞箱的距离在交互距离加一格之内),不查朝向、不查中间隔着什么。右键一格要给一个面:
  指名了用它,没指名用这一格朝着她眼睛的那一面(`Faces.toward`)。转头(`look()`)直接转到位,是给看着她的人看的;只有服务端真沿朝向算的
  几样读它——走路的按键、弓与掷物、桶自己沿视线打的那一条(`itemRayOn`)、飞行。手不缓:挖碎一格下一刻就挖下一格,右键每刻都能按;
  挖一格要花多久照原版逐刻累进度、由服务端确认。
- **每一下如实交回结果。** 左键交回 `Strike`(还在挖 / 挖掉了什么 / 被拒及理由 / 够不着没按);右键交回 `Use`(正挖着或够不着没按 / 按了:游戏接没接、
  世界变了哪几格、打开了什么界面 / 被拒)。点格子、点实体、只用手里的东西是同一个右键、同一种结果,`minecraft.use.*` 都从它写回执。右键按住(拉弓、吃喝、举盾)
  与左键按住挖一样归鼠标管。
- **挖出来的东西当场进背包。** 她的手挖碎一格(`ServerPlayerGameMode.destroyBlock`)那一段里生成的掉落物,结束时逐件走原版的拾取
  (`ItemEntity.playerTouch`:拾取事件、统计照常),放不下的留在原地;谁驱动她的手都一样,只在 `Harvest` 一处。背包满了那一声仍由
  `touchedItem` 发 `inventory_full`。本来就在地上的东西走过去才捡。
- **权限长在鼠标上。** 左键换到新的一格时问能不能拆;右键会往世界里放东西时问能不能放,否则问能不能用。要问主人时鼠标停下、交回 `Refusal.Asks`,
  由驱动者决定怎么问(寻路是走到那一格停下问);不许是 `Refusal.Denied`;服务端把挖掘退回来是 `Refusal.Server`(身体汇报,不是裁决)。
  判据只认身体是谁:是同伴就过权限层,普通假玩家照原版;别人自己 `new` 一个同伴的鼠标也绕不过去。
- **原版公式只有一个出处。** `DigTime`(挖掘进度,从 `DigTime.Mining` 算,不碰真身体也能算)、`Reach`(走到位的判据)、`Faces`(点哪一面、贴着哪一面放)、`Replaceable`
  身体与寻路规划共用;`Sight`(看不看得见)只答感知 `minecraft.scan.sight`;挑工具归 `ToolChoice.take`。纯规划的几何(`Footing`、`Stepping`、`Clearance`)与规划用的身体快照留在 pathing。
- **换驱动者时统一松手。** `CompanionBrain` 每刻只选一个驱动者(反射 > 同步 > 当前任务 > 空闲姿态),换人那一刻调完旧驱动者的 `stop` 就把键全松、
  挖掘进度清零、右键松开,新驱动者从干净的身体开始;任务与反射不各自松键。
- **寻路怎么接。** 身体端口 `Body` 留在 pathing,交出那具玩家与这四件,寻路直接用;`Ports` 里只剩寻路自己的策略。

## 八、语音

原版客户端录不了音、也放不了自定义音频,麦克风与喇叭都在玩家的电脑上,所以语音在客户端。**声线、出声与听写都在主人的客户端上。**

- **声线定义在主人的库里**:声线是一种库条目(服务商、音色、参数,不含 key),她用哪条记在她的绑定里。
- **语音输入**:客户端录音,用本机钥匙串里识别服务的 key 边说边转成文字,填进输入框,发出去就是一条普通的话。服务端看不到音频。
- **朗读**:大脑交出的回复文字片段(`Feed.Delta`)由本机的 `TurnPresenter` 分句(首句到第一个逗号就切)、用本机钥匙串里那家语音服务的 key 合成(预取两句)、从她身体的位置放出来;
  主人开口打断就硬停,她自己接着说就句界衔接。客户端报"在放音",身体据此看着主人。
- **语音服务的 key 在本机**(`config/numen/client/keys/`),各家语音服务的实现留在客户端。
- **只有主人听得到**(附近的人暂时听不到)。以后要让附近的人也听到,办法是主人的客户端合成后把音频传上服务端、转发给附近装了客户端的人。
- **以后可选的联动**:Simple Voice Chat 的服务端 API 能收玩家麦克风的包、能建以实体为声源的音频频道;做成 `plugins/` 下的联动,拿真模组验过再接。

## 九、多模态:谁来画她看到的东西

专用服务器没有渲染器,连方块贴图都没有。主流做法:

- Mindcraft:bot 进程里跑无头 3D 渲染(prismarine-viewer,three.js + WebGL 画布),从 bot 眼睛的位置画 800×512 的 JPEG,
  先交给视觉模型读成文字,再把文字交给主模型。
- BlueMap(服务端 3D 地图):服务端用 Java 从世界数据渲染;贴图在服主打开 `accept-download`(确认接受 Mojang 的 EULA、拥有正版)后
  从 Mojang 下载客户端 jar 取,不再分发;模组方块的贴图从模组 jar 里取。

试过服务端照 BlueMap 的取资源办法从她眼睛处画一帧(两轮原型):方块是数据,通用;实体与方块实体是客户端代码,只能逐个照抄,模组实体无穷多,维护不起。

定了(10-16,body 0004,暂缓):**画面交给装了我们客户端的主人那边画**,服务端请求、主人客户端把相机临时放到她眼睛处画到屏幕外的画布上、经上行分片传回;
**服务端只出"看见了什么"的清单**(视线锥内没被挡住的实体:类型、名字、距离、位置),主人不在场也能用。
主人不在线、没装客户端、或她不在主人已加载的范围里,就只有清单。排在输入管线之后。

## 十、安全:第三方服务器上谁防谁

她多半活在别人的服务器上,她的脑子在主人电脑上。三方各有要防的,分开说:

**1. 玩家防服务器。** 脑子在自己电脑上,这一层比以前简单得多:

- **key 不离开主人的电脑**:模型 key、语音 key、MCP 令牌都在客户端钥匙串里,不上服务器、不进座位;服主看不到她的对话与札记,也不替谁出模型的钱。
- 服务器看得到的只有身体这一头:她的背包、位置、她在聊天里说出口的话(原版服务端本来就把公共聊天明文写进日志)、程序与回执。
- **key 碰不到的地方**:不进日志、不进命令回执、不进模型上下文(提示注入问不出来);Lua 沙箱没有文件与系统访问,谁的 key 玩家的程序都读不到。
- **日志不写对话内容**(§六)。

**2. 服务器防玩家。** 玩家的程序送到服务端跑,没装客户端的玩家不能驾驶她(脑子在创建者的客户端上),但座位仍要防坏的客户端:

- 座位只认创建者的客户端;`program/run` 带的 keeper 必须在主人表上,`say` 的说话人也要核对;一个客户端狂发只会把自己的信箱塞满。
- 沙箱上限(指令数、字符串、时长)、每个主人同时几段、主线程每刻预算,都由服主可配;上行设带宽预算。
- 外部大脑的端点在主人本机,服务器不开端口;令牌高强度随机、只存哈希、可设过期、随时作废、带作用域;开着且绑在回环之外时界面与日志警告端点是明文 HTTP。
- 服主的总开关:能不能用 Numen、能不能用插件,各自一个。
- 接进来的 MCP 工具在主人自己的电脑上起进程,与服务器无关。

**3. 玩家防玩家。** 不让她成为搞破坏的工具:

- **她的命令权限就是替她做事的那位 keeper 的等级**(`Authority.commandLevel`,取 `NumenPlayer.keeperUuid`):主人是几级她就是几级,主人离线也照他的等级算,她自己在不在 op 名单里不起作用。
- 权限层的"归属"回答者:别人的东西拆不得、拿不得、打不得,主人点"允许"也解不开(`permission-layer.md` §二);动世界的事只由权限层裁决,工具与任务里不另设"许不许"的检查。
- 提示注入:只有主人(含 keeper)与群聊成员的话算命令,别人 `/msg` 她的话、QQ 与弹幕渠道进来的话都标着来源;模型就算被说动,动手也过权限层,越不过主人本身的权限,更越不过回答者的"不许"。

## 十一、以后:夺舍

主人下线时,用和主人同一个身份的假玩家顶替主人的身体干活。在这条管线里只是"换一个身体来源",渠道、收件箱、大脑都不变。要单独定:上线时的交接(防复制物品)、主人明确授权与范围、死亡与危险保护、服主开关、回来时完整交代做了什么。不在本方案里做。
