# Numen CLI:命令为底,工具是快捷方式

状态:设计稿(09-24)。第十三节第 1 步(铺底座)、第 2 步(三个联动插件)与第 5 步(原版指令入口)已落地,落地时定下的细节见第十六至十八节。

## 一、要解决的问题

- **工具数量只增不减。** 现在有 48 个自有工具:核心 39 个,联动插件 9 个(森罗厨房 3、车万女仆 2、YSM 4 个)。外部 MCP 服务借来的工具也挤在同一张表里。接下来要做 FTB Quests、Curios,以后还有更多模组。
  - 按"一个动作一个工具"的做法,FTB 光是查任务、看详情、提交、接受邀请就得加四个。
  - 工具定义每轮都随请求整张发出。
- **代价有三层。**
  - **token**:源码里的描述文字粗估有 1.5 万字符,还没算 JSON 结构和嵌套 schema 的开销。有 prompt 缓存,眼下这笔账不算重,但它随联动数量线性增长。
  - **注意力**:可选的工具越多,模型越容易挑错。
  - **扩展方式**:没有统一的扩展方式,每个联动都各自长出一批平行工具。
- **玩家要指令。** 有玩家反馈"Numen 不支持指令"。原版指令和模组指令本身就是现成的能力,只是没有入口。

## 二、主流怎么做

- **Claude Code**:一个通用的 Bash 工具,加上技能(技能写"什么时候、怎么做",具体动作交给命令行)。高频操作(Read、Edit、Grep……)仍然是独立工具,好处是定义常驻上下文,不用先查帮助,参数有结构,权限和展示也好做。
- **Anthropic 的"用代码执行调用 MCP"**:不把几百个工具定义塞进上下文,而是让模型按需发现、按需调用。
- **模型从训练数据里就熟悉命令行的写法**:子命令、`--help`、写错时报错里附上用法。

我们取的是其中的结构:**底层只有一套命令;高频的几条再包装成工具,作为快捷方式**。快捷方式和命令是同一件东西的两个入口,不是两套实现。

## 三、总体结构

```
模型
 ├─ 快捷工具 goto / mine / …        ← 常驻上下文,一步到位;由命令节点生成
 └─ numen 工具  "numen <命令行>"     ← 其余一切:查询、长尾动作、模组联动、原版指令
          │
          ▼
    命令调度器(Brigadier,Numen 自己的一棵树,不挂在服务器的 / 指令上)
          │  解析参数 → 找到节点 → 该节点唯一的处理函数
          ▼
    处理函数 ── 当场回结果(查询)
             └─ 交给任务队列(长活),结果照现在的回执机制送回

    numen mc <原版指令> ──→ 服务器自己的指令调度器,以她的身份执行,先过权限层
```

- **一个动作只有一个处理函数。** 快捷工具不拼出命令字符串再解析一遍,而是把已经解析好的参数直接交给同一个处理函数。
- **放在哪:**
  - 调度器、`numen` 工具、帮助、索引、快捷工具生成等机制放 `api`;
  - 原版命令放 `core`;
  - 模组命令放各自的 `plugins/*`。
  
  不另建顶层模块:命令要用 MC 的类型(物品、坐标、实体),而且"机制在 api、内容在 core"是架构铁律。

## 四、命令树

**一级命令**有两类:
- **领域**:`self`、`world`、`inv`、`gear`、`craft`、`go`、`build`、`memory`、`task`……,具体名字迁移时定。
- **模组 id**:`ftbquests`、`curios`、`kaleidoscope`、`tlm`、`ysm`……

一级命令只有当前实际装了的才出现。

**二级起是动作**,参数用 Brigadier 的参数类型,尽量复用原版现成的类型:物品 id、方块坐标、实体选择。

```
numen help                      列出一级命令,每个一句话
numen ftbquests --help          列出这个命名空间的动作与用法
numen ftbquests list
numen ftbquests show <任务>
numen ftbquests submit <任务>
numen ftbquests join
numen self status [片段]        片段见第七节
numen gear wear <物品> [槽位]
numen mc <原版指令…>
```

**约定:**
- **帮助**:任何一层都能 `--help`。用法和说明直接取自注册时写的文字,这是语法唯一的来源。
- **写错时**:报错里带上那一层的用法。模型写错了一次就能改对,不用再单独查一轮帮助。Brigadier 本身就会给出最接近的用法。
- **输出**:给精简的文本,不给大块 JSON。列表类输出默认有上限,带 `--page`;超出上限时告诉她还剩多少。
- **命令名**:用英文小写。模型对英文命令最熟,也和工具名的约定一致。

## 五、快捷工具与命令同源

一个命令节点在注册时可以声明"提升为快捷工具":

```java
numen.registerCommands("go", "Getting around.", go ->
        go.server("to", "Travel to one destination.", Go::to, X, Y, Z, SPEC)
          .promote("goto", "Travel to ONE new destination …"));   // 工具名与描述
```

(落地时改成了 Numen 自己的一层登记写法,由它生成 Brigadier 树,理由见第十六节。)

- **工具 schema 由节点生成。** 节点的参数名、类型、是否可选,直接映射成 JSON schema,不另写一份。改了命令,工具跟着变。
- **调用快捷工具就是执行那个节点。** 工具收到的 JSON 参数按同一组参数类型转换,再交给同一个处理函数。
- **回执同一份。** 模型从哪个入口调,拿到的文字都一样。
- **提升哪些,按数据定。** 先从现有对话记录里统计各工具的调用次数,高频、每几轮就要用一次的才提升。预计是移动、挖掘、攻击、收集、合成、写计划这一类。
- **难点是嵌套参数。** 比如 `goto` 的 `spec` 是个对象。命令行里有两种表达:
  - 拆成一组 `--avoid water --alter natural` 这样的标志;
  - 用一个 JSON 参数类型 `--spec '{…}'`。
  
  拆成标志更像命令行,也更好生成 schema,但要逐个对照现有字段。见第十四节。

## 六、在哪一侧执行

- **服务端**:动身体、读世界的命令,绝大多数属于这类。
- **主人客户端**:只有客户端才有的数据或逻辑,比如写计划、记忆,以及 FTB 按主人的游戏语言读任务书。

每个节点声明自己在哪一侧执行。命令树在两侧用同一份公共代码注册,所以:
- 客户端能当场给出帮助和解析错误,不必跑一趟服务端;
- 客户端节点当场执行;
- 服务端节点照现在身体工具的做法,经 `ServerToolTransport` 送过去,在服务端再解析、执行,结果走原来的回执。

**同一个命名空间里两侧可以混着。** 例如 `ftbquests list` 在客户端读(为了本地化),`ftbquests submit` 在服务端执行。

## 七、扩展点

原版命令本身就通过接口干活,原版实现是这个接口的第一个提供者,不写"原版先试、不行再问模组"。开扩展点的判据不变:**动作已有、模组只是增加名词、意图不变**。形态有四种:

1. **注册表**:最先看这一条。原版读的注册表(物品、配方、结构、生物)模组本来就在往里写,这种情况根本不用开扩展点。`numen craft` 天然认得模组配方。
2. **行为提供者**:同一个动作、多个来源。例子是 `gear wear`:原版四件甲和 Curios 饰品栏都是 `GearSource`,见 `docs/curios-gear-slots.md`。
3. **输出片段**:同一个查询、多家往里加。例子是 `self status`:
   - 输出由带名字的片段拼成,由原版的生命、装备、效果,以及插件的队伍、任务摘要等组成。
   - 这就是现有的 `contributeBodyState` + `joinFragments`,一个插件出错只丢它自己那一段。
   - 可以只看其中一段,例如 `numen self status worn`。
4. **名词解析器**:动作不变,能指的东西变多。例子是 `go <地点>`:原版能解析坐标、"主人"、"床",装了地图联动后多一个 `PlaceResolver`,能认路标。

**规矩:**
- **插件不能往原版命令树上嫁接子命令。** 它要么在自己的命名空间里加新动作,要么实现原版命令留好的接口。随意嫁接会撞名,同一件事也会长出好几种写法。
- **扩展点是 api 里有类型的 Java 接口,经 `NumenApi` 登记。** 命令只调用接口,不认识任何具体模组。
- **帮助跟着提供者走。** 例如 `gear wear --help` 列出的槽名,就是所有提供者此刻给出的槽。
- **按真实用例一个个开,不预先铺空接口。**

判据的另一半同样不变:**同一件事只留一个入口**。CLI 让"新动作"不再多花工具的钱,但把"穿戴"拆成 `curios wear`、`trinkets wear` 仍然是错的:模型得先猜这件东西归谁管,"身上戴着什么"也得分几处问再自己拼起来。

## 八、原版指令入口 `numen mc`

- **交给服务器自己的指令调度器,来源是她的 `CommandSourceStack`**:
  - 权限等级就是服务器给她的等级。她是 OP 才能 `/give`,这是服主的决定,我们不放宽也不收紧。
  - 模组的玩家指令(FTB Teams 的 `party join`、YSM 的换模型指令)天然就能用。YSM 联动现在本来就走指令。
- **执行指令本身是一种动作,由权限层裁决。**
  - `Action.Kind` 新增 `COMMAND`,规则按指令的根名来写(比如允许 `msg`、`trigger`,凡是 `setblock`、`fill`、`tp` 都问)。
  - 没有规则覆盖的就问主人,和别的动作一样。代码里不写死任何"安全指令"名单(见 `permission-no-tool-special-casing`)。
- **指令的回显原样返回给模型。** 指令造成的身体变化照样要让她知道:背包、位置的变化下一轮会出现在状态里;指令本身的回显就是这次调用的回执。
- **帮助**:`numen mc --help` 列出她此刻有权执行的指令用法,由服务器调度器按她的权限等级生成。
- **"想让她会用某条指令"只需要写一个技能**:技能写什么时候用、怎么用,不用写代码。

## 九、提示词与技能

- **一行索引**:系统提示里放已安装的一级命令,每个一句话。
  - 内容在启动时生成、排好序;只有模组增减时才会变,不打碎 prompt 缓存。
  - 模型不用先 `numen help` 就知道有哪些命名空间。
- **技能管"什么时候、怎么用"**,附一两个例子。**语法只在帮助里**,技能不抄一遍用法。
- **快捷工具的定义照旧常驻。** 它们的描述也从命令注册处来。

## 十、外脑(MCP 模式)

外脑看到的是同一批快捷工具,加上一个 `numen` 命令入口。不再维护第二套工具清单。

从外部 MCP 服务借来的工具是否也收进命名空间(`numen mcp <服务> <工具>`),见第十四节。

## 十一、不变的东西

- **权限层按动作裁决。** 无论从快捷工具进还是从命令进,最后落到身体上都是同样的动作,走同一个 `Permission`。
- **知情权。** 身体发生的事照样作为回执、事件、状态报给模型。
- **任务槽、回执、打断、叫停机制不变**,长活命令返回"开始了"。
- **GameTest 仍然从入口调用**,只是入口换成命令调度器和快捷工具这两处。

## 十二、测试

- **快捷工具 schema 生成**:单元测试逐个核对"节点参数 ↔ schema 字段"。
- **帮助快照**:单元测试。帮助是模型读的界面,措辞变了要能看到。
- **同源测试**:GameTest 里同一件事分别从快捷工具和从命令调用,回执与世界结果完全一致。
- **原版指令**:
  - 没有权限时如实失败;
  - `setblock` 一类在没有规则时会问主人;
  - 回显完整返回。
- **迁移期**:每迁一批,原来覆盖这些工具的 GameTest 改成从新入口调用,断言不放宽,全绿再往下走。

## 十五、不做的

- **不做 shell**:没有管道、变量、重定向。它是一张命令表,不是解释器。
- **不做嫁接**:插件不往别人的命令节点下挂东西。
- **技能里不抄语法**。
- **不为"以后可能要"预先开扩展点**。

## 十六、第 1 步落地时定下的细节

代码在 `api` 的 `com.dwinovo.numen.cli` 包。

- **登记写法不是裸 Brigadier。** 插件经 `NumenApi.registerCommands(组名, 一句话, 组 -> …)` 拿到自己的 `CommandGroup`,往里加 `Action`,参数用 `Param` 与 `ArgType` 声明;Brigadier 树由这一层生成。
  - 原因:帮助的说明、执行侧、可选标志、schema 都要挂在节点上,Brigadier 的节点没有这些位置;裸 builder 还能 `redirect` 或拿到别人的节点,"不许嫁接"就只能靠约定。
  - 插件手里只有自己那一组,够不着根和别的组;组名、动作名、参数名、快捷工具名撞了或不合规,都在登记的那一刻抛出。登记块返回后这一组封口。
  - 引擎自带的 `task` 组也经这扇门登记(`TaskCommands.install`),由 core 在原来三个工具的位置调用,工具表顺序不变。
- **一行命令以 `numen` 开头**:`numen` 工具的参数 `command` 是整行,如 `numen task status`。帮助里的每一行都能原样照抄。
- **层级只有两级**:组 → 动作。设计里没有更深的需要,没做嵌套组。
  - 一组也可以直接就是一个服务端动作(`CommandGroup.serverDirect`):参数紧跟组名,没有动作名,`numen mc <command...>` 就是这样。这样的组不能再有具名动作(具名动作会和它的参数抢同一个位置),登记时就查;它的 `--help` 与写错时附的用法都是这个动作的帮助。
- **帮助可以接一张服务端目录**(`Action.catalog(标题, 源 -> 条目)`):只有服务端按这具身体此刻的样子才答得出的条目(`numen mc --help` 列她能用的原版指令)。客户端解析到这种帮助时把调用原样送去服务端,那边算出来,和组的列表一样每页 20 行、认 `--page`。
- **参数**:必填的是位置参数,按声明顺序;可选的是标志 `--name value`,顺序随意。标志名就是参数名、也就是 JSON 的键。
  - 标志只有一种机制:位置参数之后挂一格 Brigadier 参数节点(`FlagsArgument`),它读到行尾,逐个认标志名,值交给那个参数自己的类型在同一个读头上读。所以出错位置是整行里的真实位置,用法照样附上。
  - 每个标志都带值(布尔也写 `--x true`),分隔都是一个空格,和 Brigadier 分隔位置参数的规矩一致;写重、缺值、没声明的标志各有一句报错。
  - 吃掉余下整行的 `text` 只能是最后一个必填参数,且这个动作不能再有标志。
- **参数类型**第 1 步开了三种:`integer(min, max)`、`word`、`text`;第 2 步补的见第十八节。要新的,就在 `ArgType` 加一种。
  - `integer` 的范围写进 schema 与帮助,读的时候不拦越界值:夹住还是拒绝、回执里怎么说,是动作自己的语义(`task timer` 夹住并说明你要的和实际定的)。
  - 快捷工具的 JSON 值取字面文字,交给同一个 Brigadier 类型整段读完。没声明的键拒掉;JSON `null` 等于没给。
- **帮助是树上的普通节点**:根下的 `help` 与 `--help`,每组、每个动作下的 `--help`,和别的命令同一次解析认出来。组与根的列表每页 20 行,`--page N` 翻页,超出时说还剩几条、怎么翻。
  - 分页只有一份,是公开的 `Listing`:动作自己列的清单(如 `ftbquests list`)把 `Listing.PAGE` 登记为参数,处理函数把读好的参数交给 `Listing.result`,每页行数、翻页提示、越界的说法都和帮助一样。
- **报错**:Brigadier 的报错原文加上出错那一层的帮助(根、组的第一页,或动作的完整帮助)。某一层连一个候选都对不上时(组名、动作名写错)报"未知命令"而不是"参数不对"。
- **回执**:命令与快捷工具都回 `TaskResult` 的 JSON,帮助是一条成功回执,解析错误是一条失败回执。
- **执行侧**:两个处理函数接口 `Action.OnServer` 与 `Action.OnClient`,登记时选哪个就是哪一侧。
  - 客户端先解析:帮助、解析错误当场回,客户端动作当场执行;服务端动作把这次调用原样经 `ServerToolTransport` 送去服务端,那边再解析、执行。
  - 服务端收到客户端动作如实拒绝。专用服务器上客户端动作照样登记(帮助要它的说明),处理函数永远不会在那里被调用。
  - 快捷工具提升自服务端动作时,调用照身体工具的路子直接送服务端,参数在那边读,读错的回执与所有身体工具同一种说法。
- **长活**:`ServerSource` 带着这次调用本身(`toolName`、`args`:快捷工具名和它的 JSON,或 `numen` 和 `{"command": …}`)。长活交 `TaskDispatch.setTask(source, record)`,重启后的重放记的就是这次调用,走同一个入口再来一遍。任务叫什么见第十八节。
- **一行索引**:`NumenCli.index()` 生成 `<commands>` 块,组按名字排序,挂在系统提示的技能表之后;只随组的增减变。
- **`numen` 工具由引擎在 `CommonClass` 登记**:插件的命令只依赖引擎,谁登记了命令都指望这个入口在。外脑(`NumenActuator` / MCP)读的就是同一张工具表,自然看到 `numen` 与各快捷工具。

## 十七、第 5 步落地时定下的细节

代码:命令组在 core 的 `McCommands`,执行是任务 `McCommandTaskRecord` / `McCommandCompanionTask`;权限层的动作是
`Action.command`,规则写法见 `docs/permission-layer.md` 的"指令"。

- **形状**:`numen mc <command...>`,组直接就是这个动作(第十六节的 `serverDirect`),余下整行是指令,前导 `/` 可有可无。
- **先解析,写不通当场失败,不打扰主人**:按她的 `CommandSourceStack` 在服务器指令树上做一遍执行前的同一道检查
  (解析完、没有剩下的字、走到能执行的节点)。写不通时说清是哪一种:没有这条指令;服务器不让她用这条(根节点对她的
  来源不可用,她不是 OP 就没有 `/give`);参数写错——Brigadier 的原话加上这条的用法(`getSmartUsage`)。这几种不进任务槽。
- **执行是任务槽里的一次同步短任务**(`runSync`,期限 5 秒,等主人答复的刻不计):动手前把 `command(整行)` 交给权限层
  (`permit`),要问就走现有的征询,和 `drop_items` 同一套;放行才执行。
- **执行走服务器自己的入口** `Commands.performPrefixedCommand`,和玩家在聊天栏里敲的同一条路,加载器的指令事件照常触发
  (别的模组在那里拦或记指令)。来源就是她的 `CommandSourceStack`(权限等级、位置、`@s` 都是她),只把回话的去处换成
  一个收集器:
  - 成功与失败的回话都收下。原版按 `sendCommandFeedback` 决定给不给人看,那是聊天栏的开关,回执不是聊天栏。
  - 要不要知会别的管理员照她的身体来(服务器的审计,不因换了去处而变)。
  - 成败以执行完的结果回调为准:分叉的指令每一支回一次,有一支成功就算成功,返回的数相加;解析不通、抛异常、被模组
    拦下时没有回调,就是没跑成。
- **回执**:成功是 `ran /<整行>: <回显>`,失败是 `/<整行> failed: <回显>`,一句一行,没有回显写 `(no output)`;`data` 带
  `command`、`output`(逐句)与 `result`。主人点过头的,回执末尾照任务基类的规矩交代。指令对她身体做的事(背包、位置)
  不另报,下一轮出现在状态里。
- **帮助**:`numen mc --help` 是动作帮助接一张服务端目录(第十六节的 `catalog`):服务器此刻按她的来源给出的
  `getSmartUsage`,每条指令一行 `/用法`,按字母排,每页 20 行。客户端解析到它时送去服务端算。
- **征询卡**:动词"执行 / run",名字是 `/整行`,没有图标;一行放不下时名字截短。"以后都允许"记下的是
  `allow command(她打的根名)`。
- **提示词**:只有组的一句说明进 `<commands>` 索引;没写技能(想让她会某条指令时再写)。
- **没做**:YSM 联动改走 `numen mc`(另一件事);任何写死的指令白名单或黑名单。

## 十八、第 2 步落地时定下的细节

三个联动插件的工具全部改成命令,都不提升(插件工具是长尾);旧工具类删掉,描述拆成组说明、动作说明、参数说明写在各插件的 `*Commands` 类里,技能里只留命令的例子。

| 旧工具 | 命令 |
|---|---|
| `kc_recipes` | `numen kaleidoscope recipes <cookware> [--have_only] [--name]` |
| `kc_inspect` | `numen kaleidoscope inspect <x> <y> <z>` |
| `kc_cook` | `numen kaleidoscope cook <x> <y> <z> <recipe>`(长活) |
| `list_maid_models` | `numen tlm models [--search]` |
| `wear_maid_model`(给 model) | `numen tlm wear <model>` |
| `wear_maid_model`(model 留空) | `numen tlm remove` |
| `list_ysm_options` | `numen ysm options` |
| `switch_model` | `numen ysm switch <model> [--texture]` |
| `play_emote` | `numen ysm emote <animation>`(`stop` 停下,照 YSM 自己的写法) |

- **"留空表示另一件事"拆成两个动作。** 工具贵,才把穿和脱塞进一个参数;命令不花工具表的钱,一个动作一个意思。
- **`ysm switch` 是任务槽里的一次同步短任务**(`runSync`,和 `numen mc` 同一种):成败以回读她身上穿的为准,回读之前 YSM 的命令必须已经执行完。原版的指令在另一条指令的执行当中被调起时排到那条之后(控制台、`/numen debug`、`/test` 调进来的都是这样,生产专用服上实测回读早于 YSM 设上),任务在服务器刻里跑,不在任何指令的执行当中,命令当场执行完。没换成时把 YSM 对这条命令说的话原样带回。
- **新参数类型**:
  - `integer()`:不设范围的整数,方块坐标用。
  - `bool()`:`true` / `false`,当标志也要写值。
  - `id()`:资源 id,读成 `ResourceLocation`;字符集与合法性用原版 `ResourceLocation` 自己的规则,不写命名空间即 `minecraft:`。配方、女仆模型用它。
  - `string()`:一个值,到空格为止的任意字符(中文、`/`、大写都行),带空格就加引号。模组自己起的名字(YSM 的模型文件名、动作名,女仆包的角色名)用它,这些名字的字符集不归我们定。
  - 动作帮助里每个参数都写出类型的完整称呼,必填的 `<model> (string, quote it if it has spaces)`,可选标志的 `--texture <string> (string, quote it if it has spaces; optional)`:"带空格要加引号"跟着类型走,哪个参数用了 `string()` 都有。
  - JSON 进来的值写成它在命令行上的样子再读:多数类型就是字面文字,`string()` 一律加上引号——JSON 的字符串本来就有边界,否则带空格的名字命令行收、JSON 拒。
- **任务叫什么**:任务记录、受理回执、`task_finished`、`<current_task>` 写的名字是 `ServerSource.taskName()`:从快捷工具进来是快捷工具名,从 `numen` 进来是"组 动作"(如 `kaleidoscope cook`)。解析到动作、交给处理函数前,源对象先绑上那个动作。
  - 命令派的活用 `TaskRecord(ServerSource, deadline)` 起记录,名字与调用 id 都取自源;交 `TaskDispatch.setTask(source, record)`。
  - 记录的名字不是能重放的工具名,所以重放记的是那次调用本身(`numen` 与那一行命令)。工具派的活照旧 `setTask(companion, record, args, reply)`,记录以工具名命名,重放按这个名字找回工具。
  - 落盘时名字与重放的调用一起记下(`CompanionRegistry.Entry` 的 `taskName`,取自受理时的记录):重启后接不回来,`task_finished` 用的就是这个名字,和受理时她看到的一样。
- **客户端动作的插件也在两侧登记命令**:`tlm` 的三个动作都在主人客户端执行,命令组照样在 `NumenPlugins.register` 块里直接登记(专用服务器上只为帮助),插件原来放在 `onClient` 里的登记工具那两行随之删掉。
- **工具表的账**(字符数粗估,英文约 4 字符一个 token、中文一字一个):8 个旧工具定义约 4500 字符、约 1350 token;换成 `<commands>` 里三行,约 250 字符、约 60 token。三个插件都装时每轮少发约 1300 token。
