# 群聊:会话就是一张成员表

状态:设计稿(2026-09-21),第一步已落地。与 `architecture-mind-model.md` 的收件箱(§四)、
唤醒经济学(§三)一脉相承,落地时按 §十二 修宪。界面部分照 `ui-design-rules.md`。起因是 #34。

## 一、问题

今天两只 Numen 站在一起,彼此是哑的。仓里没有任何同伴↔同伴的通道。

但"多只同伴"本身已经成立:名册、每同伴一个家、每同伴一个收件箱、每同伴一条循环,
都是现成的。缺的只是"她们能不能听见彼此"。

直接让她们互相说话是最自然的想法,也是所有同类实现踩坑最深的地方——两个 LLM 互相
回复没有天然的停止条件,而每一轮都是两份账单。真正的代价不是钱,是**主人失去了对场面的
控制**:他插不进去,也不知道什么时候能插进去。

## 二、不变量

整篇设计只有一条,其余全是它的推论:

> **唤醒只能由人产生。同伴说的话永远只是上下文,不产生唤醒。**

这不是"加了限制所以不会失控",是**失控没有路径**:每一次模型调用都能追溯到一次主人的
敲击。于是下面这些别人必须做的东西,我们一个都不用做——

| 别人的补丁 | 我们为什么不需要 |
|---|---|
| 轮数上限(`max_round`/`max_turns`) | 没有"一轮讨论"这个东西要终止 |
| 选发言人的额外 LLM 调用 | 主人点名就是选人 |
| 互聊冷却计数器 | 同伴的话不唤醒任何人 |
| 失速/循环检测 | 循环需要两端都能自发,这里只有一端 |
| 忙/闲四象限 + 要不要插话的判断 | 没被点名就不醒,不存在插话 |

代价是主人要当路由器。这不是代价,是目的。

## 三、会话就是一张成员表

> **一个会话 = 一张成员表(+ 主人起的名字,可选)。**

全仓只有这一个概念。**单聊是成员表长度为 1 的会话**——不是"一只同伴 <i>或</i> 一个群"两种
东西,不是"单聊变成群"的状态迁移,就是同一个东西人数不同。

于是:

- **左栏列的是会话,不是同伴。** 头像按成员的脸拼:一个人就是她的脸,三个人就是叠三张脸。
  同一条规则,没有两种图标。
- **没有"建群"这个动作。** 只有"往这个会话里拉人"——拉进第二个人,它自然就是多人会话。
- **停止 / `@` 路由 / 面板 / MCP 全都只对会话操作**,没有一处问"这是单聊还是群聊"。
  单成员时这些式子自动退化成今天的行为——不是加了一条单聊分支,是单聊本来就是这个式子的特例。
- R 选、Y 说、V 语音三件套一行不改:它们本来就只认"当前交互对象"。

**落盘按需,不按人数。** 主人改过它(拉了人、改了名)才存;没动过的不存。措辞很要紧——
不是"因为它是单聊所以不存",是"**没人动过它所以没东西存**",这条规则对所有会话一视同仁。
读的时候有持久记录就用,没有就现构一个。

遣散之后成员表不改:留着死 UUID,显示时按名册过滤。群因此只剩一个人(或没人)时随即解散——
成员表只剩她,就和她的私聊是同一张,留着就是左栏两格指向同一个大脑(见"遣散之后")。

## 四、谁醒:`@` 谁谁回,不 `@` 全体回

每句话各算各的,会话不记"上次点了谁":

```
@小柚 去挖铁        → 只有小柚醒
多挖点               → 没点名 = 说给大家的,三只都醒(小柚也在其中)
@小柚 @阿岚 一起去   → 两只醒
@阿岚 你去砍树       → 只有阿岚醒
```

试过"话头粘住"(点了谁,之后没点名的话还是她回),被否掉了:点名只是那一句的事,下一句
不点名就是广播,这才和 `@` 在别处的直觉一致。想让她一个人接着回,再打一次 `@` 就是,输入行
会补全、整块删。

**一句话里没有 `@`,全体都醒。** 这不是兜底,是和说话意图对上的:没点名的话
通常本来就是说给全体的("我回来了"、"天黑了"),而派活的时候人自己就会打 `@`。N 只醒仍是
N 次唤醒对**一次**敲击,不变量不破。

代价老实写在这:**两只可能同时接同一件活**。你说"去挖铁"忘了打 `@`,两只都应一声、都跑去
同一个矿。浪费的不是 token,是你得再说一次。两个天然的缓冲——说话规则本来就压着她们
"活干完或失败、有危险、有真问题才开口",以及先醒的那只说的话会进后醒那只的上下文——
前者靠谱,后者几乎同时醒时不保证。**不为此加调度**:最坏是重复一趟,而为它加一层协调
机制,就等于把 §二 省掉的东西又捡回来了。

### 解析

`@` 在**客户端注入时**解析成收件人 UUID,不是留给模型去读的字符串。

判据是成员的名字,不做子串匹配——名字互为前缀会误判(`@Anna` 里含着 `Ann`),所以长名字
先匹配、吃掉的那段不再参与,且 `@` 后面那个名字必须整个对上。

**两只同伴重名时,喊那个名字把她们都喊上。** 召唤不拦重名,而"按成员顺序挑第一只"挑中谁
取决于建群时勾选的先后——主人看不见那个顺序,也就无从预料谁会应声。宁可两只都来。

## 五、落到现有骨架

宪法 §四 已经把这件事准备好了:**一种事件的一切写在类型表的一行里**。群聊需要的两种投递,
一种是现成的,一种是新加的一档:

```
醒的     → query,恒为急件,STEER,立刻开轮          (现成)
旁听     → talk,AMBIENT,进队列但不参与熟度 (新加)
```

`Delivery.AMBIENT`(捎带)的语义:回合进行中与 `STEER` 一样在下一个边界注入;闲着时
**不参与熟度判断**——它自己不值得把她叫醒,躺着等下次别的事叫醒她,跟着那一轮一起走。
因此旁听是**免费**的:不额外唤醒就不额外花钱。

**这一档的条目永不为急件,在 `EventQueue.push` 一处写死。** 不变量靠发送方自觉守不住,
就不给发送方留口子。

所以这是**一个新的事件类型 + 一档新投递,不是一套新系统**。服务端唯一发出口仍是
`NumenEvents.emit`。

## 六、旁听者看到什么

旁听到的话是**世界上发生的一件事**,走 `<event kind="talk">`,和任务收尾、挨打这些排在
同一条时间线上:

```xml
<events>
<event kind="talk">[主人 → 小柚] 去挖点铁</event>
<event kind="talk">[小柚] 好,我去东边那个矿洞</event>
</events>

<query>@阿岚 你去砍树</query>
```

**不另开一个 `<talk>` 块。** 渲染是按 `Type.fromOwner` 这个布尔分两堆的,要第三堆就得在
`Type` 上再加一个与它重叠的字段——那是多源。混在 `<events>` 里还白捡一条:旁听的话和世界
的事在同一条时间线上按时间排,模型读到的是连贯的。

**每行必须带发言人前缀。** 模型上下文里只有 user/assistant 两种角色,三方以上的场面里
**所有"别人"会塌缩成同一条无法区分的流**——B 分不清那句是主人说的还是 A 说的。AG2 为此
专门做了一种带名字的视图,并在源码注释里点明了这个原因。

**共享的是说出口的那句话,不是整个回合。** A 的工具调用、思考、回执都不进 B 的上下文:
既贵又没用。

她自己说的话不推给她自己——那已经在她日志里了,再推一条就是第二个出处。

### 她得知道谁听得见

她的上下文是**一条流**:单聊里说的、群里说的、旁听到的,全混在一起按时间排(§七)。
所以不告诉她场合,她会漏嘴:

```
[单聊]  主人:别告诉阿岚,我想给她做个礼物
...
[挖矿队] 主人:@小柚 今天干嘛
         小柚:主人在给阿岚准备礼物呢      ← 她不知道阿岚听得见
```

**不告诉她谁在场就指望她守口如瓶,是我们的错不是她的错。** 这是知情权的正例,和
"身体动了得让模型知道"同一条规矩。

所以注入多人会话的话时要带上场合:**还有谁在听**,以及**她的回答谁会听见**。单人会话
不带——没人听得见,说了反而是噪音。

配套要在系统提示词里加一层(和札记的规矩同一个位置),说清三件事:这个场面上还有谁、
你说出口的话她们听得见、**你可以提到别人但她们不会因为你说话而醒**——要让谁做事,得主人来说。
第三句不写的话,她会说"阿岚你去西边"而阿岚根本收不到,看着像协作,其实是自言自语。

### 没有"模式"这个开关

"谁听得见"只由成员表定,没有第二个来源。想只跟小柚说,就去她那个会话说(左栏点她,
或准星对着她按 Y)——那不是群里的"私聊模式",是一个成员更少的会话。"让大家都别回"没人
提过需求,不做。早先这里列过一张"群聊 / 私聊 / 全员静默"的推演表,那是在验证不变量,
不是待办;加一个 mode 字段就是给"谁听得见"开第二个口子。

## 七、记录:存储按人,视图按会话

**一个人一本日志,会话没有自己的日志。**

她只有一本,因为她只有一个脑子、一条时间线:单聊里你说的、群里你说的、她旁听到的、
世界事件、她自己的回复、工具调用——全在一起按时间排。她不活在两个聊天窗口里。

反过来做(一个会话一份)会更糟:她的**模型上下文必须是一条流**,于是发请求前又得把 N 本
合起来,而工具调用、压缩摘要这些不属于任何会话的东西没地方放。问题只是从显示侧搬到了
模型侧,而且搬到了更要命的那一侧。

### 说出口的话带一个会话标记

一本混合的日志切不出"挖矿队的记录"——你私下跟她说的话会漏进群视图。所以:

```
一个人一本日志(她的全部经历,一条时间线)
  └ 说出口的那些行,各自带一个"属于哪个会话"的标记

一个会话的记录 = 所有成员日志里带着这个标记的行,按时间归并
```

**只有说出口的话需要标记**:主人说的、她说的。工具调用、世界事件、压缩摘要都不进聊天视图,
不需要。`ConvoLog` 的记录本来就允许可选元数据(现在有 `ts`),加一个同族的字段,老版本
读到不认识也不会丢。

标记怎么来:

- **主人说的** → 他此刻在哪个会话里说的,就标哪个
- **她说的** → 标她**被哪个会话叫醒**的那个。世界事件叫醒她时沿用上一个——那件活本来
  就是那个场面派的

这个"她当前在哪个会话里"是整套设计**唯一新增的状态**,住在 `EntityAgentLoop` 上。它有两个
用处:决定她的话推给谁听,以及这句话记在哪个会话名下。

### 归并

```
1. 从每只成员的日志里取带本会话标记的行:她自己说出口的话、主人说的话
2. 旁听条目(talk)跳过 —— 那是转述给她听的,不是原始记录
3. 主人的话按(会话 + 发言号 + 原文)去重
```

第 3 条为什么不用时间戳:主人的一句话被复制进每个醒着的成员的日志,**各自盖各自的时间戳**
(各自的循环各取一次 `currentTimeMillis`,忙着的那只还要等到下一个边界、和别的事件拼成
一条才落盘),差几毫秒到几秒都有;原文又可能重复("好"说两遍)。拿时间去判"同一句"只能
定窗口,那是猜。

**发言号**(`Conversation.turn`)是 `say` 送话之前拨一次、落盘一次的计数:同一句话的 N 份
副本号相同,两句不同的话号不同。它随每份副本一起进日志——挂在 `<query>` 后面那行
`<audience turn="17">…</audience>` 上,旁听行也带。键里加原文是为了斜杠命令:命令不经
`say`、不拨号,只靠号会和上一句撞;原文一并比就分得开。

`say` 整个作为一个单元在主线程上跑:拨号、定场面、送话之间插不进第二句。语音转写在别的
线程回调,要是各自往主线程排队,连说两句就可能共一个号——这是时序上堵死,不是概率上。

底子是牢的:`ConvoLog` 是 append-only 的,压缩只换掉"发给模型的那份视图"
(`load`),`loadDisplay` 是完整的物理记录,一条不少。归并就是调 N 次现成的 `loadDisplay`。

**归并要写成一个函数,面板和 MCP 外脑用同一个。** "这个会话发生了什么"是一个读取问题,
不是存储问题;只要出口只有一个,外脑那条线就不必另起炉灶。

### 为什么不给群一份自己的记录

试过在纸上推,结论是**现在不做,但以后加得上**:

- 加一份群记录 = 加一个订阅者,从那天起开始记,**很便宜**;
- 拆掉一份已有的群记录、改回归并、还要处理两条显示路径,**很贵**。

不知道未来的时候选可逆的那个。而且群记录会破掉一条现有的不变量:
`CompanionHome` 的"遣散 = 删一个目录,不需要任何清理代码"。

### 遣散之后

遣散 = 删掉 `companions/<uuid>/` 这一个目录。于是:

- **她的日志没了** → 面板归并时她那几行缺席,那段对话看起来少一边
- **别人的记忆不缺** → 旁听到的行早就进了其他成员的日志,阿岚仍然记得小柚说过什么。
  她当时真的听见了,不该因为小柚走了就当没听过

缺口不遮掩:**遣散时给同会话的其他成员推一条事件**("小柚离开了"),让缺口有个解释。

**只剩一个人的群随即解散**,走的是主人点垃圾桶的同一条路(`Conversations.dissolve`):记录删掉,
群里说过的话仍在各成员的日志里(界面上不再有显示它的视图),还站在这个场面里的那只退回私聊。
判断只在"她被遣散"这一刻做(`Conversations.left`):会话记录是全部世界共用的一份,名册只是当前世界的,
拿名册去扫全部会话,会把别的世界的群当成没人了。

哪天觉得面板上缺一边碍事,可以让转述在原始记录缺席时顶上(按时间 + 说话人合并),
代价是转述得带上逐行时间戳。**这一层是可加的,不是现在就得决定的。**

## 八、入口与界面

### 8.1 只有"拉人",没有"建群"

主流(Discord、微信)都是**勾选 + 一个确认按钮**,没有任何一家用"把头像拖到一起";
而且**建群时不问名字**——Discord 给通用名,微信拼成员名,想改再点抬头。

我们照着做,但因为 §三 那条统一,连"建群"这个动作都不存在了,只剩:

> **聊天抬头右边一个「＋」,打开邀请卡** —— 勾完就进去。界面上的字是"邀请",本文里的"拉人"
> 是机制名(`pullIn`)。

在单人会话里拉一个人,它就是双人会话了;在双人会话里再拉一个,就是三人。**没有状态迁移,
只有成员表变长。**

"就他俩"没落盘也得有稳定身份——面板每帧重列左栏、每次说话都现构一遍。它的 id 就是她的
UUID。从它拉人是**另起一个会话**(新 id),她俩的私聊照旧在;从落过盘的会话拉人是扩这个会话,
名字、发言号、记录上的印都还是它的。

Discord 要两条入口是因为它有几百个好友;我们左栏总共就那几只,多一条入口就多一个要发现
的按钮。G 面板左栏底部那个 `+` 留给召唤,不加分支——召唤是常用路。

另有一个快捷手势:**左栏把一格拖到另一格上**(手机桌面合并成文件夹那一下),前者的人拉进
后者那个会话,残影缩进合并后的那格。它和勾选卡走的是同一个 `pullIn`——勾选卡是明路(没人
会想到去拖),拖拽是顺手。按下移过几个像素才算拖,不然会误切会话;拖到空处松手弹回。

### 8.2 左栏列的是会话

头像按成员的脸拼:一个人是她的脸,多个人是叠脸。**同一条规则,没有两种图标。**

**名字默认跟着成员走,主人一旦改名就固定**——Discord 与微信共同的做法。好处是不会出现
"群里早没有阿岚了,群名还叫阿岚"。

### 8.3 管理:成员就地增减,改名与解散照规矩

名字旁边三枚图标:铅笔改名、红垃圾桶解散(过确认卡)、`＋` 邀请(邀请卡,名册上有人不在
这个会话里才画)——`ui-design-rules.md` 写死的"改与删是并排的两个入口"。成员抬头那一行:
头像上小 `×` 移出。

没有成员管理页,没有权限角色,没有群公告。

铅笔和垃圾桶作用在**左栏选中的那一格**,不是两套入口:就他俩时改人设、遣散;落过盘的会话改名、
解散。判据是"落没落盘",不是人数。群里的成员被遣散到只剩一个人时,群自己就解散了(见"遣散之后"),
所以不会有"只剩她一个的群"。背包页、用量、目标行、计划卡只属于一只同伴,会话没有单一的主时不画。

### 8.4 聊天面板

- **抬头一行成员头像**,悬停出名字与移出。
- **连发合并**:同一只同伴接连说两句,只画一次头像。她一次说两句是常态,不合并会刷屏。
- **被 `@` 的名字高亮**。这不只是好看——它正好对应"谁会醒"。
- **工具行、思考行也标谁的**:它们算在那只的连发里,第一块画脸和名字;两只紧挨着的工具调用
  不折进同一块。正在打字的回复按成员各画各的。
- **G 面板打开就落在当前交互对象上**(准星指着的、转盘选的);在面板里切到谁,R/Y/V 就对着谁。
  "当前对着谁"只有一份。

### 8.5 斜杠命令只在私聊里

斜杠命令(`/clear`、`/compact`、`/goal`、技能命令……)动的是**一只同伴的大脑**:清她的上下文、
整理她的上下文、给她定目标、用她的技能。它和背包页、用量、目标行一样只属于一只同伴,所以只在
会话有单一的主时可用——判据就是 §8.3 那一条(`Conversations.soloOf`),输入行问的是宿主的
`loop()`,取不到她就是不可用。

群里说不清它作用于谁:`/clear` 清一只,就出现"别人记得她说过什么、她自己忘了";清全体,又得
为 N 份上下文、N 条分隔线另立一套规矩。两头都是为群聊多造东西,所以不做。想动哪只,就去和她的
私聊里动。

不可用时斜杠输入仍是命令,**不当成话发给全体**:打 `/` 时补全只弹一行灰着的"命令只能在和同伴的
私聊里用。",回车回的也是这一句(和其它命令回话画在同一处)。同一句话,不列一排用不了的命令。

## 九、明确不做

- **中心调度器 / orchestrator。** 它会成为第二个决策源,和"改世界或伤害实体只由权限层
  裁决、没有第二个入口"直接冲突——**同伴的许可是她主人给的,不是队长给的**。这也正是 #71
  那套设计不能要的原因。
- **同伴能唤醒同伴。** §二。
- **会话上的"模式"开关(私聊 / 全员静默)。** "谁听得见"只有成员表这一个来源,见 §六。
- **按距离决定谁在会话里。** 按 Y 跟她说话本来就无视距离,群聊突然讲距离就是凭空多一条
  主人没见过的规矩。成员是名单说了算。
- **跨主人的群。** 不做。群名册是客户端本地的,别人的同伴不在我的名册上,勾都勾不到;
  真要做得先让服务端认识"群"这个东西。投递那一侧(`NumenEvents.emit` 的在线直送/离线出箱)
  本来就通,所以这扇门没关死,只是现在不开。
- **额外调 LLM 选发言人。** 主流正在淘汰(AG2 v1.0 撤掉了、LangChain 把
  `langgraph-supervisor` 停维、OpenAI 两代都没有过)。我们连它的替代品(handoff 工具)都不需要。
- **轮数上限当终止机制。** 硬上限是安全网,不是终止逻辑。
- **每人每轮必须发言 / 全量 transcript 每轮重拼。** 强制发言就是强制烧钱,全量重拼是 O(轮数²)。
- **为了让大家到齐而暂停世界。** 学术实现靠这个拿可复现性;陪伴产品里主人就在旁边玩,
  世界不能停。
- **为群聊单开一条"说话"链路。** 她说的话已经是气泡那一份,群聊只是多了个听众。

  Project Sid 的反例值得抄在这里:agent 有两个独立 LLM 模块,人说"给我一把镐",
  chat 模块回 "Sure thing!",function 模块却去 explore ——**人拿着想象中的镐走了。**

## 十、协作靠世界,不靠对话

"A 把铁给 B"是一个世界动作,不是一句话。她们共享同一个箱子、同一堵墙、同一片地,还各有
一份札记。**能靠世界传的信息就别用对话传。**

这是调研里最一致的结论:效果最好的实现都把**事实**从对话里搬走了——ChatDev 的黑板只进
结论不进对话,MetaGPT 的黑板是磁盘上的 git 目录,Anthropic 的子 agent 只回传一两千 token
的摘要。而我们的黑板就是世界本身,比谁的都实。

所以"主人要当路由器"在实践中没想象的累。

## 十一、账单与规模

- 调用次数**线性于 N**,不是 N²(因为没有互聊)。
- 但**一份上下文**意味着旁听的话也堆进她的历史,所以每只的上下文长得更快、压缩得更频繁。
  总成本是 **N 份账单 × 每份更厚**,不是简单的 N 倍。
- 每只同伴有自己的 provider 绑定。`TokenLedger` 是现成的抓手。
- **天花板在服务端,不在模型。** Project Sid 号称 1000+ agent,论文自己交代跑崩了,瓶颈是
  Minecraft 服务端算力;而我们的同伴是真 `ServerPlayer`,比他们重得多。MineCollab 那篇的
  建造任务,三个 agent 以上就"超出预算做不起"。

先按**两到三只**设计,不为更多做抽象。
