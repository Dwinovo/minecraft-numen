# 建造:原语命令、设计与建成的房子

状态:设计稿(09-26),未落地。它是 `docs/cli.md` 第 4 步里 `build` 的去向——`build` 不再是一个一次写完整栋房子的工具,而是一组命令。

## 一、为什么

- **一次写完太重。** 现在的 `build` 工具要把整栋房子的原语一次写进一个调用:输出长、写得慢、容易超过输出上限被截断;中间写错一处,整串被拒,只能从头重写。
- **做过的就忘了。** 房子盖完,原语就没了。她没法回答"house 盖在哪、盖了几栋",也没法改一栋已经盖好的房子。
- **为将来的 DSL 铺路。** 一份建造方案本身就是"一串命令",正是 DSL 要推广的形态;把它存成命令文本,建造就是 DSL 的第一个具体用例。

## 二、心智模型

像"基础设施即代码"(Terraform 的 plan/apply):

- **原语是命令。** 每种原语(`layer`、`set`、`line`、`cylinder`、`sphere`、`copy`,以及单格的 `place`)就是 `build` 组里的一个动作。
- **设计是一段程序。** 一份有名字、存盘的原语命令序列,坐标相对原点 `(0,0,0)`。它像一个函数,可以在任何地方、盖任意多次。
- **建成的房子是实例。** 某份设计的某个版本,在某个维度、落点、朝向上盖出来的那一次。
- **改房子就是改程序。** 改设计 → 看差异(plan)→ 把差异应用到实例上(apply)。

命令层无状态:每一行都能单独看懂;状态(设计、版本、实例)都在服务端,由名字点到。

## 三、命令

```
build place crafting_table 10 64 5              当场执行一个原语(绝对坐标)
build layer … / line … / sphere … 同理           不带 --into 就当场执行

build new house                                 新建一份空设计
build layer … --into house                      往设计末尾加一步(相对坐标)
build show house                                列出设计:每步编号、类型、范围、方块数、所需材料
build step house 2 <原语…>                       把第 2 步换成新原语
build insert house 3 <原语…>                     在第 3 步前插入
build drop house 4                              删掉第 4 步
build designs                                   设计库:她们写的设计 + 蓝图文件
build delete house                              删掉一份设计(还有实例在用时如实拒绝,见 §五)

build at house 10 64 5 [--rotation 90]          按设计在此开工 → 产生实例 house#1(蓝图文件同一个入口)
build built                                     列出建成的实例:设计、版本、维度、落点、朝向、何时、谁盖
build plan house#1                              按设计最新版算出对这栋的差异:补几格、换几格、拆几格
build apply house#1                             按差异施工,实例升到最新版
```

- **同一套原语、同一个执行器。** 当场执行 = "只有一步的设计,立刻开工";`--into` 只是把这一步记进设计。两条路共用原语解析与执行器,不是两套建造逻辑。
- **原语参数照现有 `build` 工具的语义**(方块写法同 `/setblock`、加权混合、遮罩 `carve|overwrite|solid|keep`、`layer` 的字符网格与图例、`copy` 的旋转与镜像),拆成标志与位置参数;`layer` 的行与图例用可加引号的一串值表达。
- **整体预检不变。** `build at` / `build apply` 开工前对整份(或整份差异)做材料预检:生存模式下缺料就一格都不放,如实报缺什么。当场执行的单个原语同样先预检。
- **"后写覆盖先写"不变。** 设计按步骤顺序求出每一格的最终方块,开工照最终结果放。

## 四、差异(plan / apply)

- 按新版设计在实例的落点与朝向上求出**每一格应该是什么**,和世界里的**实际**方块比:已经对的不动,缺的补,不一样的换。和按蓝图施工跳过"已经对的格子"是同一个执行器。
- **只拆自己盖的。** 旧版设计里有、新版里没有的格子要拆,但只拆满足下面两条的:
  1. 按实例所记版本的设计,这一格本该是这个方块,而且现在仍是它;
  2. "谁放的方块"记录(`PlacedBlocks`)表明它是她(或主人的同伴)放的。
  
  别人放的、主人后来自己摆的、被改动过的,一律不碰;拆除照常经权限层。
- 世界变了也照实:有人挖掉几块墙,plan 如实写"补回 3 块";有人在屋里加了东西,plan 不拆它。
- `plan` 只读不动;`apply` 是一件后台任务,结果以 `task_finished` 报告,实例的版本号在完成时才升级。

## 五、持久化

三样东西,同一个事实只存一处:

| 什么 | 存在哪 | 格式 | 生命周期 |
|---|---|---|---|
| 设计 | 服务器级蓝图库 `schematics/designs/<名>/v<N>.numen`,和 `.litematic` 同库,跨世界复用 | 纯文本:开头几行 `#` 注释(作者、所属主人、创建时间),其后每行一条原语命令(相对坐标) | 主人或她删除 |
| 版本 | 同一目录下的 `v1`、`v2`……;最新版是编号最大的 | 同上,每次修改写一个新文件 | 还有实例引用就保留;没人引用的旧版在写新版时清掉 |
| 实例 | 世界存档(SavedData,和 `PlacedBlocks` 一样跟着世界走) | `house#1`、设计名、版本、维度、落点、朝向、时间、谁盖的 | 随世界;将来做拆除时删 |

- **读写都过命令解析器。** 保存设计时每一行都按命令树解析,写不通就拒并报出第几行;主人手改文件同样校验,不合法的设计不加载并如实报告。设计文本的语法就是命令的语法,没有第二份。
- **不另存"这栋放了哪些方块"。** 拆除边界由"实例所记版本的设计"加 `PlacedBlocks` 推出,避免两份记录对不上。
- **归属。** 设计记着所属主人;只有这位主人的同伴能改、能删;其他人可以看、可以照着盖。改设计文件不是动世界的动作,不经权限层;照设计动世界的每一格照常经权限层。
- **删除设计。** 还有实例引用它时拒绝并列出这些实例,免得实例失去可 plan 的版本。

## 六、她怎么知道

- `build built`、`build designs` 随时可查;不往每轮状态里塞(索引思路:需要时查,不前置正文)。
- 开工、差异施工都是后台任务,结果以 `task_finished` 报告,写明放了、换了、拆了多少格,缺料时写明缺什么。

## 七、不做的

- 不做"当前设计"这类隐藏指针:每条改设计的命令都点名设计。
- 不做通用的命令序列(DSL):那是后期的事;本稿只保证设计文本就是合法的命令行,将来直接复用。
- 不做拆除实例、设计合并、跨主人共享写权限:没人提,不预先铺。
