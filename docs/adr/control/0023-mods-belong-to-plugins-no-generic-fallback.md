# 0023 模组的事归插件:不留通用的兜底

- 状态:已接受,已落地(说明已改;`numen.gui.*` 已随 0021 的第 3 步拿掉)
- 日期:2026-11-23
- 另见:[0021](0021-look-and-do-no-windows-for-the-model.md)(本条修订它的几处,见"修订了什么")、
  [0020](0020-questions-answered-by-whoever-knows.md)(问题与登记的门)

## 背景

0021 把界面从模型面前拿掉,一种特殊方块一组函数。写的时候还留着几处"没人适配的模组机器也能凑合用"的话:

1. 决定 4:普通的格子容器"(箱子、木桶、没人适配的模组机器)留一组通用的放与取"。`numen.container` 给模型的说明照着写成了
   "a machine with no functions of its own"。
2. 后果:"能存、能取、能看存量的那一半照旧通吃"。
3. 没有定的:原始 NBT 是"没人适配"时的兜底;插件写自己的函数时要不要用开界面、点格子的引擎(用得到就得挪进 `numen-api`)。

用户的原话:

> 我还是发现你隐隐约约有一种通过某种机制就能通吃Minecraft的想法,我很明确的告诉你这非常不现实,就算你掌控了比如说GUI里面的格子,
> 其实用起来也很别扭,你最终不写插件,numen能做到的还是非常局限,与其提供一个残缺品,不如干脆就别提供,要提供就直接写插件来提供好的。
> 之前的说是"通用",其实真的就是一个残缺品,最后还是要靠插件来适配,这样子的话意义不大。

> 那是插件的自己实现啊,和numen有什么关系?这些函数本来就应该放在numen里面,numen是numen-api的第一个插件,负责打通原版的Minecraft啊。

往一台模组机器里"通用地放",放进哪一格由它的界面按 Shift 点的规矩分:原料进了燃料格、升级格,她不知道,回执还说放进去了。
这就是残缺品。

## 决定

1. **没有哪个机制通吃 Minecraft。** `numen` 是 `numen-api` 的第一个插件,只打通原版。一个模组要让她看得懂、会用,由插件按那个
   模组自己的 API 做好:登记回答者(看)、登记自己的函数(做)。
2. **没有插件就不提供,不拿通用的半成品顶上。** 不让模型自己操作界面里的格子(`numen.gui.*` 照 0021 拿掉,拿掉之后不补替代品);
   原始 NBT 不当兜底给。
3. **`numen.container` 是原版容器的一组**:箱子、木桶、漏斗、投掷器、发射器、潜影盒、箱子矿车。给模型的说明只说这些,不承诺模组机器。
4. **开界面、按步骤做事的那件活(`task.station`)留在 `numen`**,它是原版这些函数的实现,不挪进 `numen-api` 给插件复用。插件用
   `numen-api` 已有的任务与权限层写自己的活(森罗厨房的锅就是这样写的)。

## 修订了什么

0021 的这几处以本条为准,其余不变:

- 决定 4 括号里的"没人适配的模组机器"与"通用的放与取":见本条决定 3。
- 后果里"能存、能取、能看存量的那一半照旧通吃":不再这样说。方块里存着什么仍经加载器的标准存储读,模组方块实现了那个约定就
  读得到,这是加载器的约定,不是对模组机器的承诺。
- 没有定的里"原始 NBT 给不给"的理由(兜底)不成立,见本条决定 2;"插件要不要用引擎"定了,见本条决定 4。

## 后果

- 没装对应插件的模组机器,她不会用,帮助里也不说她会。
- 给一个模组做联动的工作量都在插件里;`numen` 与 `numen-api` 不为它加东西。
- `numen.container` 没有另加判断去拦原版以外的目标:打得开界面就照做。模组的箱子(只管装东西的)因此照样能用,但这不是承诺。

## 实现说明

- `numen.container` 给模型的那句说明与 `docs/shell.md` 的那一行改成只说原版容器。代码逻辑没有动。
