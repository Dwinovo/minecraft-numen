# 0024 看:方块、实体、物品各一个问题,回答是带名字的字段

- 状态:已接受(方块、实体已落地;物品未落地,见文末)
- 日期:2026-11-23
- 另见:[0020](0020-questions-answered-by-whoever-knows.md)(问题与登记的门)、
  [0021](0021-look-and-do-no-windows-for-the-model.md)(本条修订它的决定 1 与"没有定的"里两项)、
  [0023](0023-mods-belong-to-plugins-no-generic-fallback.md)(没有兜底)

## 背景

0021 把"看"做成了一个问题(`Questions.DESCRIBE`):`numen.scan.block` 问一圈"这是什么",回答者各交回几行字。落地之后露出三处不够:

1. **只有方块能问。** `numen.scan.entities` 每只实体是固定的几个字段,模组的生物说不上话;界面拿掉之后,实体身上穿的拿的没有地方看。
2. **回答是几行字。** 她读得懂,程序用不了(写不出 `if 进度 > 50`),也看不出哪一行是谁说的。
3. **一个问题混着两种目标**(`Focus`:一格或一只实体),每个回答者开头都要先判"问的是不是我这一种"。

用户的话:

> 这个看的东西确实需要具备拓展性。

> 我觉得你那个idea挺好的,物品,实体,方块。

> 那我们和CC和fabric,neoforge这种挺像的呀,都是一个机制。

## 主流怎么做

- **CC:Tweaked**:方块、物品、实体各一个细节登记处,写法相同。提供者是一个函数,拿到一张表和要描述的东西,往表里加带名字的字段;
  问的时候把登记过的提供者挨个叫一遍,交回合并好的表。它自己的原版信息也从同一个口登记。分两档:一次列很多个时只给基本的,
  看一个时才把提供者都问到。
- **mineflayer**:实体是固定字段,另挂一份服务器同步来的原始数据,要什么自己翻;扩展靠插件往机器人上加函数,没有"往看里加东西"的口。
- **NeoForge 的能力、Fabric 的查询**:核心定问什么,各模组登记来答,问的时候核心去问。同一个思路。

## 决定

心智模型:**她面前只有看和做。`numen-api` 什么都不认识,只定问题、开登记口、被问时问一圈;谁懂谁登记来答,`numen` 是第一个
登记的,答原版。**

1. **看的对象是三种:一格方块、一只实体、一件物品。各一个问题常量**,回答者拿到的就是那一格、那只实体、那件物品,不必先判目标是哪一种。
2. **每一种分两档。** 列一片(`numen.scan.blocks`、`numen.scan.entities`、`numen.inv.items`)只给基本的,不问任何人;看一个
   (`numen.scan.block`、`numen.scan.entity`、看一件物品)给基本的,再加问一圈得到的回答。
3. **回答是带名字的字段,不是几行字。** 一个回答者交回一张字段的表,值是脚本的普通值(字符串、数、布尔、列表、表);不认识就不说话。
4. **登记带名字:`numen.answer(问题, 名字, 回答者)`。** 回答归在这个名字下(`details.furnace.cook_percent`),日志点的也是它;
   同一个问题下重名、名字不合规,登记时就是错。

   ```lua
   numen.scan.block(熔炉).details
   -- { storage = { inventories = { ... } }, furnace = { fuel_seconds = 12, cook_percent = 40 } }
   numen.scan.entity("villager@3f9a1c").details
   -- { villager = { profession = "minecraft:farmer", level = 2 }, equipment = { mainhand = { item = "minecraft:wheat", count = 12 } } }
   ```
5. **没有兜底**(0023):没人认识的东西,她拿到的只有基本的;不给原始数据让她自己翻。
6. **分工不变**(0020 决定 2):问题常量、问的那一圈、登记的门在 `numen-api`;原版的回答者在 `numen`,从同一扇门登记;模组的在各自的插件。

## 修订了什么

0021 的这几处以本条为准:

- 决定 1 里"一个新的问题常量"与示例里交回几行字的写法:见本条决定 1、3、4。
- "没有定的"里"实体也问这是什么":定了,见决定 1、2。
- 实现说明里的 `Questions.DESCRIBE`、`Focus`、`details` 是"一句一条":已换成本条的样子。

## 后果

- 给一种模组的方块、生物加"她看得懂",是插件登记一个带名字的回答者,交回几个字段。
- 程序可以直接用回答里的数;她读到的也分得清每一段是谁说的。
- 回答的字段没有固定的清单:有哪些字段写在登记它的那一方给的说明与技能里。
- 基本的那几项仍是 `numen-api` 自己算的(实体敌不敌对、主人是谁),不在这一圈里。

## 实现说明

方块与实体已落地:

- `Questions.BLOCK`(回答者拿到她与那一格)、`Questions.ENTITY`(她与那只实体),回答者是同一个接口 `Describer<T>`,交回
  `Map<String, Object>`,null 或空表是没话说。`Questions.DESCRIBE` 与 `Focus` 删了。
- `Question` 的回答者带名字,按登记先后;重名、名字不合规(与函数名同一条规矩)登记时抛错。门上是
  `NumenApi.answer(Question<T>, String, T)`。
- 问的那一圈在 `Descriptions.of(问题, 她, 目标)`:交回"名字 → 字段",没说话的不占名字;回答者抛异常、或交回写不成脚本的值,
  只丢它那一条并在日志里点名。
- `numen.scan.block` 的 `details` 是按名字的表;新增 `numen.scan.entity`,基本的那一行和 `numen.scan.entities` 出自同一个函数,
  再加 `details`。
- 原版的回答者(`numen` 的 `describe.VanillaDescribers`)。方块:`sign`(两面各四行、涂没涂蜡)、`storage`(几份存储各带露出的面:
  物品、流体、能量,仍经加载器的标准存储读)、`furnace`(燃料还烧几秒、烧到百分之几、还要几秒;读方块实体存盘的那三个数)。
  实体:`equipment`(六个装备位上有的)、`villager`(职业、等级)、`tame`(驯没驯服,能坐的带坐没坐,能备鞍的带备没备)。

物品没有落地:物品的描述每一轮都出现在她的背包清单里,那里要的是一句短话,不是一张表;"短话"与"字段"怎么出自同一处要先定。
