# 0014 插件的登记归在插件名下:能撤回、能重登,函数可由代码描述,受权的动作只有一块积木

- 状态:已接受,已落地(实现说明见文末)
- 日期:2026-10-31
- 另见:control 0009(Lua API 登记)、control 0015(KubeJS 联动)、issue #108

## 背景

插件经 `NumenPlugins.register` 拿到一扇门(`NumenApi`),往里登记工具组、编码、事件监听、事件类型、身体状态片段、穿戴来源、
随附的技能与模块、`/numen` 下的指令。现在这些登记散落在各自的全局表里,登记了就撤不掉,所以:

- 插件分页里关掉一个插件要重启才生效(花名册把"这次启动"和"下次启动"分成两份设定);
- 想做脚本化的联动(#108:整合包作者改完脚本就生效,不重编译、不重启),没有地方能把上一版的登记换掉;
- 工具函数只能靠反射扫一个带 `@Fn` 的 Java 类来登记,脚本里没有 Java 类可扫;
- 动手前过权限层的那套流程(逐个动作判 允许/拒绝/要问 → 发问 → 等答复 → 记下准许)写在 `numen` 的 `AbstractCompanionTask` 里,
  插件用不到,森罗厨房的 `PotActTask` 只好自己抄了一遍。

用户的要求:照主流,不为某一个使用者特化,不留多源与胶水,组合解耦,单体多模块各守边界。

## 决定

照主流的"登记即句柄、按作用域撤销"(VS Code 的 `Disposable`、Guava `Closer`、OSGi 的服务登记、IntelliJ 的动态插件):

1. **登记归属**:每次登记都向对应的表要一个句柄;一个插件的门持有它全部的句柄,组成这个插件的作用域。撤回一个插件 =
   关掉它作用域里的全部句柄;重登 = 撤回后再跑一遍它的 `setup`。表各自负责"撤掉我这一条"做得干净,门只管收集。
   引擎自己的登记(`registerHost`)同样有作用域,只是不进花名册、名单也管不着。
2. **对所有插件一视同仁**:花名册的开关、脚本重载、单测都走这同一对操作,没有第二条路。只经门登记的插件天然可以运行中撤回;
   在门外动了东西的插件(Mixin、直接挂在加载器上的监听)在登记时声明"卸下要重启"(对应 IntelliJ 插件的 `require-restart`),
   花名册对它仍显示"重启后生效"。不靠猜。
3. **函数由描述定义**:一个函数的契约(名字、参数及类型与说明、返回、执行端、文档)是一份描述;注解反射(control 0009)是它的一个
   生产者,代码构造是另一个。登记处、编码、帮助、类型签名、体检只认描述,不再各自读注解。
4. **读登记的地方只读活表**:系统提示、帮助、外部大脑的工具清单都从当前的表生成;登记变化时发一次"表变了"的通知,
   有缓存的地方据此失效(MCP 端照规范发 `tools/list_changed`;`/numen` 指令树重建并重发给在线玩家)。
5. **受权的动作是 numen-api 的一块积木**:"提出这几个动作 → 权限层判 → 要问就发问并等答复 → 结果与准许交回"做成可组合的组件,
   任务持有它而不是继承它;Numen 的任务、Java 插件、脚本都用这一块。`numen` 与插件里各自的那几份照搬删掉。
   身体做了什么照常如实报告给模型。

模块边界:作用域、函数描述、受权动作的组件都在 `numen-api`;`numen` 只是使用者;`numen-api` 不认识任何具体插件。

## 后果

- 插件分页的开关对只经门登记的插件当场生效;状态"重启后生效"只剩给声明了要重启的插件。
- 每张登记表多一个撤回的口子,登记的接口(`NumenApi`)对插件不变,现有插件不用改。
- 森罗厨房等插件删掉自抄的权限流程,改用同一块组件。
- 这是 control 0015(KubeJS 联动)的前提;它只是这套机制的又一个使用者。

## 实现说明

- 句柄与作用域:`Handle`、`Scope`(`agent/…/scope`,纯 JVM,放在登记表里最低的那个模块,`EventTypes` 在那里)。表:函数组、值转换、同伴事件订阅、
  事件类型、身体状态片段、穿戴来源、内容目录、内置 Lua 模块、`/numen` 指令、没跑的客户端块。`registerForClientMod` 的目标模组声明是插件自己的
  属性,不是登记,不进作用域。引擎自己的登记(`registerHost`)也走作用域,只是不撤。活的执行器也在门里:`numen.taskRunner(记录类, 执行器)` 经 `TaskFactory.register`
  登记,句柄 `close()` 撤掉执行器,并把这种活里正在跑的叫停(`StopCause.PLUGIN_WITHDRAWN`),一个插件的活不比它的作用域活得久。
  还在门外的表(`ToolRegistry`、网络包、每刻钩子等)不是门能撤的,用它们的插件声明要重启。
- 句柄:`Handle.once` 保证只撤一次;按键放的表(`TaskFactory` 同类型后登记的顶掉先登记的,函数组、事件类型、值转换、内置模块拒绝第二次
  登记)撤之前先比引用,表里现在的不是自己登记的那条就不动——两次登记出来的 record 可以 `equals` 相等,不能比值。
- 门过期:作用域一关,那扇门的每个登记方法都抛 `IllegalStateException`,点名插件(照 pi-mono 的"重载后旧上下文失效而不是静默生效")。
- 声明卸下要重启:`NumenPlugins.register(id, Unloading.NEEDS_RESTART, setup)`。声明的有:`numen`(工具、任务执行器、本能链、网络包在门外)、
  `tlm`、`ysm`、`ftbquests`(加载器总线与 Mixin、宿主每刻钩子在门外)。`kaleidoscope`、`curios`、`litematica` 只经门登记,是动态的。
- 花名册:停用名单是现行的唯一设定,开关翻一下落盘并当场装上或撤回;"这次启动/下次启动"两份设定删了。`pending` 只在开关和状态要重启才对得上时
  为真(声明了要重启的装着时被关;启动时就在名单上、登记方没交 setup 的被开)。来源多一种 `SCRIPT`。
- 函数描述:`ApiFunction` 是描述,`Binder`(反射)与 `FunctionBuilder`(代码)是两个生产者;读参数得到 `FnArgs`,反射的生产者再组成参数 record。
  描述生产出来没有主人,`ApiRegistry` 登记时盖上名字空间与组;门多一个 `api(group, summary, List<ApiFunction>)`。
- "登记变了":`Registrations`。MCP 端点没有函数清单(四个固定工具,函数在 `guide` 文本里现取),所以不发 `tools/list_changed`。
- 受权的动作:`permission.GatedAct`;`AbstractCompanionTask` 与 `PotActTask` 各持一块,抄的两份流程删了。森罗厨房被拒的回执现在是"cannot <动作>:
  <理由或主人的原话>",主人答复被拒也带这个前缀(以前只有规则拒绝带)。
