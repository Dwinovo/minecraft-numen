# 0020 扩展点是一个问题:Numen API 出题,谁懂谁登记来答,没人答就说没人认得

- 状态:已接受(问题常量与 `numen.answer` 沿用;旧四个登记口的搬迁未落地,见文末);决定 4(一次动作前后变了什么)被 [0022](0022-light-click-receipts.md) 取代,决定 5(界面种类)被 [0021](0021-look-and-do-no-windows-for-the-model.md) 取代
- 日期:2026-11-23
- 另见:control 0014(登记归属)、control 0016 与 0017(同一类的扩展点)、control 0018(只读事件)、body 0003(她缺的那半个客户端)、issue #167

## 背景

#167:她右键 AE2 的终端,读不到 ME 网络里的东西;右键无线终端,服务器崩了。崩溃是 0.1.4.1 的旧缺陷,0.1.5 已修。
顺着这件事往下看,暴露出来的是一条做法上的债。用户的原话:

> 一直以来,numen想的都是继承的思想,只要我们捕捉到对象是某个类,然后解析他,就可以让numen的鲁棒性提高,可是事实上,各个模组自己开发自己的,
> 几乎不存在有同一个可以解析的父亲,那么继承这个时候失效,显然要采用组合的思想,让各个模组自己去反馈自己的逻辑。

当时代码里的样子:

1. **"按之前记一下、按之后比一下"有五份,各写各的。** 鼠标比点中那格周围的方块与开没开界面(`Mouse.press`);点一下的回执比身体、瞄的那一格、
   实体的装备、身边新冒出来的实体(`PressReceipt`);界面里做一件事的回执比身体与界面的格子(`tools/menu/Receipt`);进度奖励比背包;
   FTB Quests 插件自己又写了一份。插件看不见 `numen`,所以它只能重写,也没法往 `numen.use.item` 的回执里添一句话。
2. **回执看的东西是写死的。** 物品还是那件、里面的数据变了(扳手换模式、工具充电)、饥饿、状态效果、耐久,都报成"什么都没变"。
3. **三处传话,有一处漏了。** 鼠标知道"这一下打开了界面",`Interaction` 只在对着方块或实体按的那条路上把它传下去,对着空气按
   (无线终端、背包这类物品)的那条路没接:界面开了,她收到的是"什么都没变"。回执那句话又是第三处拼的,所以对着箱子按也会一边交回界面、
   一边写"nothing visibly changed"。
4. **认得的界面是一张固定的表。** `MenuKinds` 里列着原版八种(附魔台、切石机、织布机、交易、信标、铁砧、讲台、合成器),读出来的类型
   `Screen` 是封死的。模组的界面加不进去。
5. **门上一个问题一个方法。** `registerGear`、`rangedWeapon`、`knowledgeSource`、`contributeBodyState`:每多一种扩展,`NumenApi` 多一个方法、
   改一次形状。同伴事件那边早就不是这样了(`CompanionEvent` 是常量,`on` 一个字不用动,理由写在它的注释里)。

用户的要求:

> 我的想法也是要强大一下numen-api的接口才行,numen是numen-api的第一个插件,不需要任何特化,这样子才能发挥开发者们的想象力。

> 主流的工程设计上应该也会遇到这种问题,我觉得我们应该去看看主流。

## 主流怎么做

- **NeoForge 的能力(`BlockCapability`)、Fabric 的 API Lookup(`BlockApiLookup`)**:各家机器没有共同父类,"这格方块能不能存物品"靠认类答不了,
  于是一个问题是一个常量,谁的方块能答谁登记一个提供者,要用的人拿着常量去问;都答不上有兜底的提供者。
- **Jade、The One Probe**:"准星指着的是什么"由各模组登记的提供者各往同一个提示框里添几行。
- **Fabric 的事件(`Event` 与 `invoker`)**:读下来是一张回调表和一个循环,当场调、当场拿结果,没有队列。
- **Claude Code 的钩子**:工具调用之前、之后各有一个钩子点(`PreToolUse`、`PostToolUse`,失败另有 `PostToolUseFailure`),登记只有一种形状;
  之后的钩子交回一段 `additionalContext`,附在工具结果旁边给模型,几个钩子交的模型都收到;钩子之间不保证先后,一个出错默认不拦这次调用。
  它没有给"之前"留东西给"之后"的办法,两个钩子只共享调用编号。

## 决定

心智模型一句话:**Numen 不再认东西,改成问问题。Numen API 出题,谁懂谁登记来答,没人答就老实说没人认得。**

用户的复述:

> 右键一下,numenplayer的右键永远都是收集所有可以回答这件事情的回执,逐个去问,然后收集回答,至于谁能回答就让他们自己登记,
> 有点像发出一个事件,然后多个消费者消费。

1. **一个扩展点是一个问题常量(`Question<T>`),登记永远是同一个方法:`numen.answer(问题, 回答者)`。** 以后加问题只多一个常量,门不改形状。
   插件自己也能出题,让别的插件来答。登记归在插件名下、能撤回(control 0014)。
2. **判断一样东西放哪边,看谁要往里挂。** 插件看不见 `numen`,所以要让插件挂的接口在 `numen-api`;`numen` 把原版的回答从同一扇门登记进去,
   没有别人用不了的路。模型看到的动词(`numen.use.*`、`numen.gui.*`)留在 `numen`。
3. **不用事件队列。** 当场问、当场要答案拼回执,是一张登记表加一个循环。队列只有给模型的收件箱那一个,不动。
4. **问题一:这次动作前后变了什么(`Witness`)。** 回答者被叫两次:动作之前交回一份记录(不归它管就交回空),动作之后问那份记录"变了什么"。
   之前记下的东西就装在那份记录里,由账本(`Ledger`)替它拿到结账。账本由驱动这次动作的任务开和关:吃东西、拉弓的结果在松手之后,
   所以账不记在鼠标按下的那一刻。挖、合成这些有自己的账,不开这一本。
5. **问题二:开着的这个界面是什么、能做什么(界面种类)。** `numen.gui.view` 问一圈谁认得,有人答就用它读出来的内容,没人答只给格子并说明
   没人认得。原版八种由 `numen` 登记;模组界面也是"选一项"的,接上同一个能力,模型照旧用 `numen.gui.choose`;模组独有的事由插件加自己的动词。
6. **五条规矩。** 不懂的时候也站得住(没人答不崩、不猜);各说各的(一个回答者出错只记日志,回答之间不依赖先后);只能添、不能改别人说的话;
   动作失败、被叫停、超时也要结账(身体可能已经变了);能不能做只由权限层说,回答者只说事实。
7. **不照主流的一处**:Claude Code 的前后两个钩子之间不带状态;我们的核心就是"之前记下、之后比较",所以"之前"交回一个对象。

## 后果

- 给模型多看一样东西 = 写一个回答者登记进去,不改 `numen`,也不改 `numen-api`。
- 她右键之后知道的事变多了:物品里的数据、耐久、饥饿、状态效果、打开了什么界面,和原来的那几样一起报。
- 回执的长度随回答者增多而变:规矩是只说变了的,没变的不提。
- 通用的这一层有上限:模组自己的包、不在她眼前的、过一会儿才发生的,靠对应模组的插件或她自己去看。

## 没有做的

- **界面种类搬进 `numen-api`**(决定 5):未落地。卡在一处要先定:界面读出来的内容是各种界面自己的 record,`numen.gui.view` 的返回类型里
  要写得出"这几种之一"。现在这个"之一"是封死的 `Screen`,它的类型在登记 `numen.gui` 那一刻就定死了(`RecordCodec` 构造时取字段类型);
  插件后登记、运行中撤回的种类进不了签名与帮助。要让类型定义跟着活表走,得先动 API 登记这一层。
- **门上已有的四个登记口**(`registerGear`、`rangedWeapon`、`knowledgeSource`、`contributeBodyState`)搬成问题常量:未落地,单独做。
  搬之前门上有新旧两种写法并存。
- **"这一下会动到什么"也由回答者申报**(模组的放置类物品现在只被问"能不能用这一格",不被问"能不能放";`Mouse.placing` 只认方块、桶、
  打火石、火焰弹):等碰到具体用例再开。裁决仍只归权限层。
- **本能链的登记**(`BrainChains`、`ReflexRegistry`)不在门上:代码里记了 TODO。
- **AE2 插件**:等这套机制做好再接。

## 实现说明

- 问题与门:`Question<T>`(`numen-api` 根包,自己拿着回答者的表,`register` 交回只撤一条的 `Handle`)、`Questions.WITNESS`、
  `NumenApi.answer(问题, 回答者)`;花名册多一种记数 `ANSWER`。瘦 api jar 放行 `Question*` 与 `witness` 包。
- 账本在 `numen-api` 的 `witness` 包:`Witness`(`open` 交回 `Before`,`Before.changes` 说变化)、`Focus`(对着哪一格、哪只实体)、
  `Ledger`(`open` 问一圈、`close` 结账,结过再问给同一张单子;开账与结账各自逐个隔离,出错记日志点名回答者的类)。
- 原版的回答者在 `numen` 的 `witness.VanillaWitnesses`,经门登记:背包与经验、物品里的数据(写法取 `StackLabel`,两边写出来一样时点名
  变了的组件)、血量、饥饿、状态效果、骑乘、瞄的那一格、实体的装备、身边新实体、打开或合上的界面、开着的界面里的格子。
  其中物品里的数据、饥饿、状态效果、打开或合上的界面是新加的。
- 用账本的:`InteractAtCompanionTask`、`InteractEntityCompanionTask`(失败、超时、被叫停的那句话后面也接上已经变了的事)、
  `MenuKinds` 里做一件事的那一步。`PressReceipt` 与 `tools/menu/Receipt` 删了;`BodyDelta` 只剩"用坏的装备"(每件活的回执都带);
  `Belongings` 不动(进度奖励、FTB Quests 只要背包那一半,照旧直接用它)。鼠标交回的"哪几格变了"(`Mouse.Use.Pressed.changes`)是寻路
  开门、垫路在用的结果,不是回执,不动。
- 漏传话的那一处:`Interaction` 对着方块、实体、空气按的三条路都从 `landed` 过,打开了界面就记下(连同 `MenuOrigin`)。原版没有
  "对着空气右键开界面"的物品,这条路没有 GameTest;要真模组的物品才验得到。
- 回执的话:打开了界面写 `opened a window: <菜单类名>`;什么都没变写 `nothing visibly changed`,不再列看了哪几样(那张单子现在是活的)。
- 测试:`QuestionTest`、`LedgerTest`、`NumenPluginScopeTest`(回答者随插件撤回与重登)、`VanillaWitnessesTest`;GameTest
  `a_plugins_witness_adds_its_line_to_the_click_receipt`(插件的一句进了回执,旁边抛异常的回答者不碍事)、
  `a_click_reports_what_changed_inside_the_held_item`(打火石的耐久),点开箱子的那条多断言回执写着打开了界面。
