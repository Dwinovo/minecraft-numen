# 0040 每节点分配再压一轮;小搜索的固定开销

- 状态:已接受;接 [0035](0035-search-allocation.md)(第一轮减分配)与 [0039](0039-learning-inside-the-deadline.md)(到时限停的搜索剩下的超时都是整堆回收)
- 日期:2026-11-01

## 背景

和 Baritone 对着跑同一批题(AutoDL,真墙钟时限,`Compare`)时看到两件事:每展开一个节点分配约 7.7 KB(Baritone 约 0.66 KB),GC 总时间中位 2.3 s 对 0.27 s;
展开不到 50 个节点就到的搜索墙钟中位 2.6–2.9 ms(Baritone 0.16–0.29 ms)。
两件都是纯性能:**不改任何搜索决策**,v3.1 的 dev(664 行)与封存(887 行)`results.jsonl` 改前改后逐字节相同(见下)。

## 剖析(AutoDL,JFR 分配采样与 1 ms 执行采样,mountains 规格 B 3 s 档整批;按第一个 `numen` 帧归属)

每节点分配的大头(占分配字节):

| 分配点 | 占比 | 实际是什么 |
|---|---|---|
| `Sight$Line.visit` | 15.8% | 每条视线数到目标时,对整块目标也走原版 `VoxelShape.clip`:`toAabbs` 列表、`AABB.move`、`CubePointRange`、`BitSet`、`Vec3` 十来样 |
| `Nodes.grow` | 12.0%(另 `AStar.edge` 3.3%、`Nodes.filled` 1.1%) | 十九条平行数组翻倍;生成的节点约是展开的七倍,绝大多数是没取出的候选 |
| `EditedView$Changes` / `over` / `set` | 11.9% | 每展开一个节点、每精确判一步,把最近几步的改动叠在快照上:新建视图、两张数组 |
| `Faces.point` | 5.9% | 每个垫、挖的候选问一次面心,整块也列一遍盒子 |
| 其余 | 各 ≤ 3% | `Stepping.samplePoints`、`Contact$Cells`、`Draft.record`、`Semantics.eyeInWater`…… |

执行采样(同一批):快判断读世界不是瓶颈;`Vertical$Levels.readBand`(估价的竖直项现扫快照)占 10.6%,其中 `WorldSnapshot.decode` 6.2%;`Burial.of` 6.0%;
`EditedView$Changes.get` 5.6%;`Nodes.find` 5.0%;`AStar.recentEdits` 4.7%。

小搜索(展开不到 50 的 144 道,同一份整块快照上每道重复 30 遍取中位,热身后):墙钟中位 1.86 ms,P90 37.7 ms,每次分配中位 312 KB。
执行采样:改前 nether 71%、mountains 95% 的时间在 `Vertical.floor` → `Levels.readBand` → `WorldSnapshot.forEachBlock`/`decode`;nether 另有 25% 在 `Burial.of`。
分配里每次搜索固定的约 300 KB 是 `Recall` 的表:每种结论一张 4096 槽的直接映射表(`long[]`、`byte[]`、结果数组),用到哪种建哪种,几十个节点的搜索也要建四五张。

## 决定

1. **整块目标与整块面心自己算**(`Sight`、`Faces`):
   - 射线数到整块时,碰没碰上、碰哪一面由 `Sight.Line.clipUnit` 直接算,逐步照 `VoxelShape.clip` 对整块的做法(射线太短不算;起点前挪千分之一在格里就是射线朝向的反面;
     否则照 `AABB.clip` 看进格的三个面、取最近的)。原来路上的整块已经这样判("碰没碰上"),这次让目标自己也走这条路并给出面;
     目标的交互轮廓(`getInteractionShape`)非空时仍走原版 clip。`Line` 的追踪回调直接交回 `Direction`,不再包 `BlockHitResult`。
   - `Faces.point` 对整块直接给面心,不列盒子。
   - `SightTest.aWholeBlockTargetIsHitWhereVanillaClipHitsIt`:两万条随机射线(含从格里射出、贴着面)对着原版 `Shapes.block().clip`,碰没碰上、碰哪一面逐条相同。
2. **搜索面对的世界重用一份叠加视图**(`EditedView.Reusable`、`AStar.faced`):展开、精判、`blocking`、补 `Maneuver` 都把"走到那里的最近几步改动"装填进同一份视图,
   不再每次新建视图与改动表。装填一次,上一次的视图和叠在它上面的草稿就作废——它们都只活在一次展开或判断里。没有改动仍直接用快照本身。
   `EditedView.over` 的装填逻辑抽成 `apply`,两条路共用。
3. **竖直项的读法**(`Vertical.Levels`、`WorldSnapshot.forEachBlock`):
   - 原来问到哪一层就把它所在的一整个区段高度(16 层)读进来,每层的读法是解开整层 256 格。现在只读问到的层和它下面一层
     (第 y 层的落脚只来自这一层的矮方块和下面一层顶面超过一格的栅栏、墙,与 `Footing` 找托的两层一致);一带里读过的层是连续一段,再问到外面时向那边长一倍,
     一带最多读四五次、多读的不超过要的一倍。读一次要把快照里每个方块段的调色板问一遍,所以不一层一层各读一次。
   - `forEachBlock` 一次扫描共用一个调色板回调、缓冲用到才建,不再每个方块段、每次调用各建一份。
4. **记事本的表从小起步**(`Recall.Table`):256 槽起步,被顶掉别的格的次数到了槽数就换一张大一倍的空表,封顶仍是 4096 槽。表只是缓存,丢了就现算,槽数多少不改变任何结论。
5. **`Nodes` 的哈希表按进表的节点数长**,不按节点总数长(未核的候选不进表,占节点的绝大多数);**`Contact` 斜走的拐角表**用到才建。

### 没做的

- **估价预计算改惰性**:`Vertical` 本来就是问到哪一带读哪一带,上面第 3 条只是把"一带"缩到问到的那几层。`Burial` 不能惰性——它是从目标往外做的 Dijkstra,
  一个格的值是 `min(它到目标的最短价, 起点的最短价)`,而开搜第一件事就是问起点的估价,要答它就得把 Dijkstra 做到起点;做完了就是现在的全部结果。
- **`Nodes` 分块、不翻倍**:节点数组翻倍留下的垃圾约等于最终容量,分块能去掉它,但每次读写多一次间接,堆的比较与哈希探测都走这些数组。收益在分配上,CPU 上无依据,没做。
- **视线里非整块的轮廓**(草、雪层、台阶……)仍走原版 `clip`:它们的轮廓随坐标偏移、每次现建,没有可缓存的东西,自己重写一遍 `VoxelShape.clip` 是多出一份与原版并行的实现。

| | 改前 | 一层一层各读(含 4、5) | 改后(含连成一段向外长) |
|---|---|---|---|
| 墙钟中位 / P90 | 1.86 / 37.7 ms | 1.94 / 14.6 ms | 1.75 / 14.4 ms |

| nether 墙钟中位 | 21.5 ms | 8.5 ms | 11.0 ms |

读这张表:

- **分配**降了两成;**GC** 降了三到四成,≥ 500 ms 的整堆回收从 3–5 次到 0–1 次。每节点 CPU 只快了 4.5%,与 0035 的结论一样——这条路径主要耗在读方块、查表和堆上,不是分配。
- **小搜索的 P90** 降了六成,**规格 A 的中位**降了一半;规格 B 3 s 的中位两遍里一遍降 21%、一遍持平,0.5 s 档一遍降 4%、一遍高 0.7 ms,噪声(共享宿主,load 约 20)盖过了它。
  改后 hills、mixed 的小搜索里 `Vertical` 现扫快照仍占七成半到八成的时间,其中解开层的 256 格(`decode`)约四成:竖直项是"整份快照里这一层最高的落脚"的下界,要回答就得把这一层所有带这类方块的方块段解开一遍。
  再往下降要么改下界的定义(只看起终点附近),搜索决策会变,不是纯性能;要么缓存解开的层(代价是每次搜索多留 MB 级的数组,这次不做)。
- **TIME 停的搜索的 P90 反而高了 5–10 ms**:搜索每节点快了 4.5%,学习(0039 的 1/16 份额按改前的速度量出)的相对份额略大了一点。份额是实测常数,搜索结构或速度明显变了就重测,这次变化在误差内,不动。

## 后果

- 视线里整块的碰撞判断只剩 `Sight.Line.clipUnit` 一处自己的实现;非整块仍是原版。以后原版对整块的 clip 口径变了(升级版本),`aWholeBlockTargetIsHitWhereVanillaClipHitsIt` 会第一个说话。
- `EditedView.Reusable` 的约定是"装填后上一次的视图作废":调用方只能在一次展开或判断里用它;要留着的视图仍用 `EditedView.over`。
- `Recall` 的槽数是性能参数,不影响结论;`Vertical.Levels.BAND` 只决定一次最多向外长多远,不影响结论。
