## 背景

与 Baritone 的对比(AutoDL,v3 数据集,单次规划,3 s、节点上限 20 万)里,规格 B 有 7 道只有 Baritone 到达(forest-long-034、hills-short-029、
mixed-medium-021、nether-medium-004/019/021/038),规格 A 有 1 道真的只有 Baritone 到达(caves-long-008;另两道 mixed-long-008、nether-short-031
标准答案是区域内无解,Baritone 的"到达"在我们的物理下不成立)。其中 forest-long-034 B 我们的半程终点偏离目标 99 格。另外精确判断(verify)占每节点约 42%,
每展开一个节点判 1.7–2.6 次。

## 一、只有 Baritone 到达的题:不是同一个成因

用 `AStar.run` 在同一份整块快照上换权重、放宽时限与节点上限重跑(同一台机器、一个 JVM 一道题):

| 题(规格) | 权重 4 | 权重 2 | 权重 1 | 成因 |
|---|---|---|---|---|
| forest-long-034 (B) | 到达,11.7 万展开 | 到达,1.5 万 | 到达,6.0 万 | 估价洼地(见下) |
| hills-short-029 (B) | 到达,4.0 万、1.45 s | 11.2 万 | 26 万 | 评测那次撞上 JIT(`jitMs` 6232、CPU 只占墙钟 44%),单跑 3 s 内到达 |
| caves-long-008 (A) | 到达,8.6 万、2.1 s | 13 万 | 44 万 | 同上,单跑 3 s 内到达 |
| mixed-medium-021 (B) | 到达,15.6 万 | 33 万 | 53 万 | 要挖穿 34 格,展开数靠近 20 万上限,是每节点速度 |
| nether-medium-004/019/021/038 (B) | 到达,10.8–22.5 万 | 17–53 万 | 23–102 万 | 同上,地下挖穿,估价只有真价的 1/6–1/4(h0 212 对真价 1241) |

**forest-long-034**:起点 (307,43,96) 在一个封死的洞里(地表约 y=65–70),终点在地表 (409,69,199),竖直差 26 格。洞里的水平走向离目标越来越近,
估价(直线下界加竖直项)只会说"沿洞往前更近";真正的出口在起点附近往回的斜坡。权重 4 下开放集按 `g + 4h` 排,洞里死胡同的键比回头的出口低,
要把整个洞的体积搜完才轮到出口;3 s 的 3.7 万到 5 万展开不够,半程停在洞的尽头(偏离 99 格)。权重 2 时同一条题 1.5 万展开到达。
这是加权 A* 的估价洼地(heuristic depression),不是学习、半程选择或走法缺失造成的:单次搜索里没有学习,走法全都在(权重 1 能走出同一个出口)。

**没有修**:通用的出路只有三条——降权重、洼地回避、按洞口分段。权重 4 是 0033/AStar 里在 dev 上扫 2 到 8 的结果(规格 B 到达 256/255/261/267/266/270),
为这一道题降权重等于换掉一个整体取舍;洼地回避 0027 试过不采纳。没有新的证据支持改其中任何一个,不改。其余几道是每节点速度或 JIT 噪声,
对应的是 0035、0040 的每节点成本,不是搜索决策。

## 二、精确判断的账(dev,664 趟,按走法与快判断的返回位置统计)

改前每趟的精确判断共 4917 万次,按结果分:

| 结果 | 次数 | 占比 |
|---|---|---|
| 成立,落点成了新节点或更便宜的节点 | 2170 万 | 44% |
| 成立,但落点那一格已有不比它贵的节点(关系 `relax` 里 `nodes.g[next] - g <= MIN_IMPROVEMENT` 或节点已展开),白判 | 1846 万 | 37.5% |
| 不成立 | 900 万 | 18% |

- 白判里最大的一块是 `SWIM`(1002 万次,占 SWIM 判断的 68%):水里每格有几个憋气档的节点,多条等价路径到同一格同一档;
  搜索前的"落点已有不比它贵的节点"只查憋气最宽裕的 0 档(`settledNode`),查不到这些。要在判之前拦下,得先知道候选落点的憋气档,
  那取决于这一步是否整步泡在水下与耗时,在精确判断之前不知道。
- 其次是快判断乐观价太低造成的:`WALK` 挖、垫(10.1M 次通过里 719 万比乐观价贵十刻以上,垫桥要探身潜行,慢十来刻)、`ASCEND`、`PILLAR`、
  非平地节点上的 `DIAGONAL`。乐观价低只让它们多排一次堆(贵了按真价放回去),判断本身是要做的;它们之中 `WALK` 垫桥有 230 万次在判完才发现落点已有更好的节点。
  乐观价不能抬:垫桥是站着点得中还是要探身,取决于落点邻格的几何(落点下面有块时站着就点得中),快判断不读这些。
- 被拒的 900 万:`FALL` 259 万(几乎全是落进下面的岩浆湖/摔不起)、`DIAGONAL` 142 万(落点那一列身体占的格里有整块)、`WALK` 167 万、
  `DOWNWARD` 89 万(挖掉脚下那块,再下面是空的)、`ASCEND` 105 万。

### 试过:收紧快判断(没有采纳)

按这几处各加一条"当场不成立"的判断(都由精确判断里同一个前提推出,保持乐观,`QuickTest` 通过):

- `Drop`:落点那一列往下头一个说不清的格以上都是空的、落点待得住、站着落地摔不起、不是水、身上没有水桶接——不成立;脚下一格是整块先于身体占的格判;
- `Downward`:平地上挖掉脚下那块,再下面是空的——不成立;
- `Diagonal`:落点那一列身体占的格里有整块,而节点不平(快判断原来答"可能")——不成立;
- `Walk`:不许挖而落点那一列身体占的格里有整块;脚下没东西托(也不是水里梯子上能挂住的)而不许放或站不稳——不成立;
- `Ascend`:不许挖而台阶之上、起步头顶有整块——不成立。

结果(同一台机器、同一批题):

| | 改前(8a0ffa290) | 收紧后 |
|---|---|---|
| dev 精确判断次数 | 4917 万 | 4344 万(−11.7%) |
| 其中不成立 | 900 万 | 500 万 |
| v3.1 dev 到达 | 575 | 575(water-medium-012 B 成功变失败;forest-long-023 B 失败变成功) |
| v3.1 held 到达 | 755 | 755(mountains-medium-013 B 成功变失败;nether-medium-021 B 失败变成功) |
| 真墙钟每节点 CPU(规格 B 3 s,展开 ≥ 1000,中位,各跑两遍交替) | 15.68 / 15.45 µs | 15.71 / 15.79 µs |
| 同批每节点分配 | 6406 / 6544 B | 6386 / 6351 B |
| 真墙钟到达(B 3 s 六块地 720 题) | 632 / 632 | 634 / 635 |

判断少了 12%,每节点 CPU 却没有可量的变化:被拒的判断多半在前几条前提上就失败,本来就便宜,省下的次数没有省下多少时间。
到达持平(逐格各有一进一出,是计数时钟的"想多久"随判断数变了之后分段的重排)。没有可量的收益,按"做不到就不收",**代码全部撤回**,不留在树里。

## 后果

- 想再压 verify 的耗时,该看单次判断的成本(`Draft`、`EditedView.getBlockState`、`Contact`),不是次数:减掉的 12% 次数几乎都是便宜的失败。
- SWIM 的白判(占全部判断的 20%)要有"候选落点的憋气档"才拦得下;如果以后水里的搜索成了瓶颈,从这里下手(在 `Breath` 里给出一步之前就能算的憋气档上界)。
- forest-long-034 这类"出口在回头路上"的洞,等有了新的估价手段(按洞口/连通性的估价)再谈;降权重不是不花代价的。
