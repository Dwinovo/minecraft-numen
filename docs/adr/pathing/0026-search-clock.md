# 0026 时钟端口:每次想多久看时钟,放不放弃看节点

- 状态:已接受;取代 0010,与 0006 的教训一起读
- 日期:2026-10-28

## 背景

0006 按墙钟给预算,结论随机器负载漂移,"没有路"时有时无;0010 改按节点数,结论可复现,但慢机器上首段要等很久(冷 JIT 真机 234µs/节点),
快机器上空着时间不用。我们真正在乎的是时间:多久开始动、每刻占服务器多少。

## 决定

1. 搜索只问"时间到没到"。时钟是端口,由宿主注入:
   - 正式运行:真实时钟,每 64 个节点看一次表;
   - GameTest、靶场、单测:假时钟,按展开的节点数折算。同一份搜索代码,测试逐字节可复现。
   注入只有一个接缝,不用全局可变静态,公共代码不判断运行环境。
2. 三种时限:
   - 首段:下令后第一次搜索,短(几十毫秒,靶场定),时间到交半程,身体立刻动;
   - 接续:半程一交出就从半程终点在后台接着搜,时限是"身体走到半程终点前还剩的时间"减余量,有上限;
   - 单次搜索节点上限:只防内存,按每节点内存量定。
3. **放弃不看时钟**:一趟的收场只认"搜索证明到不了"或"这一趟的节点总数用完"(按起终点估价定)。时钟只决定每次想多久。
4. 接续搜不出时,下一次加大时限,直到节点总数用完。这是我们自己的设计:Azalea 找不到路时以同样的时限反复重试(源码 0d38e0d),不加时。
5. 多个同伴:沿用唯一的派发口,首段优先于接续;每次搜索带截止时间。

## 依据

Baritone(首段 500/2000ms,走路时下一段 4000/5000ms);mineflayer-pathfinder(每刻 40ms、总 5s,半程边走边续);Azalea(超时交半程,无解按同样时限重试)。

## 后果

- 真机上同一请求每次想到的深度可以不同,路线可以不同;到不了的判定与机器快慢无关。
- 日志照记节点数与耗时;复现真机问题时在测试里用假时钟按日志里的节点数重放。
