# 0030 一趟分两半:规划的 `Trip` 与执行的 `Driver`

- 状态:已接受
- 日期:2026-10-30

## 背景

`Driver` 一个类里有两件事:一件是怎么把一趟走完的规划(搜索怎么派、搜到哪交出、接着往下搜、总预算、这一趟的记忆、什么时候收场),
一件是身体怎么执行它(认步、驱动正在走的一步、停稳)。规划那一半其实不碰身体——它要的只是起点在哪个节点、读哪份世界快照、按哪份成本模型——
却因为和执行写在一个类里,只能带着一具真身体才跑得起来。这挡住了两件事:评测要把成千上万道题的整趟规划(分段、交接、续算)跑一遍,而不是为每一道题起一台服务器、
放一具身体走路;评测里另写一份分段的串法,又会和 `Driver` 的真实做法慢慢漂开。

## 决定

按 Nav2 等把全局规划与控制器拆开的做法,把规划那一半抽成 `drive/Trip`,`Driver` 只剩执行:

- **`Trip`**:搜索的派发与收结论(`fromBody`、`continueAhead`、`poll`)、路线与进度(`Course`)、接续(`Continuation`)、总预算与每次想多久(`Allowance`)、
  这一趟的记忆(`TripMemory`)、换目标(`retarget`,只问 `Goal.keepsStop`)、重搜的记账与日志(`replan`)、收场的判断(`Halt`)。
  `poll` 的结果(`Trip.Event`)告诉执行:路线没变 / 接长了 / 换了新路线 / 扔掉了 / 收场了。
- **`Trip.Ground`**:`Trip` 向身体与世界要的东西,一共四样——为从某个节点出发的搜索拷的世界快照、此刻的成本模型、身体此刻稳稳站着的节点与站法、
  日志里身体的样子(外加一个可选的"派发在主线程上用了多久"的回调)。`Driver` 用活世界与真实的身体实现它;评测用一块存档与一具虚拟的身体实现它。
- **`Driver`**:认步(`Tracker`)、驱动正在走的一步(`Step`)、到达(`Arrival`)、下载具、对外交出状态与收场。它在执行里遇到的"这一步走不通"等原因,
  经 `Trip.blocked`、`Trip.replan` 记账——重搜的原因仍只有 `Journal.Replan` 那几种、仍在一处记账。

## 行为不变

这是纯结构改动,行为逐位不变。证明:同一份提交前后,在固定存档的靶场 `numen_pathing_terrain` 上各把 30 条路线真走一遍,记下来的每个字段(除墙钟字段)比对。
B 规格(出厂,可挖可垫)三遍前后逐位一致。A 规格(不挖不垫)的 `broken` 与 `rock_far` 两条在拆分之前本身就跑一遍变一遍(八遍基线里 `broken` 出了六种价,
`rock_far` 的第五次搜索展开数在 106579 与 106582 之间跳),拆分之后落在同样的分布里,其余 28 条逐位一致;它们的跳动不来自这次拆分
(怀疑是真服务器上随机刻让方块变了样,没有深究)。

## 后果

- 评测可以只带 `Trip` 与一具虚拟身体跑整趟:路线数据定每步要走多少刻,接续的时限走真实的 `Trip.aheadTicks → Allowance.next`,不再另写一份串法(ADR 0031)。
- `Driver` 不再握着搜索的任何状态;`Trip` 不碰身体、不碰 `ServerPlayer`。
