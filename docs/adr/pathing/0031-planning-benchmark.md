# 0031 规划评测:大量自动出的题 + 分档 + 标准答案

- 状态:已接受;取代 [0013](0013-terrain-range.md)(手挑路线的靶场)
- 日期:2026-10-30

## 背景

0013 之后寻路一直在一块固定存档上的 27 条手挑路线上调参、判对错。题是人按勘测表挑的,调的权重、时钟、分段常数都是对着这 27 条拟合出来的:换一块地就不知道对不对,
删一个机制、比两个版本也没有尺子。方法学上这是"在少数几题上调参再在同样几题上报分"(调参集即评测集),文献里的做法是反过来
(Moving AI 栅格基准、体素基准、GPPC、MotionBenchMaker):大量程序化出的题、按最优长度分桶、附标准答案、报分位数与置信区间、调参与封存分开。

## 决定

以后改寻路机制、调常数、比版本,只看这套评测。它分三层,本记录定第一层:

1. **数据集**(独立仓库 <https://github.com/Dwinovo/numen-pathfinding-benchmark>,数据放发布附件,不进本仓库):
   - 七块固定存档,都是原版世界生成:`hills`(平地、陡坡、树林、断崖、湖)、`mountains`、`water`、`forest`(密林)、`caves`、`nether`(下界生成器与群系)、
     `mixed`(没见过的混合主世界,整块只进封存)。每块一个区域文件(512×512)。制作与选种见 `numen/pathing/src/gametest/terrain/README.md` 与数据集的 README。
   - 题库 `problems/<地块>.jsonl`,一行一道题:起点、目标、距离档、规格 A/B 各一份标准答案、标签、dev 或封存。
   - 版本与校验码记在 `numen/pathing/build.gradle`(`pathingDatasetVersion`、`pathingDatasetSha256`),`fetchPathingDataset` 下载、核校验码、解到构建目录;
     本地调试用 `-PpathingDataset=<目录>`。数据集目录是唯一入口:出题、评测、对比都从这一个路径读。
2. **出题**(`benchmark/Generate`,手动跑一次,结果进数据集;只依赖地形,**不需要标准答案**):
   - 在每块地上按固定随机种子撒点。起点七成在地表(含水面)、三成在洞穴地面(下界没有地表,什么站得住的格都算);终点按种类取:地表四成半、洞穴两成半、
     封闭的地下空腔一成、封闭在实心里的一格两成。洞穴是连着大片空间的地面,空腔是六邻接泛洪不到 4000 格就到头的一团。目标种类照模型实际会下的令:
     走到某格、走到某格附近 r 格内(跟随,r 取 2–5)、挖到某格(只对封闭的一格)。
   - 按起终点**三维直线距离**(含高低差:深处的终点自然落进远的档)分三档:短 ≤32、中 32–128、长 128–400。分档与价钱模型无关,题目永远稳定。起终点离区域边缘至少 64 格。
   - 规格两种,同一道题两种都跑:A 不挖不垫(`RouteSpec.defaults()`);B 出厂规格可挖可垫、只看价钱(`edit().changes(true)`)。
   - **平凡题**不进题库,判据是几何的,与任何搜索算法无关(`benchmark/Straight`,只此一处):起终点之间的直线按列走(水平方向每一格一列,取整),
     每一列在上一列的脚高上下一格内找站得住的格;全程找得到、都是站在实地上(没有水)、斜着换列时两边的邻列在脚和头的高度上没有实心方块挡着(切角过得去),
     就是"明摆着一路平走过去"。直线上的事实同时给报表标签:有水(`water`)、不平稳——有高于一格的台阶、没有地面的列或切角过不去(`rough`);
     另有终点被封死要挖才进得去(`dig`)与终点在地下(`underground`)。标签只看地形与题,不看搜索结果(也就不再有"要垫"这个标签:搭桥垫柱是搜索的选择,
     不是题的性质,近似的是 `rough`)。
   - **不适用于 A**:规格 A 不挖不垫,需要编辑才做得成的题——挖到某格,和走到封死的空腔、封闭在实心里的一格——按构造不适用,出题时就分出来
     (`Problem.applicable`),数目与理由记进 manifest,评测不给 A 跑,也就不会被当成失败。
   - 每块地每个距离档收 40 道题;分 dev 与封存按题号哈希五五开,`mixed` 整块封存。封存的只在定版前跑。
3. **标准答案**(`benchmark/Reference` 与 `benchmark/Answers`,单独一步,不属于出题):
   - 求解器就是真实的搜索——同一个 `Search`、同一套 `Moves`/`CostModel`/`Goal`,在整块区域的快照上一次搜到底,不分段、不限时、不带这一趟的记忆、不沿旧路,
     权重 1(`AStar.run(search, 1.0, …)`;权重原来是 `AStar` 里的常量,现在是搜索的参数,生产调用仍是 `AStar.WEIGHT`)。放弃的条件只有一个:展开节点上限
     `NODE_CAP`。权重 1 搜到了就是最优价(`optimal`);搜完了没有目标是证明过的无解(`unsolvable`);上限用完了没有最优解可记,改按生产权重再搜一遍取一个已知的上界
     (`best-known`,次优比只作参考);再搜不出就是 `unknown`。次优比 = 我们路线的价 ÷ 最优价,价钱按我们自己的成本模型计;Baritone 不进这套评测
     (它有些走法我们的模型算不出价)。
   - 慢,所以是独立的命令:`Answers solve <数据集目录> <分片目录> [--shard i/n]` 把"题 × 规格"按题号排序取第 i 份、每算完一条追加写进分片文件、重启时跳过已有的;
     `Answers merge` 把分片并起来、按题号排好、记下算出它们的主仓库提交,写进数据集的 `answers.jsonl` 与 `answers-manifest.json`,并报每题的 CPU 成本。
     只要 Java、构建好的评测类路径和数据集目录,在 Linux 的 CI 或租来的机器上原样能跑;并行度按堆装得下几个求解器定。成本模型改了就重算、发数据集小版本。
   - **没有答案文件是正常状态**:评测照跑,报表里没有次优比这一列;有答案文件时报表头写明它是哪个提交算的。成功率、起步耗时、单次最长思考、展开数都不依赖答案。

**规划评测**(`benchmark/Bench`,纯 JVM 程序,不要服务器、不要 GameTest):

- 路径是 读存档 → `WorldSnapshot` → `Trip` → 结果。`RegionWorld` 是 `WorldSnapshot.Sections`(给快照取方块段的来源):区域文件用原版的 `RegionFile`/`NbtIo` 读,
  方块段用与原版区块序列化器同一份调色板编解码(`PalettedContainer.codecRW`)解开,生物群系用从原版数据包读出的真注册表,没有手写的 NBT 或调色板解码。
  原版引导(注册表加标签)是单测的 `Vanilla`,单测与评测共用,放在 `fixtures` 源码集里。
- 一趟是真实的 `drive.Trip`(ADR 0030)加一具**虚拟身体**(`Rehearsal`):身体不走,按交出的路线推进;路线上每步走多少刻是 `Course.minimumAt`,
  接续的时限走真实的 `Trip.aheadTicks → Allowance.next`,什么时候能走由 `Trip.settled` 定,评测里不重新判断 `Trip` 判过的任何事。
- 时间按搜索表折算(`SearchClock.PER_EXPANSION`、`PER_CHECK`、`PER_COLUMN`,与测试服务器上的 `STEADY` 同一套系数),不是墙钟:同一份代码、同一批题,
  跑几遍结果逐字节一致(只有 `meta.json` 里的耗时是墙钟)。题之间在线程上并行,每题的搜索仍经 `Searches` 的线程池,结果与线程快慢无关。
- 指标(每行 `Row`):到没到与怎么收场、起步耗时(下令到交出第一段)、单次最长思考、站着等搜索的总时间、整趟耗时、搜索次数与展开数、
  死路重搜与重规划次数、路线价、挖与垫的块数、次优比(有答案文件时);证明到不了的题记证出来用了多久。
- 结局三类(`Row.Outcome`):**到了**;**证明到不了**——第一次从脚下搜(这一趟还没有记忆、世界是原样)就把能走到的都搜完了没有目标(`Stop.EXHAUSTED`)。
  这不是"区域边缘截断":搜索只要有一步读到快照之外没加载的列(区域边缘、快照半径的边),停因就是 `UNLOADED` 而不是 `EXHAUSTED`,所以 `EXHAUSTED` 是整个可达集合都在已加载的
  区块里搜完了;**放弃**——别的一切(总预算用完、路伸出了区域、重搜之后才搜完、执行里走不下去)。成功率 = 到了 ÷ (到了 + 放弃),证明到不了的不是规划的失败,不进分母,单独报数量与证出来用了多久。
- 报表(`Report`)主表按 规格 × 档 × 终点种类(地表、洞穴、空腔、封闭的一格)分组,次表按 规格 × 档 × 标签(水、崎岖、挖、地下),总表只作补充。每组报三类结局的数、成功率与 Wilson 95% 区间,
  起步耗时、单次最长思考、展开数、次优比(有答案文件时)各报中位 / P90 / P99 / 最大,挖垫块数报平均。对比工具(`Diff`)给两次结果,列各档指标的变化、成功变失败与失败变成功的题、次优比变化最大的 20 道。

## 评测里做的假设

题只由"题 + 规格"决定,下面这些不随题变,都写死在 `Spec` 里:

- **身体**:原版生存模式的玩家(单测用的同一份 `Vanilla.SURVIVAL`:宽 0.6、高 1.8),满血 20、吃饱 20、满氧气 300,没有药水与属性加成,背包第一格一把钻石镐,其余空。
  A 与 B 同一具身体,差别只在规格。
- **垫路料**:身上带着圆石(`Materials`),A 不垫所以不用。**许可**什么都放行,**没有要避开的生物**(`Threats.NONE`)。
- **加载的区块**:区域里的 32×32 个区块都在,区域之外都没有。搜索快照与真实运行同一个半径(`WorldSnapshot.SEARCH_RADIUS`,以派发点所在区块为中心),
  标准答案求解器读整块区域的一份快照。区域边缘的搜索停在边上(`Stop.UNLOADED`),与真服务器上区域外没加载的区块一样;起终点离边缘 64 格,所以正常的题不碰边。
- **世界不变**:虚拟身体不挖不垫,接续的搜索读的世界叠上了路线的改动(`Trip` 自己做的)。方块实体、实体、随机刻、水流都没有。
- **到达**:路线终点在目标里就算到,不做到达后的视线判定(`Arrival`)与脚下打滑、被推出路线、卡住、看护判卡住——这些要身体,留给真走评测。
- **存档的数据版本**必须是当前原版的,不做数据升级。

## 不在这一层的

真走评测(带身体,量重规划、卡住、掉血、主线程每刻耗时、实际价与规划价之比)与变化世界评测(中途改世界)需要身体,仍在 GameTest 服务器里,在 dev 里抽样跑;
用 dev 题重跑精简审计的各开关也在后面。27 条手挑路线、`TerrainGameTests`、`TerrainSuite` 与 `terrain/hills` 存档(已进数据集)随这条记录删去;
三条"悬空搭的硬挡场地"(禁区挡道、方块不够过河、没有镐挖黑曜石)是检查收场原因对不对的功能测试,不是评测,挪进了日常 GameTest(`TerminationGameTests`)。

## 后果

- 调参、删机制、比版本都用同一套题:`./gradlew :numen:pathing:pathingBench`,改前改后各一份 `results.jsonl`,`pathingBenchDiff` 出对比。
- 封存集只在定版前跑一次;调参时看 dev 的分档表。
- 数据集有版本:成本模型改了标准答案就过期,重出题、发小版本、更新这里的版本与校验码。
