# 0035 搜索热路径减分配;评测时钟系数不改

- 状态:已接受;[0026](0026-search-clock.md) 的 `SearchClock.STEADY` 系数不动
- 日期:2026-11-01

## 背景

游戏里每次搜索的时限是墙钟,节点更快就是同样时限里搜得更多、半程更好、更少放弃。主流(Baritone)的热路径不按步建对象:可变坐标、预取的上下文、静态判断。
先量热点,再去掉热路径上每步的对象分配,**不改任何判断逻辑**。

## 热点(本机、单线程、dev 每档取几道、生产权重 4、节点上限 10 万,JFR 加 `ThreadMXBean`)

每展开一个节点分配约 7.7 KB。采样占比按分配点(第一个 `pathing` 帧):

| 分配点 | 改前 | 改后 |
|---|---|---|
| `Quick.nothingToClick`(`Optional`、不可变 `BlockPos`、`Faces.against` 的六个邻格 `BlockPos` 与方向数组) | 约 6.5% | 约 1% |
| `AStar.recentEdits`(合并几步改动的 `ArrayList`、`addAll` 的 `toArray`) | 约 5% | 约 0 |
| `ToolChoice.best` 每次查表现建的方法引用(经 `CostModel.tooHard`/`digFloor`) | 约 5% | 0 |
| `Footing.highestTop` 每格一个 `BlockPos` | 约 3.5% | 约 1.5% |
| `Strides.inWater` 遍历 `EnumSet` 的迭代器 | 约 1% | 0 |
| `EditedView.over` 的 `Changes`(`long[]`、`BlockState[]`) | 约 5% | 约 6%(未动) |
| `Nodes.grow` 各平行数组翻倍 | 约 10% | 约 10%(未动) |
| `Stepping.samplePoints`/`Walk`、`Draft.uncover`/`bridging` 的 `Vec3`、`double[]` | 约 8% | 约 8%(未动) |

CPU 上没有单一热点:去掉快照懒解码(每个新快照只付一次)之后,自身耗时最多的是 `Probe.getBlockState`、`settledNode`、`recentEdits` 的父链、堆的下沉,各 2–4%。
每个精确判断里 `DigTime.ticks` 约占 5%:`CostModel.digFloor`/`tooHard` 对同一个方块状态每次都重算,而挑工具时已经算过同一个数。

## 改了什么

- `ToolChoice`:方法引用做成字段;`Pick` 带上挑选时已比出的 `floorTicks`(脚踏实地、眼睛不在水里),`ticks` 在这个情形直接用它(同一个函数、同一件工具、同一个状态,值逐位相同)。
- `CostModel.placing()` 直接返回可空的 `Block`,不包 `Optional`(规划一步问几十次)。
- `Faces.against` 用一个可变坐标走六个邻格、方向数组只取一次;新增 `Faces.anyAgainst`(找到第一个能点的邻格就停),三处"只问有没有面可贴"的地方改用它。
- `AStar.recentEdits` 合并几步改动时复用一块缓冲(调用方只在一次展开或判断里用,不留着)、按下标放入。
- `Footing` 一次测高度共用一个可变坐标;`Strides.inWater` 用预先合好的位掩码。

没动的:`Nodes` 的数组翻倍是摊销的,`EditedView.over`、`Stepping`、`Draft` 里的小对象要重写调用约定,每项收益在 1–3% 内,不值得动逻辑。
0034 试过"节点不存 `Maneuver`、交路线时重判"做不到逐位不变,这次没碰。

## 行为逐字节不变

同一棵树前后各跑一遍 `pathingBench`(v2 数据集,计数时钟),`results.jsonl` `cmp` 相同:
dev 668 行 md5 `986fe04426d95cf8c3504bf1a7e1dcc2`,封存 883 行 md5 `3896049328b2b681f62043dae2d16a0d`;`pathingBenchDiff` 两个集合全 0。
另外 132 次整题搜索(每档每地块几道,权重 4)的(停因、展开数、精确判断数)改前改后逐行相同。

## 提速

| | 改前 | 改后 |
|---|---|---|
| 整块区域快照上的搜索,每展开墙钟(含 2.7 次精确判断) | 13.2 微秒 | 12.0 微秒(−9%) |
| 同上,每展开分配 | 7737 字节 | 6651 字节(−14%) |
| 评测整趟(新快照、估价预计算、整趟,223 趟,每版两次交替)每展开墙钟 | 17.9 微秒 | 16.8 微秒(−6%) |

分配少了 14%,墙钟只快 6–9%:这条路径主要耗在读方块、查表和堆上,不是分配。

## 时钟系数不改

`SearchClock.PER_EXPANSION` 4 400 ns、`PER_CHECK` 2 700 ns 不动。这次也量了一遍,数字如下,只作记录。

- **这次实测**(本机 Windows 11、JDK 21、ParallelGC,单线程、机器空闲):dev 每三道取一道(规格 A、B 合计 223 趟),走真实的趟逻辑(`Rehearsal`),每次搜索记墙钟与(展开数、精确判断数),
  按趟求和后无截距最小二乘。改前 17.3 / 0.55 微秒,改后 15.7 / 0.8 微秒;拟合总量比实测高 4%;R² 0.88,单趟中位相对误差 86%;每展开伴随 2.38 次精确判断,几乎不随趟变,两个系数分不开,可信的只有合计。
  旧系数在这个口径下只有实测的 61–64%。
- **口径差异**:旧系数是 10-29 在靶场上对"只搜索"的墙钟定的;这次的口径是整趟,含新世界快照的懒解码与估价预计算,这些读方块的活不在"展开数、精确判断数"里,被摊进了系数。
  同一份代码,"只搜索"口径(整块区域快照上、热身后)每展开 13.2 微秒,整趟口径 17.9 微秒,差三成多就是这部分。
- **为什么不改**:
  - 计数时钟的用途是在版本之间做可复现的比较,系数是固定的折算口径,不是对真机的预测;换系数等于换尺子,所有基线(0031 起的 dev/封存数、本 ADR 之前的各 ADR 表)都要重来,不是提分。
  - 系数跟机器走(这是一台开发机),而且两个系数在数据里分不开、单趟误差大。
  - 系数变大,GameTest 测试服务器上每次搜索的深度变浅(同样的 200 毫秒时限只搜约三分之一的节点):按这组系数在 Fabric 上跑 GameTest,
    `forest_plants_a_vanilla_tree_in_a_column_without_touching_the_world` 红过一次(最后几格放不下、总预算用完),旧系数下整套通过。树形随场地坐标变,同树的对照没做到,是否因果没有定论。
  - 评测在新系数下(dev 到达/放弃 507/34 → 506/35、封存 701/45 → 697/47,起步 p90 59.7 → 138.6 ms)只是换了一把更严的尺子,不反映代码变好变坏。
- **以后若要重标**,前提:固定口径(只搜索还是整趟,先定下来写进注释)、在目标服务器上测、多台机器取合计,并同时重跑所有基线、重过 GameTest。
