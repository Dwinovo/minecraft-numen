# 0003 缺的那半个客户端:代答握手,对外是真玩家

- 状态:已接受;界面与只在客户端的数据怎么拿,还在讨论
- 日期:2026-09-20、09-24
- 提交:`8c93cc984`、`0a705fc21`、`3415a11be`

## 背景

服务端玩家(body 0001)只有服务端那一半,两类问题跟着来:
- 服务端有几处要等客户端回执的握手。跨维度之后原版等她答传送编号,没人答,她就一直卡着(09-20 真机)。
- 有的模组按"是不是假玩家"区别对待。FTB Quests 经 Architectury 问 `isFake`,答"是"就不让她参与任务线。

## 决定

- **只代答服务端真正在等的握手**:mixin 在她连接唯一的下行出口把包给 `FakeClient` 看一眼再丢;它代答传送编号(1.21.1 里只有这一处真在等)。
  原版 `ServerGamePacketListenerImpl.tick()` 不直接跑:它是为客户端权威的身体写的,跑它等于每刻把她拽回原地。
- **对别的模组她是真玩家**:Architectury 问她是不是假玩家时答不是(窄 mixin,单独一份配置,只在 Architectury 在场时挂上)。
  她和主人同队一起推进任务,奖励进她的背包要报告给模型。

## 后果

- 原版某个状态"永远不清"时,先查是不是一次没人回的握手,是就加进 `FakeClient`,不在业务层兜底。
- 界面与只同步到客户端的数据(例如 1.21.2 起配方不再全部同步给客户端)还没有定法。10-05 讨论过三条:协议层把"打开界面"的下行包翻成窗口、
  借主人客户端托管她的真界面并读旁白控件树、每个智能体一个真无头客户端;用户曾希望有无头客户端,没有定。
