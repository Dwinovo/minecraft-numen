# 0008 她在不在线跟着"主人在不在"走:召唤、下线、删除

- 状态:已接受
- 日期:2026-11-11
- 修订:`docs/input-pipeline.md` 10-18 "主人下线照旧收拾她(收程序、停在 `AWAY`)"——那一条只定了大脑,这里补上身体
- 另见:body 0001(身体是服务端玩家)、body 0005(区块加载照真玩家)、body 0006(重生照真玩家)、runtime 0001(两个大脑)、issue #155

## 背景

主人下线时,她的程序被收掉、内脑待命(`OwnerPresence.collect`),身体却留在世界里。没有人驾驶的身体照样占着区块加载、身边照常刷怪、
会被打死掉一地装备,还算进原版的睡觉人数,别人跳不了夜(issue #155)。

主人想让她离开只有"遣散"一条路:身上的东西按死亡掉在脚下,名册除名,她的家(对话、札记)整个删掉。玩家把它当"下线"用,结果是不敢用。

带着东西离开世界的那一半其实早就有:`Companions.dormant` 存档离场、`Companions.bringBack` 按 `.dat` 原样回来,主人登录时名下的同伴靠后者恢复。
缺的是规则——什么时候该在、什么时候不该在——以及一个入口。

## 心智模型

**她是服务器上的一个玩家账号。** 名册(`CompanionRegistry`)里有她 = 这个账号存在;身体在世界里 = 这个账号在线。
背包、装备、位置、骑着什么,都在原版给玩家的那份 `.dat` 里,在线不在线都是她的。

对这个账号只有三个动词:

| 动词 | 是什么 | 东西 | 她的家(对话、札记) |
|---|---|---|---|
| 召唤 | 建号;已有的号则上线并来到主人身边 | 原样 | 原样 |
| 下线 | 登出 | 随 `.dat` 留着 | 原样 |
| 删除 | 销号 | 掉在脚下 | 删掉 |

**在不在线是算出来的,不是记出来的。** 她此刻该不该在世界里只由三件事决定:

```
该在线 = 名册里有她  且  主人在场  且  没有被留在外面
```

- **主人在场**只有一个出处:`OwnerPresence.present`——他人在游戏里,或他的外部大脑连着,或渠道上他的一句话正被处理。
  意思是"此刻有人能驾驶她"。没有人能驾驶的身体不留在世界里。
- **被留在外面**有两种原因:主人让她下线了;服务器把她请出去了(`/kick`、插件)。两种都等主人再召唤,期间谁也不替主人把她带回来。

世界的样子与"该在线"不一致时,由一处对账把它修过来:该在而不在的带回来,不该在而在的登出。登入、登出、外部大脑连上或断开、
来访开始或结束、主人下令,这些都只是"重算一次"的时机,它们自己不决定她的去留。

## 决定

1. **身体的出勤跟着主人在场走。** 主人不在场时她登出,在场时她在线。外部大脑连着就算在场:主人下线而外部大脑还连着,她留下由它驾驶;
   主人不在游戏里、外部大脑这时连上来,她被带回来。外部大脑"连着"的宽限(有请求在飞,或 120 秒内出过声)沿用 `McpPresence`,这里不另设。
2. **判据一处、对账一处。** "该在线"是一个不碰 Minecraft 的纯函数(名册条目、主人在不在 → 该不该在),可单测。
   对账读名册与玩家表,把一位主人名下的同伴修到该有的样子。所有时机都调它,不各自带回或登出:
   主人登录时的恢复(现在的 `respawnAllOwnedBy`)并进对账,不留两条带回的路。对账仍排到登录之后的下一个服务端刻(原因见 `Companions.scheduleRestoreFor`)。
3. **下线就是真玩家登出。** 走原版 `PlayerList.remove`:存 `.dat`、公屏"离开了游戏"、骑着的坐骑照原版处理。回来走 `placeNewPlayer`:
   公屏"加入了游戏",落在 `.dat` 里的位置。不传送,不动背包。
4. **"留在外面"在名册里只有一个状态,带原因。** 主人下令的与服务器请出去的是同一个状态的两种原因,不是两个各自为政的标记。
   旧存档里的 `removedFor` 读成"服务器请出去"。主人召唤她,状态清掉。服务器请出去的,主人上线时照旧告诉他;主人自己让下线的不用告诉。
5. **入口照三个动词。**
   - `/numen player summon <名字>`:不变。被留在外面的她由此回来,来到主人身边(召唤一直是这个意思)。
   - `/numen player despawn <名字>`:改为下线。面板上的 ✕ 同样改为下线。
   - `/numen player delete <名字>`:删除,即原来的遣散(东西掉在脚下、名册除名、她的家删掉),行为不变,只换名字。面板上放在比 ✕ 深一层的地方,要确认。
   - 外部大脑的 `delete` 仍是删除。
6. **她要知道。** 回到世界时给她一条事件:因为什么离开的(主人不在场 / 主人让她下线)、过了多久、此刻在哪。
   离开时不另发——她下线期间没有回合,一条回来时的事实就够她接上。
7. **默认如此,不设开关。** 不提供"主人不在也留在世界里"的选项;有人确实需要再议。

## 后果

- issue #155 的三件事一起解决:主人下线后不留人、有带着东西的下线、不必拿删除当下线用。
- 她不在线时不算睡觉人数。主人在线时她仍算,和任何一位在线玩家一样:让她去睡,或让她下线。不改原版的睡觉计数。
- 主人不在时她不再加载区块。拿她当挂机假人的用法没有了。
- 她进出世界会在公屏出现"加入了游戏 / 离开了游戏",和真玩家一样。
- 渠道来访没有宽限:一句话把她带回来,处理完她又登出。渠道聊得密会让她进进出出;到有渠道插件实际在用时,在 `Visits` 那一侧给来访加宽限,不在这里绕。
- 外部大脑的召唤要主人在游戏里才成立(`ServerActuator.asOwner`):被主人下令下线的她,主人不在游戏里时外部大脑叫不回来。这是"等主人再召唤"的本意。
- 下线这条路比以前走得多。它在混合端上有已知的链接问题(issue #163,Paper 的 `PlayerList.remove` 返回类型不同),Paper 端发布前要先处理。
- 命令 `despawn` 的含义从"永久遣散"变成"下线":老用户照旧输入只会让她下线,不会丢东西。原来的含义挪到 `delete`。
- 回归用例只守这条规则的几个面:主人不在场她就不在玩家表里且背包原样、回来在原地;外部大脑连着时主人登出她留下;
  主人让她下线后登录不带回、召唤才回;删除照旧掉落并除名。
