## 背景

最早的设想是"免配置版的 Voyager":玩家在客户端装一个模组,AI 调 mineflayer 的 API 操控一个角色。mineflayer 接管了客户端与服务端之间收包发包的那段逻辑,
在服务端眼里它就是一个真实的玩家。研究下来这条路有三个问题:
1. 要把整个 mineflayer(Node 写的网络包逆向)翻译成 Java,才给得了玩家免配置的环境;
2. 服务器容不下它:服务器一般会封这类自动机器人,纯客户端的机器人服主管不了,还带来性能开销与玩家之间的矛盾;
3. 很难适配别的模组:要适配一个模组就得把它的网络包也逆向一遍,没适配的模组完全用不了。

代码里第一版的身体是一只生物(05-14 的 `AnimusEntity`,06-12 改成 `PathfinderMob`、自己管主人):移动是往 `MoveControl` 里写速度,
和玩家的物理不是一回事;要点方块、用物品时还得借一个 FakePlayer 去点(06-12 `770f420e4`)。执行层为了让它像玩家补了一层又一层。

## 决定

同伴是一个服务端的假玩家(`ServerPlayer`),和 Carpet 的假人同类:没有通道的 `FakeConnection`,走原版玩家加入的流程
(`placeNewPlayer`:读存档、进玩家列表、加载区块、进世界)。生物那一套任务、寻路、执行整个删掉。

## 后果

- **近乎原生**:原版与沿用原版容器逻辑的模组,她不经适配就能用一点(例如 Mekanism 的熔炉,至少能往里放东西)。区块加载、背包、存档、死亡复活都是原版现成的。
- **服务端好管**:她在服务器上,服主能分配资源、设权限(后来的权限层)。
- 她是服务器上的一个玩家,规划要预测的就是原版玩家的物理,寻路可以照玩家的寻路学(寻路 0002)。
- 她只有服务端那一半:客户端才有的东西(握手的回执、界面、部分只同步到客户端的数据)要另想办法(body 0003)。
- 别的模组会把她当成真玩家对待,也可能按"假玩家"区别对待(body 0003)。
