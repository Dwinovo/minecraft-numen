# 0004 她看到的画面交给客户端画,服务端只出清单

- 状态:已接受,暂缓(10-16 用户定先做完输入管线)
- 日期:2026-10-16
- 提交:服务端光线投射原型在分支 `worktree-agent-a23138761e48f88cb`(不合,留作参考)
- 另见:`docs/input-pipeline.md` §九

## 背景

想让她能看图。服务端大脑与 Paper 服上没有渲染器,于是先试了服务端 CPU 光线投射(贴图照 BlueMap 的办法从 Mojang 下载客户端 jar 取),出了两轮原型与样图:

- 方块是通用的:方块模型是资源里的 JSON 数据,模组方块也能画对。
- 实体与方块实体不是:它们的形状、贴图的选法、姿态都写在客户端的 Java 渲染代码里,服务端没有,只能逐个照抄。
  原版几十种,版本一变就要跟;模组的实体无穷多。BlueMap 也只画方块,箱子、床、告示牌是手做的补丁;Mindcraft 的 prismarine-viewer 只覆盖原版。

用户的判断:补丁太多,维护压力大。

## 决定

- **画面由装了我们客户端的主人那边画**:服务端请求,主人客户端把相机临时放到她眼睛处、画到屏幕外的画布上,图片经上行分片传回。
  游戏怎么画她就怎么看到,模组实体、资源包都自动对。Paper 端同样靠玩家装我们的客户端模组(和 Simple Voice Chat 一样)。
- **服务端只出"看见了什么"的清单**:视线锥内、没被挡住的实体,带类型、名字、距离、位置;不涉及模型,模组实体天然覆盖,主人不在场也能用。
- 服务端光线投射不做。

## 后果

- 主人不在线、没装客户端、或她不在主人已加载的范围里,就没有画面,只有清单。
- 主人那边每看一眼多画一帧;光影模组的兼容要单独处理。
- 依赖输入管线的上行通道,排在它之后。
