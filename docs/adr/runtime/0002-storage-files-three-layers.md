## 背景

数据全搬到服务端([0001](0001-server-agent-two-brains.md)),要定存法。原来各处各写各的:对话 jsonl、收件箱 jsonl、库各自的 JSON,迁移、原子写、坏行处理每处一份。
用户问过要不要 SQLite;也要求存储参考 pi,模块高内聚、低耦合。

## 决定

- **文件,不用数据库。** 要存的全是"按同伴一份、按时间顺序读",没有关联查询,写的只有服务端。
  SQLite 要带各平台原生库,服主边开服边拷世界时库文件可能拷坏,13 条版本分支与 Paper 都要各验一遍。以后真要全文搜索或多服共享,优先纯 Java 的嵌入式库,只换最底层。
- **三层,用组合拼**:
  1. 基础件,新模块 `store`(纯 Java,只依赖 Gson,不认识业务):只追加的日志(带版本的头、记录有稳定 `id`/`parentId`、未知类型跳过但保留、坏行跳过、整份迁移先写临时文件再原子替换)
     与小文档(带版本号的 JSON,读时迁移,原子写)。
  2. 记录格式各管各的,只依赖 `store`,彼此不认识。
  3. 按归属组装:她的存档、服务器配置、玩家的库各一份,用的一方不碰路径。每个归属一条串行写车道,停机排空。
- **对话日志照 pi 的会话格式**,改三处:压缩只写摘要与"从哪条 id 起保留"的指针,不复制;换模型、换思考档位记成记录;插件可写不进上下文的自定义记录。
  不要 pi 的文件锁:服务端单进程,一份数据只有一个写入方。
- **日志不写对话内容**:`latest.log` 服主与托管商看得到,玩家求助又常整份传到公开网站;INFO 级只记编号与摘要。

## 后果

- 磁盘读写全在后台线程;读不能再扫目录,札记改成首次读进内存、之后读写走内存,运行期间手改札记文件要下次启动才读到。
- 旧格式迁移一次;对话日志升到第 4 版。
