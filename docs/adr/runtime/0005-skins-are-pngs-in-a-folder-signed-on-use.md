# 0005 皮肤是文件夹里的 png,用时才签

- 状态:已接受,已落地;修订 `docs/input-pipeline.md` §六原先的"皮肤是一种库"
- 日期:2026-10-21
- 另见:[0004](0004-host-library-is-the-server-directory.md)、`docs/input-pipeline.md` §六

## 背景

皮肤原来是内容库的一种:条目里存原图和 Mojang 签名的数据,新建、改名、删除都在设置页的皮肤库里;图要经系统文件框、拖拽导入,签名要等排队签完才成为一条条目。
玩家想要的只是"把这张 png 穿到她身上";条目、改名、签没签过,都是不属于他的概念。

## 决定

- **皮肤就是文件夹里的 png,文件名就是皮肤名**:每台机器的 `config/numen/skins/`(`NumenPaths.skins()`,客户端与服务端同一个写法,Paper 上是 Numen 的数据根目录下的 `skins/`)。
  玩家只往里放图,没有新建、改名、删除。客户端列自己机器上的("我的"),服务端列服务器上的("服务器提供",归属照 [0004](0004-host-library-is-the-server-directory.md):
  房主两头是同一个文件夹,只列一节)。两头共用同一份列举 `SkinFolder`。
- **选皮肤时**按文件名列出,带小脸;列表上方"打开文件夹"(原版的 `Util.OS.openFile`;手机上没有系统打开器,改显示路径,请用手机自带的文件管理器放图——FCL 通过
  FolderProvider 把游戏目录交给文件管理器);文件夹空着给一句说明和刷新。粗细自动判断,照 skinview-utils 的 `inferModelType`(`SkinVariants`,纯函数):细手臂用不到的四块区域任一块有透明像素、
  或四块全纯黑、或全纯白就是细,否则粗;高清皮肤按比例放大坐标;64×32 旧格式恒为粗。玩家可以手动改。
- **签名只在服务端,用时才签,玩家看不见"签名"这回事**:选中"我的"一张,客户端把 png 和粗细交给服务端(库协议 `skin` 的 `put`,可分片);"服务器提供"的服务端自己读。
  服务端按"图片内容哈希 + 粗细"(`SkinRef`,完整 SHA-256)查签名缓存(`SkinCache`,服务器目录下 `skin-cache/`,按内容寻址、玩家不管理):命中当场穿上;没有就进现有的签名队
  (`SkinSigning`,MineSkin;服主可在钥匙串填 key),签完连同原图存进缓存,再穿上。界面只显示"正在准备皮肤…"和失败的原因码。
  同伴身上记的是对缓存的引用(`binding.json` 的 `skin`:`<哈希>-<粗细>`),穿着的签名数据照旧在名册里。
- **整条流程是一个组合** `Wardrobe`:拿到原图(文件夹、网址、正版玩家名)→ 查缓存 → 没签过就签 → 套上(`Dress`:换身体、记引用)。面板和命令走同一个入口:
  `/numen companion <她> skin player <正版名> | url <网址> | server <文件名>`,不带参数是脱掉。
- **删掉**:皮肤库这一种内容库及其界面、`/numen skin add`、系统文件框、拖拽导入。
- **迁移旧数据**(`SkinMigration`,可重复):服务器"内置"皮肤导出成 png 放进服务端 `skins/`,玩家"我的"皮肤——单机或房主直接导出进同一个文件夹;连专用服务器的玩家,
  服务端在他下次带客户端连上时按段下行(`SkinHandover`,同导出记忆的分段),存进他本机的 `skins/`,发完一张删一张旧记录;签好的数据进缓存,同伴已穿着的绑定改成引用,照穿不误。

## 后果

- 同一张图同一粗细只签一次,不论谁要;改了图或换粗细才重签,换粗细用的是缓存里存着的原图。
- 借正版玩家的皮肤也要取到它的原图才存得进缓存(键是原图的哈希);取不到就是借不成。
- 玩家的图经我们的通道上传到服务端、再由服务端交给 MineSkin;这件事不再在界面上写明,只在文档里。
- 缓存只增不删(每条几 KB),玩家换了很多张图的服务器目录会慢慢长大;要清就整个删 `skin-cache/`,下次用到时重签。
- `config/numen/skins/` 这个名字早年也是旧版客户端存皮肤原图的地方;那些按旧 id 命名的 png 会作为皮肤出现在列表里,无害。
