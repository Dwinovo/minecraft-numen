# 0003 我们的客户端只走 MC 的连接,网络包不拖慢刻

- 状态:已接受,在落地(输入管线第 2 步)
- 日期:2026-10-16
- 提交:`881668a30`(设计稿)
- 另见:`docs/input-pipeline.md` §二、§五

## 背景

大脑与数据搬到服务端以后([0001](0001-server-agent-two-brains.md)),面板历史、语音音频、程序与回执都要经网络来回,量比以前大得多。
用户担心两件事:要不要让服务器另开端口;网络包会不会阻塞服务端运行。自定义网络包本身也有上限(上行单包 32767 字节)。

## 决定

- **我们的客户端不另开端口**,只走 MC 自己的连接;载荷层分片(`Wire`/`Fragments`):下行单包 1 MiB、上行 32767 字节、一条消息至多 8 MiB。
- **只有外部大脑需要端口**:默认关,先做服主自己开端口、建议反向代理加 HTTPS(BlueMap、Dynmap、Simple Voice Chat 都另开端口),文档给隧道的办法。
  和 MC 共用一个端口按开头字节分流,以后单独调研。
- **网络包不许拖慢刻**:拖慢游戏的不是收包,是收到后在主线程上做重活。上行处理器可声明在网络线程上跑;
  分片拼装与解码在网络线程,识别、合成、模型请求、磁盘读写在后台线程,主线程只做碰世界与她状态的那一小步。
- **每位玩家有上行带宽预算**(256 KiB/s),超了丢弃,不排进主线程的队;下行的大东西按页、按段推。

## 后果

- Fabric 侧收包现在一律排进主线程,在网络线程拼装需要 mixin,留到语音那一步。
- 群组服(Velocity、BungeeCord)对网络包的转发要实测。
