# 0001 测试分层照主流:GameTest 只测短、确定、固定场地的集成,算法与长趟进纯 JVM

- 状态:已接受,未落地
- 日期:11-04(与用户定)
- 相关:pathing [0022](../pathing/0022-reliability-matrix.md)(可靠性矩阵)、pathing [0031](../pathing/0031-planning-benchmark.md)(纯 JVM 规划评测)、
  pathing [0044](../pathing/0044-fly-and-glide-verbs.md)(其"验证"一节被本条修订)

## 背景

**现状(11-04 实测)。** 仓库里 803 条 `@GameTest`(两平台各约 766 条进默认整套)。一遍整套里,用例本身只跑约 400 秒,其中
`pathing_matrix` 一批 14 条占 130 秒,`numen_shape`、`numen_build`、`numen_permission` 三批合计 60–110 秒;每遍另有固定开销:
datagen 约 2.5 分钟、构建、`--no-daemon` 冷启动。超时设在 600 刻以上的用例 125 条(矩阵、挖掘、建造、滑翔、绕路等)。

**出的事。** 0044 的执行者一轮 3 小时,写代码约 25 分钟,其余在等测试:
- 滑翔用例在代码生成的丘陵(正弦叠加)、树林上飞一两百格、几百刻,断言不掉血、落点离目标多远、比走路快,5–10 遍挂 1 遍。
- 为了过,执行者改缓地形、缩小树冠、调断言上限;另一轮为了"证明稳定",每遍重启服务器连跑 10 遍。
- 同一批用例并发 6 份时整批挂、3–4 份时过,说明被测代码或场地里有随负载变化的东西。
- 偶发红(生成器种树、身体独处一个维度还在走)每遍整套都可能出一次,每次再花半小时排查。

**主流怎么做(调研,源码确认)。**

| 项目 | 规模 | 写法 | 不稳定 |
|---|---|---|---|
| Fabric API | 114 条 | API 行为,场地多为空结构或 .snbt | 无一条用重试;CI 每次推送跑 |
| NeoForge | 213 条 + 约 40 个 JUnit | 代码在固定位置摆方块 | 全库只有 1 处 `attempts=5, requiredSuccesses=4`(光照引擎异步);PR 必跑 |
| Create | 71 条,67 个 .nbt | 终态断言(`succeedWhen`) | 不稳定的注释掉并写 FIXME(`TestContraptions.java:229`) |
| AE2 | 112 个测试场地 | 代码摆固定方块 | 重试写死 1/1;合成计算放 JUnit(`CraftingSimulationTest`) |
| Botania | 93 条 | 超时多为 20–50 刻 | 未见重试 |
| Mekanism | 65 条 + 36 个 JUnit | 超时 8–20 秒 | 分配算法放 JUnit |
| Baritone | 不用 GameTest | 鞘翅寻路全在纯 JVM 单测:固定种子的地形、逐块核对、断言用范围(`assertEquals(500, lastX, 16)`) | — |

- 测实体移动的 GameTest 只有"生成无 AI 的实体、清零速度、两刻后看速度正负"这种粒度(NeoForge `EntityFluidInteractionTests`、AE2 `TinyTntTestPlots`)。
  没有任何项目用 GameTest 测长距离寻路、AI 导航、几百刻的飞行;没有任何项目在 GameTest 里生成起伏地形。
- 原版的重试(`attempts`/`requiredSuccesses`,26.x 叫 `max_attempts`/`required_successes`)是"N 次里成 M 次",重跑在同一世界、排在所有批次之后。
  无头 `GameTestServer` 第一轮跑完就停机,重试多半来不及生效(读源码推断,未实测);原版证明稳定用的是 26.x 的 `--verify`
  (每条四个方向各 100 份、一次开服并行)。主流没有"重启服务器连跑"的做法。
- Fabric 的自动化测试文档同样建议:逻辑放单元测试,GameTest 测与世界的集成(<https://docs.fabricmc.net/develop/automatic-testing>)。

## 决定

### 一、分层:每一层只测它该测的

| 层 | 跑在哪 | 测什么 | 例子 |
|---|---|---|---|
| 单元测试(JUnit) | 纯 JVM | 算法、推算、判据、解析、决策 | A* 与估价、走法前提、坠落规则推演、`Pilot` 挑键、降落选点、进近与放高度、回执文本 |
| 纯 JVM 场景 | 纯 JVM | 长趟、真实地形下的决策结果;地形是入库的固定夹具 | 鞘翅在丘陵、树林、林中空地的落点、掉不掉血、比走路快;寻路规划评测(0031,照旧) |
| GameTest(默认整套) | 无头服务器 | 工具从入口调到身体、世界、回执的集成;原版物理与我们推算对得上 | 起飞、平地一段滑翔落地不掉血、被方块顶住收工并报、拒绝的提示、背包与容器、权限 |
| 慢批 GameTest | 无头服务器,单独入口 | 必须在真世界里穷举的证明 | 可靠性矩阵(0022) |
| 端到端、评测 | 专用服、真模型 | 照旧 | `e2eTest`、`runBench`、`pathingBench` |

纯 JVM 场景照 Baritone:地形固定(固定种子生成或从评测数据集截取的小块快照,入库作夹具),同一份 `Dynamics` 步进器逐刻推,断言用范围。
它测的是我们的决策;我们的推算和原版物理对不对得上,由 GameTest 里的短用例对照(例如同一组按键下几十刻的位置在给定误差内)。

### 二、GameTest 的规矩

1. **确定。** 同样的代码,在任何负载、并发份数、机器快慢下结果相同。被测代码里只要有随墙钟或负载变的行为(预算按耗时算、读未等齐的后台结果),
   就是被测代码的缺陷,改代码,不改用例。
2. **短。** 默认整套里每条用例 `timeoutTicks` 不超过 600(30 秒游戏时间)。超过的要么缩短场景,要么改成纯 JVM 场景,要么进慢批。
3. **固定场地。** 用结构文件或代码在固定位置摆方块;不用噪声、正弦之类生成的起伏地形,不靠随机。"真实地形"归纯 JVM 场景。
4. **断言终态与回执。** 物理量断言用范围或方向,不断言逐刻轨迹;不为了让用例过去调上限、改场地。
5. **不用重试。** 不写 `attempts`/`requiredSuccesses`。不稳定就是缺陷:查根因修掉。一时修不了的,经用户同意才可隔离(停用并写 FIXME 与原因、
   登记在一处),不许放宽断言或改场地来"修"。
6. **证明稳定只在一次开服里做。** 照原版 `--verify` 的思路:被怀疑的用例在同一服务器里铺多份并行跑,不重启服务器连跑。

### 三、验证节奏(写进 `CONTRIBUTING.md` 与 `AGENTS.md`)

- 改代码时只跑相关的那一批 GameTest(`-Pgametest=` 选套件、按批筛选)与相关单测;不 clean,不 datagen(改了语言文件除外)。
- 交付前跑一次默认整套,两个平台并行。慢批与 `pathingBench` 只在改了寻路执行或规划时跑。
- 目标:默认整套每平台用例时间在 2 分钟内;做到之后,照主流把默认整套放进每次推送的 CI。

### 四、迁移(按耗时与不稳定排先后)

1. **查不确定的来源**:并发份数一多就挂的那批、生成器种树、身体独处维度"still idling"等已知偶发红,逐条找根因(第二节第 1 条)。
2. **滑翔与鞘翅**:丘陵、树林、林中空地、远处未加载区块、高墙等长趟改成纯 JVM 场景;GameTest 只留短用例(起飞空柱、平地一段落地、被顶住收工、
   拒绝提示、推算与原版物理的对照)。0044"验证"一节的场景照此分层,断言意思不变(不落树冠、不掉血、落点离目标的上限、比走路快)。
3. **可靠性矩阵**进慢批,默认整套不跑。
4. **其余超时 600 刻以上的用例**(挖掘、建造、绕路、改地形、漂浮等)逐条看:缩短场景、改纯 JVM 场景或进慢批。
5. **偏慢的批次与批间空档**:已查清并处理。每批开头原版把本批的场地一块块摆出来,其中 `StructureUtils.clearSpaceForStructure` 对每块场地外扩后的
   几万格逐格"放方块并通知邻格",场地却铺在没人用过的新区块里,绝大多数格本来就是目标状态:这是批间空档(默认整套约 70 批、合计约 84 秒)的大头。
   `StructureClearMixin`(GameTest 夹具,两个加载器共用)让本来就是目标状态的格子跳过,空档约减半。走、挖、游、到达这几类用例并成一批
   (`numen_on_foot`),慢的几条叠着跑,少付五次批间固定开销。并批只合"和平正午、各占自己场地、不看别人玩家进出"的几类;
   有真玩家进出、全服广播、整个服务器只有一份的东西(MCP 端点)的用例各自成批,合不得。

每一步迁移,断言的意思不能变弱:一条 GameTest 改成纯 JVM 场景,要在新层里覆盖同样的判据;删掉的 GameTest 在提交里写明去了哪一层。

## 后果

- 默认整套变短、变稳,执行者一轮验证从小时级降到十分钟级;整套能进推送 CI。
- 长趟与真实地形的覆盖挪到纯 JVM,快且可重复;代价是要维护地形夹具,以及"推算与原版物理对得上"这一层对照用例。
- 隔离用例需要用户同意并登记,不会悄悄变多。
- 0044"验证"一节里在 GameTest 上跑真实地形的要求,由本条修订为纯 JVM 场景加短 GameTest。
